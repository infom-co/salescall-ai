## 3. 常駐のさせ方（Windows の上で、止まらずに動かす方法）

⚠️ **大事な制約**：Windows の「サービス」（ログインしなくても裏で動く仕組み）は、**画面を持たない場所で動く**ため、Rakuten Link の画面を操作できず、ログインした人の音声装置も使えない。⇒ 少なくとも**電話を操作する処理は、ログインした人の画面の上で動かす必要がある**。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) データベースだけ Windows のサービス。システムの処理は、ログインのときに起動する「見守り役」が全部まとめて動かす**（落ちた処理を見守り役が起こし直す。PCは自動でログインする設定にする） | 起動の仕組みが1つだけで分かりやすい。電話の操作も確実に動く。起き直したときに「途中で落ちた試行を『結果不明』にする」決まり（DESIGN.md 4-2）を1か所で必ず行える | PCに自動でログインさせるので、PCそのものを守る手当て（置き場所・ディスクの暗号化・画面のロック）が要る。誰かがログアウトすると全部止まる（⇒ 止まれば発信もしないので、害は出ない） |
| (2) 電話の操作だけ画面の上、それ以外（門・判定・取込・ダッシュボードの裏側）はサービス | ログアウトしても、ダッシュボードや取込は使える | 起動の仕組みが2つになり、片方だけ動いている状態の扱いを決める必要がある。最初の段階では、電話が動かなければ業務は進まないので、得が少ない |

**CL-2 の推す案：(1)。** 自動更新による再起動・スリープを止める設定（Intent.md 14-4）は、どの案でも要る。

### 7-2. データベースをクラウドに置くことについて（CL-2 の意見：賛成）
サブスクで他の人も使う方向なら、クラウドのほうが合う。理由：
- 使う人が増えても、データベースは1か所のまま。PCの中に置くと、PCの外から使う人のために、あとで移し替えが要る。
- 控え（バックアップ）・更新・ディスクの暗号化を、提供元に任せられる（CL-1 の条件 2 も満たしやすい）。
- 心配だった「インターネットが切れると門が判断できない」は、**新しい弱点にならない**。会話AI（Gemini）がもともとインターネットを要るので、切れたら電話の業務はどのみち進まない。門が判断できなければ発信しない側に倒れるので、害は出ない。

⚠️ **GitHub はデータベースの置き場にならない**（プログラムの置き場）。相手の電話番号などの個人情報を GitHub に入れてはいけない。

| 候補 | 良い点 | 悪い点・確かめること |
|---|---|---|
| **(1) Supabase（PostgreSQL。東京の置き場あり）** | PostgreSQL そのもの（行単位のセキュリティも使える）。**ログインの仕組み（認証）が付いていて、行単位のセキュリティと組み合わせられる** ⇒ サブスクで利用者が増えたときにそのまま使える。小さく始められる（無料の枠と、月 25ドルほどからの枠。⚠️ 第三者のまとめの値。決める前に公式の料金表で確かめる） | ⛔ Supabase は、画面（ブラウザ）からデータベースを直接読む仕組みも用意している。これを使うと「依頼主IDを必ず受け取る読み書きの層1つ」（DESIGN.md 11章）を通らない道ができる ⇒ **使わない設定にし、読み書きは必ず層を通す**（静的検査と試験で見張る） |

#### 7-2-1. 無料で使えるか（2026-10-13 ユーザーの問い「Fly.io はオプションを付けなければほぼ無料。Supabase は？」）
⚠️ 値は第三者のまとめと公式のページから。決める前に、公式の料金表とユーザーの契約の画面で確かめる。

| | Supabase の無料の枠 | Fly.io の「ほぼ無料」（管理を任せない PostgreSQL） |
|---|---|---|
| 費用 | 0円（データベース 500MB、プロジェクト2つまで） | 小さな機械＋保存の場所で、月 数ドル。新しい契約には無料の枠が無く、古い契約（Hobby など）だけ無料の枠が残っている、とのこと（ユーザーの契約がどちらかは要確認） |
| 控え（バックアップ） | **無料の枠には自動の控えが無い**（有料の枠は毎日・7日分） | **自分で作って見張る**（管理を任せないため。更新・故障時の切り替えも自分） |
| 止まること | **1週間使わないと止まり、手で戻す必要がある** | 止まらない |

- **控えは、無くてよいものではない。** 発信禁止の台帳が消えると、断った相手にまたかける（取り消せない害）。⇒ 実在の相手のデータを入れる本番では、控えが要る。
- CL-2 の推す進め方：
  - **作っている間（架空のデータだけ）**：Supabase の無料の枠（東京）。止まっても害は無い。
  - **本番（実在の相手のデータを入れる前）**：控えのある枠へ上げる（Supabase の有料の枠、月 25ドルほど）。Fly.io の「ほぼ無料」を本番に使うなら、控えを自動で取って、戻せることを試験で確かめる仕組みを CL-2 が作る（手間と、見張りの責任が増える）。
- **【訂正 2026-10-13 ユーザーの指摘】Fly.io は、月の請求が 5ドル未満なら請求を取り消している**（Fly.io の社員の掲示板での返事。公式の文書には無く、続く約束も無い。最初に作られた個人の組織だけが対象）。⇒ 管理を任せない PostgreSQL（月に数ドル）なら、**実質無料**になる。上の表の「新しい契約には無料の枠が無い」は、この取り消しを見落としていた。
  - Fly.io にした場合に CL-2 が作るもの：(1) 控えを毎日自動で取り、**Fly.io とは別の場所にも置く**（Fly.io の保存の場所の毎日の写しだけに頼らない）。(2) 控えから戻せることを、試験で確かめる。(3) 控えが取れなかったら知らせる。
  - 気をつけること：使う量が 5ドルを超えると全額の請求になる。取り消しは約束ではないので、続かなくなったら置き場を見直す。
- どちらも中身はふつうの PostgreSQL で、読み書きは CL-2 の層を通すので、あとで置き場を替えても、プログラムはほとんど変わらない（Supabase のログインの仕組みを使った場合は、そこだけ替えが要る）。

### 7-3. サブスクで他の人も使う方向への備え
- **データの単位に、依頼主の上の層「契約者」を足す**（サブスクでこのシステムを使う人・会社。最初の契約者はユーザー自身）。
  ```
  契約者 ─┬─ 利用者（ログインする人）
          └─ 依頼主 ─ 業務・実施回・タスク・…（DESIGN.md 3章のとおり）
  ```
  - 読み書きの層は「誰が・どの契約者の・どの依頼主のデータを」を必ず受け取る。分離は2段（契約者どうし・依頼主どうし）になり、どちらも行単位のセキュリティと試験で守る。
  - あとから足すと、すべての表と試験を作り直すことになるので、**最初から入れておく**（使い始めは、契約者はユーザー1人だけ）。
  - ⚠️ DESIGN.md 3章の図に1段足すことになる。3章は CL-2 の持ち場なので、決まったら CL-2 が書き換え、19章の自分の節に記録する。
- **認証**：外のログインの仕組みを使う（Supabase に決まれば、その認証。メールアドレスと合言葉、あとで二段階の確かめ）。依頼主はログインしない（いまの決定）。依頼主が見る画面を作ることになっても、同じ仕組みで足せる。

### 7-4. あとで決めること（サブスクにしたときに出てくる問い。いまは決めない）

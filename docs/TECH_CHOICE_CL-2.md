## 3. 常駐のさせ方（Windows の上で、止まらずに動かす方法）

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) データベースだけ Windows のサービス。システムの処理は、ログインのときに起動する「見守り役」が全部まとめて動かす**（落ちた処理を見守り役が起こし直す。PCは自動でログインする設定にする） | 起動の仕組みが1つだけで分かりやすい。電話の操作も確実に動く。起き直したときに「途中で落ちた試行を『結果不明』にする」決まり（DESIGN.md 4-2）を1か所で必ず行える | PCに自動でログインさせるので、PCそのものを守る手当て（置き場所・ディスクの暗号化・画面のロック）が要る。誰かがログアウトすると全部止まる（⇒ 止まれば発信もしないので、害は出ない） |

### 7-2. データベースをクラウドに置くことについて（CL-2 の意見：賛成）
サブスクで他の人も使う方向なら、クラウドのほうが合う。理由：
- 使う人が増えても、データベースは1か所のまま。PCの中に置くと、PCの外から使う人のために、あとで移し替えが要る。
- 控え（バックアップ）・更新・ディスクの暗号化を、提供元に任せられる（CL-1 の条件 2 も満たしやすい）。
- 心配だった「インターネットが切れると門が判断できない」は、**新しい弱点にならない**。会話AI（Gemini）がもともとインターネットを要るので、切れたら電話の業務はどのみち進まない。門が判断できなければ発信しない側に倒れるので、害は出ない。

⚠️ **GitHub はデータベースの置き場にならない**（プログラムの置き場）。相手の電話番号などの個人情報を GitHub に入れてはいけない。

### 7-5. CL-1 の意見（`docs/team/CL-1.md` 4-1）への答え
- (a) 会話の処理が書き込む入口：**用意する**。会話の処理は、自分が受け持つ1回の通話（試行）の分だけを書ける入口を通す（別の通話の記録は書けない）。項目の状態がどう移るか（DESIGN.md 4-4・Q6）は CL-1 の流れの制御が決め、入口は保存するだけ（判断を二重に持たない）。
- (b) 同時に流せる本数：門の上限は設定の値にする（引き継ぎのとおり）。加えて、DESIGN.md 3-1 の「1回線に進行中の試行は1つだけ」の制約と、門の 5-2 の 7（空いている回線を借りる）で、**Rakuten Link を1回線として登録すれば、同時1通話が自動的に守られる**。
- (c) 1つの通話が落ちても、ほかを巻き込まない：見守り役は、**回線ごとに1つの処理**を動かす形を案にする（1回線＝同時1通話なので、通話ごとに分けるのと同じになる）。落ちた処理を起こし直すときは、途中だった試行を「結果不明」にし、すぐにはかけ直さない（DESIGN.md 4-2）。CL-1 と、見守り役の作りを決めるときに詰める。

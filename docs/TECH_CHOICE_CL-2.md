## 1. 言語

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) Python に統一**（業務の土台も、会話も、電話の操作も） | 会話の試作（`phase0/`）をそのまま育てられる。**データの形の定義を1か所に置ける**（CL-1・CL-2・CL-3 が同じ定義を読む。TEAM_PLAN 2章の7）。Windows の画面の操作（Rakuten Link）・音声装置・Excel の読み込み・日本語を単語に分ける処理（G-23）の道具がそろっている。決まりの見張り（DESIGN.md 14章の静的検査）を、Python の標準の道具で書ける | 型の誤りが動かすまで見つからない言語なので、型の検査の道具を必ず使う（試験の一部にする）。画面（ダッシュボード）の見た目の部分は、CL-3 が別の作り方を選ぶ可能性がある（その場合も、データの形は Python の定義から書き出して渡す） |
| (2) 業務の土台と画面は TypeScript、会話と電話は Python | 画面と業務の土台が同じ言語になる。型の検査が強い | **言語が2つになり、データの形の定義が2か所に分かれやすい**（一本化に反する。自動で書き出す仕組みを足せば防げるが、手間と壊れる場所が増える）。会話の試作との間に、もう1つ境目ができる |
| (3) C#（.NET）に統一 | Windows との相性が最もよい（常駐・画面の操作）。型の検査が強い | 会話の試作を書き直すことになる。Google の会話AIの公式ライブラリが、C# で同じだけ使えるかは**未確認**。日本語を単語に分ける処理の選択肢が少ない |

**CL-2 の推す案：(1) Python に統一。** 版は、決まったら CL-1 の試作の版に合わせる（この作業環境では 3.13 で試験できる）。

## 2. データベース

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) PostgreSQL を、本番のPCの中で動かす**（あとでクラウドへ移せる形にしておく） | 一意の制約・部分一意の制約・取引を、どれも正式に持つ。**行ごとに読める人を制限する機能（行単位のセキュリティ）がある** ⇒ 依頼主の分離を、読み書きの層と二重に守れる（DESIGN.md 11章）。複数の処理が同時に書いても安全。順番待ちの取り出しに向いた機能（ほかの処理が取っている行を飛ばして取る）がある。依頼主もログインすることになったとき・回線を別の機械に増やすとき、そのまま使える。無料。Windows 用の公式の入れ方があり、Windows のサービスとして動く。この作業環境でも試験できる | 入れて・更新して・控え（バックアップ）を取る手間がある（控えは、決まった時刻に自動で取る設定を作る）。SQLite より重い |
| (2) SQLite（1つのファイル） | 入れる手間が無い。ファイル1つで控えが簡単。一意の制約・部分一意の制約・取引はある。書くのは同時に1つだけなので、門の取引が単純に正しくなる | **行単位のセキュリティが無い**（依頼主の分離は、読み書きの層だけで守る）。書けるのが同時に1つなので、通話の本数・処理の数が増えると詰まりうる。依頼主のログイン・別の機械からの利用になったら、移し替えが要る |
| (3) クラウドの PostgreSQL（管理を任せる型） | 控え・更新を任せられる。依頼主がログインする画面をクラウドに置くときに自然 | 費用が毎月かかる。インターネットが切れると門が判断できない（⇒ 発信しない側に倒れるので害は出ないが、止まる）。**相手の電話番号などの個人情報をクラウドに置く**ことになり、委託・安全管理の確かめが要る（Intent.md 13章） |

**CL-2 の推す案：(1) PostgreSQL を本番のPCの中で。** 理由：取り消せない害の3つ（二重発信・断った相手への再架電・別の依頼主のデータの混入）を、データベースの機能で直接守れるものが最も多い。依頼主のログインが決まったときに、(3) へ移すかを改めて比べる。

## 3. 常駐のさせ方（Windows の上で、止まらずに動かす方法）

⚠️ **大事な制約**：Windows の「サービス」（ログインしなくても裏で動く仕組み）は、**画面を持たない場所で動く**ため、Rakuten Link の画面を操作できず、ログインした人の音声装置も使えない。⇒ 少なくとも**電話を操作する処理は、ログインした人の画面の上で動かす必要がある**。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) データベースだけ Windows のサービス。システムの処理は、ログインのときに起動する「見守り役」が全部まとめて動かす**（落ちた処理を見守り役が起こし直す。PCは自動でログインする設定にする） | 起動の仕組みが1つだけで分かりやすい。電話の操作も確実に動く。起き直したときに「途中で落ちた試行を『結果不明』にする」決まり（DESIGN.md 4-2）を1か所で必ず行える | PCに自動でログインさせるので、PCそのものを守る手当て（置き場所・ディスクの暗号化・画面のロック）が要る。誰かがログアウトすると全部止まる（⇒ 止まれば発信もしないので、害は出ない） |
| (2) 電話の操作だけ画面の上、それ以外（門・判定・取込・ダッシュボードの裏側）はサービス | ログアウトしても、ダッシュボードや取込は使える | 起動の仕組みが2つになり、片方だけ動いている状態の扱いを決める必要がある。最初の段階では、電話が動かなければ業務は進まないので、得が少ない |

**CL-2 の推す案：(1)。** 自動更新による再起動・スリープを止める設定（Intent.md 14-4）は、どの案でも要る。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **(1) データベースの表を順番待ちに使う**（タスクの「予定時刻」を見て候補を出し、門が取引の中で予約する） | **正本がデータベース1つだけ**になる（予定を書くのは「次の動きの決定」だけ、予約は門だけ、という設計（DESIGN.md 2章 Q2・Q4）がそのまま形になる）。新しい部品が要らない。通話後の検証の順番待ちも、同じやり方で持てる | 1秒より細かい速さは出ない（電話の業務には十分） |
| (2) 専用の順番待ちの部品（Redis など）を足す | 大量・高速の処理に強い | **状態を持つ場所が2つになる**（データベースと順番待ちの部品で、食い違いが起きうる＝一本化に反する）。Redis は Windows を正式には支えていない |

**CL-2 の推す案：(1)。**

## 5. 認証（誰がログインして、何を見てよいか）

**ダッシュボードを運営者だけが使うか、依頼主もログインするか（18-1 の5）で変わる。** CL-3 が材料を出すので、決まってから選ぶのがよい。どちらになっても、次は先に作れる：
- データの読み書きは、**「誰が」「どの依頼主のデータを」**を必ず受け取る層1つだけを通す（DESIGN.md 11章・Q14）。ログインの方式は、この層の外側で差し替えられる形にする。

| 案 | 良い点 | 悪い点 |
|---|---|---|
| (1) 運営者だけ：本番のPCの中（と社内の回線）だけで画面を開き、運営者の利用者名と合言葉でログイン | 外から入られる入口が無い。簡単 | 外出先から見られない。依頼主には、出力のファイルで渡す |
| (2) 依頼主もログイン：外の決まったログインの仕組み（例：Google のアカウントでログイン）を使い、利用者ごとに見てよい依頼主を決める | 依頼主が自分で結果を見られる | 画面をインターネットに出す必要があり、守る手当てが増える。データベースの置き場（2章の (3)）にも関わる |

**CL-2 の推す案：いまは決めない。** 18-1 の5 が決まってから選ぶ。それまでは、読み書きの層（誰が・どの依頼主か）だけを作る。

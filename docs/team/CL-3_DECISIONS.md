## 1. ダッシュボードを運営者だけが使うか、依頼主もログインするか（Intent.md 18-1 の5）

> ✅ **決定（2026-10-13）**：依頼主はログインしない。将来、ユーザー以外もサブスクでこのシステムを使う方向に備える。⇒ 下の「決まったこと」。以下は、決める前に出した材料（記録として残す）。

**どの案でも、運営者のログインは要る。** 検証モードで「誰が承認したか・誰が結果を直したか」を記録するため（DESIGN.md 10章）。決めていただきたいのは、**依頼主にも画面を開かせるか**です。

| | 案A：運営者だけ | 案B：依頼主もログインする（自分の依頼主の画面だけ、見るだけ） | 案C：まず案A。あとで依頼主の「見るだけの画面」を足せる形にしておく |
|---|---|---|---|
| 依頼主への渡し方 | ファイル・報告書・書き戻し（7-3） | 画面＋ファイル・報告書・書き戻し | 当面は案Aと同じ |
| 良い点 | ・依頼主どうしが互いの画面に入る道が、そもそも無い（分離の守りが単純）<br>・画面に、門の理由・費用の原価・運転の状態などを全部出せる（見せてよいかの選別が要らない）<br>・本番PC（Windows）の中だけで動かせ、インターネットに画面を出さなくてよい<br>・早く作れる | ・依頼主が自分で進み具合・結果を見られ、問い合わせと報告の手間が減る | ・今は案Aの良い点のまま早く安全に進められる<br>・あとで依頼主の画面を足しても、作り直しにならない（下の「備え」） |
| 悪い点 | ・依頼主が途中経過を知りたいとき、報告を送る手間がかかる（定期の報告書の自動送付で補える） | ・画面を外から開けるようにする必要がある＝インターネットに出す置き場（クラウドなど）が要り、言語・置き場所の判断（14-2。CL-2 が案を出す）に響く<br>・ログイン・パスワードの再設定・二段階の確認・利用者の管理・操作の記録が要る<br>・依頼主に**見せてはいけないもの**の選別が要る：費用の原価（採算）、APIキーの識別名、運転の状態、門の理由のうち「依頼主をまたいだ間隔」（ほかの依頼主が同じ番号にかけたと分かる。DESIGN.md 15-3 の 7）、通話後の検証の「AIの言い間違いの疑い」など<br>・画面を2通り作り、分離の試験も依頼主の利用者の分だけ増える（Intent.md 5-6 の S-15） | ・依頼主の画面を足すときに、置き場（外から開けるか）を決め直す |
| 備え | ― | ― | 「誰が・どの依頼主を・何をしてよいか」を確かめる層（Q14。CL-2）に、最初から「利用者の種類（運営者／依頼主の利用者）」を持てる形にしてもらう（CL-2 へのお願い） |

- **CL-3 のおすすめ：案C**（当面は案A）。理由：(1) 取り消せない害の「別の依頼主のデータの混入」の道が一番少ない、(2) 依頼主の画面を出すには置き場の判断（14-2）が先に要る、(3) 検証モードの期間は、どのみち運営者が結果を確かめてから送るので、依頼主が画面で生の途中経過を見る意味が小さい。
- あわせて聞きたいこと：**運営者の中で、できることを分けるか**（例：承認・停止・書き戻しの実行ができる人／見るだけの人）。分けない場合も、操作の記録には「誰が」を残します。

## 2. 依頼主が要る出力の形と、書き戻しの要件（Intent.md 18-1 の6）

> ✅ **決定（2026-10-13）**：スプレッドシートや Excel の、依頼主が指定する形で報告することが多いと見込む。出力は、あとから依頼主ごとに合わせる前提にする。⇒ 下の「決まったこと」。以下は、決める前に出した材料（記録として残す）。

渡す内容（DESIGN.md 7-1b）はユーザー確定済みなので変えません。決めていただきたいのは**形**です。最初の業務（18-1 の4）が決まっていないので、まず「既定の形」を案にしました（DESIGN.md 7-3）。依頼主ごとに変えられる形にしてあります（出力の設定で上書き）。

### 2-1. ファイルの形
| 案 | 良い点 | 悪い点 |
|---|---|---|
| (a) CSV・UTF-8（BOM 付き）【既定の案】 | 表計算ソフトで開いても文字化けしにくい。「✕」が書ける。作りが単純 | ごく古い表計算ソフトや、依頼主の取込の仕組みが Shift_JIS しか読めないと困る |
| (b) CSV・Shift_JIS | 日本の古い業務システムでも読める | **「✕」を書けない**（確かめた）。「×」などの代わりの字を決める必要がある。会社名の一部の字（外字・旧字）も書けないことがある（書けないときは出力を止めて場所を出す） |
| (c) Excel のファイル（xlsx） | 文字化けが起きない。列の幅・見出しの色など、見やすくできる | 作りが少し増える。依頼主のシステムに読み込ませるには不向きなことがある |
| (d) Google スプレッドシートへ直接書く | 依頼主がすぐ見られる。ファイルの受け渡しが要らない | 依頼主のアカウントの権限をもらう必要がある。実際は「書き戻し」と同じ扱い（2-4） |

### 2-2. 1行の単位と、出す行
| 決めること | 既定の案 | ほかの案 |
|---|---|---|
| 1行は何か | 1行＝相手1件（タスク）の最終の結果 | 1行＝1回の発信（かけ直しも別の行） |
| どの行を出すか | 判定が済んだものだけ | 全件（まだ終わっていない相手も「途中」として出す） |
| 毎回、全部か差分か | 毎回その時点の全部（依頼主は前のファイルを置き換える） | 前回から変わった行だけ |

### 2-3. 列（既定の案。DESIGN.md 7-3-4）
依頼主の管理番号／相手の名前／電話番号／業務の結果／通話の終わり方／かけた回数／最後にかけた日時／質問ごとの列（値・選んだ選択肢・「-」・「✕」）
- 既定では出さない：録音・文字起こし・費用・内部の状態の名前など。要る依頼主には足せる。
- 聞きたいこと：**依頼主が自分の表と突き合わせる鍵**（依頼主の管理番号）を、取込のときに必ず出してもらうか。

### 2-4. 報告書
| 決めること | 既定の案 |
|---|---|
| 要るか | 要る（実施回ごと） |
| 中身 | 件数、業務の結果ごとの数、終わり方ごとの数、必須項目ごとの「取れた」「-」「✕」の数、未完了の理由、判定できない件数（DESIGN.md 7-3-6） |
| 費用を載せるか | 載せない（運営者の採算の情報なので） |
| 形と頻度 | ⏳ 聞きたい（PDF／メールの本文／画面、実施回の終わりに1回／毎日） |

### 2-5. 書き戻し（依頼主のシステムへ、結果を直接書く）
| 決めること | 案 |
|---|---|
| 要るか | (1) 要らない（ファイルだけ）【最初の業務ではこれで足りるなら、いちばん安全】 (2) 要る |
| 先 | Google スプレッドシート／kintone／Salesforce／依頼主の独自の仕組み（API）など。⏳ 依頼主に聞く |
| タイミング | 1件ずつ、判定のあとすぐ／1日1回まとめて |
| 先に求める条件 | **「こちらの鍵で、あれば上書き・無ければ作る」ができること。** できない先は、返事が来ないまま時間切れになったとき、自動で再送しない（二重に登録しないため。人が確かめてから再送）（DESIGN.md 4-5） |

### 2-6. 取れなかった項目の書き方
- 既定は「-」（わからない）・「✕」（答えたくない）（ユーザー確定）。依頼主から別の書き方の指定があれば、出力の設定で変える。
- Shift_JIS を選ぶ依頼主には、「✕」の代わりの字（例：「×」）を決めていただく必要があります。

## 5. 画面の作り方（Intent.md 14-2 の「画面のフレームワーク」）

> ✅ **決定（2026-10-13）**：案A（FastAPI・Jinja2・HTMX）。画面は Fly.io で動かし、**Fly.io の月の請求が 5ドル未満に収まることが重要**（ユーザー）。⇒ 決まり6つを Intent.md 5-5 に書いた。以下は、決める前に出した材料。

### 5-1. 画面に求めること（比べる物差し）
1. **守りがサーバー側だけにあること**：画面からの読み書きは、すべてサーバーで CL-2 の読み書きの層（Python）を通して確かめる（Intent.md 11-2・原則4）。画面の側に守りを置かない。
2. **データの形を画面の側で定義し直さないこと**（`docs/TEAM_PLAN.md` 2章の7）。
3. **Python に統一**（2026-10-13 ユーザー確定）。
4. いまはユーザー1人。**将来はサブスクで、外から多くの人がログインする**（5-1 の決定）。ログインと、なりすましの送信への備えが要る。
5. 中身（Intent.md 5-5）：一覧・検索・詳細・録音の再生・承認・設定の編集・取込のプレビュー・出力の型の編集（列の対応付け）・状況の数（自動で新しくなる）・停止のボタン。
6. **分離の試験（Intent.md 5-6 の S-1〜S-19）を、画面を通して機械で流せること。**
7. 作る手間・直しやすさ（CL-1〜CL-3 のAIと、ユーザーが読める）。

### 5-2. 案
| | 案A：サーバーで画面を作る（FastAPI ＋ 画面のひな形 Jinja2 ＋ HTMX） | 案B：Django（画面・ログイン・管理画面がそろった道具） | 案C：データの口だけ Python（FastAPI）、画面は別の言語（TypeScript・React） |
|---|---|---|---|
| どんな形か | サーバー（Python）が画面のHTMLを作って返す。一部だけ入れ替える動き（数の自動更新・承認ボタン）は HTMX という小さな仕組みで書く | 同じくサーバーが画面を作る。ログイン・権限・なりすましの送信への備え・管理画面が最初から付いている | ブラウザの中で動く画面のプログラムを別に作り、Python のデータの口とやりとりする |
| 良い点 | ・**全部 Python**。画面の処理は薄く、確かめはすべてサーバーの層<br>・データの形は CL-2 のものをそのまま読める（二重に定義しない）<br>・部品が少なく、作りが単純<br>・画面を通した試験を、Python の試験の中で流せる（S-1〜S-19） | ・ログイン・権限・送信への備えが成熟していて、サブスクの多人数にも向く<br>・全部 Python | ・いちばん凝った画面を作れる（出力の型の列の対応付けを、引っ張って並べる、など）<br>・サブスクの製品として見た目を磨きやすい |
| 悪い点 | ・ログイン・送信への備えは、別の部品を選んで組み合わせる（選ぶ手間と、守りの責任が増える）<br>・引っ張って並べるような凝った操作は手間がかかる（要る所だけ小さな画面のプログラムを足す） | ・**Django は自分のデータの定義と表の作りの仕組みを持つ**。使うと、CL-2 の層・表の作りと別に、データの形が2つできる（一本化に反する）。使わないと、Django の良さ（ログイン・管理画面）の多くが使えない（ログインの仕組みも Django の表に頼るため） | ・**言語が2つ**になる（Python に統一の決定と食い違う）<br>・データの形を画面の言語でもう一度書く必要が出る（自動で作る手もあるが、仕組みが増える）<br>・作る手間がいちばん大きい。ブラウザに渡す合言葉（鍵）の扱いなど、守る所が増える |
| 外した案 | Streamlit・NiceGUI など「Python だけで画面も作る道具」：1人で使う分析の画面には向くが、多人数のログインと、操作ごとのサーバー側の確かめを自分で組み込む形になり、サブスクに向かないと判断した | | |

- **CL-3 のおすすめ：案A。** 理由：(1) 守りがサーバーの1か所（CL-2 の層）に集まる、(2) データの形を二重にしない、(3) Python に統一の決定に合う、(4) あとで凝った画面が要っても、データの読み書きは CL-2 の層にあるので、画面だけを案C の形に替えられる（作り直すのは画面だけ）。
- 案A でも、ログインの仕組みは CL-2 があとで決めるもの（`docs/TECH_CHOICE_CL-2.md` 8章）を使う。画面の側で、別の利用者の表を作らない。

### 5-3. あわせて決めていただきたいこと：画面をどこで動かすか
| | (i) 本番のPCの中 | (ii) Fly.io（データベースと同じ置き場） |
|---|---|---|
| 良い点 | インターネットに画面を出さないので、外からの攻撃を受けにくい | どこからでも開ける。サブスクの契約者も使える。データベースに近い |
| 悪い点 | PCの外から開けない（サブスクには使えない）。PCが止まると画面も見られない | インターネットに出すので、**最初からログインがしっかりしている必要がある**。⚠️ 動かす機械が1つ増えるので、Fly.io の「月 5ドル未満は取り消し」（`docs/TECH_CHOICE_CL-2.md` 7-2-1）を超えて、全額の請求になりうる（量を確かめる） |

- CL-3 のおすすめ：**作っている間（架空のデータだけ）は手元で動かし、実在の相手のデータを入れる前に (ii) へ移す**。どちらでも同じプログラムで動く形にする（案A なら、置き場が替わっても中身は同じ）。
- 停止のボタン（Intent.md 5-5 の (10)）は、どこで押しても、データベースの「運転の状態」に書かれ、本番のPCの門がそれを読む（門は CL-2）。

## 0. この設計の芯（5つ）

1. **判断は、問いごとに1か所だけ。** 「今かけてよいか」「完了か」「次はいつか」「このエラーはどうするか」は、それぞれ**1つの処理だけ**が答える。ほかの場所は、その答えを読むだけにする（2章）。
2. **取り消せない操作は、「判定」と「予約」を1つの取引で行う門だけが許す。** 判定と実行の間にすき間があると、同時に動く2つの処理が両方とも門を通り、同じ相手に二重にかける（5章）。
3. **会話のいまの位置は、プログラムが持つ。AIは持たない。** AIは「聞く・話す・答えを分類する」だけを受け持つ。次にどの質問へ進むかは、プログラムが決める（6章）。
4. **聞き間違えやすい項目は、聞いたその場で相手に確かめる。** 相手本人の「はい」だけが、AIとは独立した証拠になる。AIが聞き取った値どうしが一致しても、同じ耳で聞いた結果どうしなので、独立した証拠にはならない（6-4）。最後にまとめて読み上げるのではなく、その場で確かめるので、途中で切られても確かめた分は残る（2026-10-12 ユーザー確定）。
5. **「わからない」は、第3の値として最後まで運ぶ。** 0・空・既定値で埋めない。わからないものは、完了にも発信可にも倒れない（1章）。

## 1. 「精度100%」について ── 作りで保証できること・できないこと

**正直に書く。AIと音声に頼る部分は、作りだけでは100%にできない。** そこで、次の2つに分ける。

| 区分 | 中身 | どう扱うか |
|---|---|---|
| **作りで100%にする**（不変条件） | (1) 門を通らない発信は0件 (2) 同じ番号への同時の二重発信は0件（依頼主をまたいでも） (3) 発信禁止台帳に載った番号への発信は0件 (4) 停止中の新規発信は0件 (5) 必須項目が「取れた」（4-4）でない「完了」は0件 (6) 別の依頼主のデータの参照・更新は0件 (7) 取込に失敗したときの部分的な更新は0件 (8) 書き戻しの二重登録は0件 (9) キーの値がログ・画面に出るのは0件 | データベースの一意制約・取引・静的検査・テストで、**機械が守る**。わざと壊したら本当に止まるかも試す（14章） |
| **作りでは100%にできない**（AI・音声・人に依存） | 聞き取りの誤り、回答の分類の誤り、AIが言ってはいけないことを言う、相手が誤って「はい」と言う、留守番電話や自動音声の見分け | 測って下げる。**誤りが起きても、取り消せない側（完了・発信可）には倒れず、「不明」「要確認」に落ちる**ように、誤りの向きを作りで決めておく |

### 1-1. 誤りの向きを決める、とは
| 誤り | 起きたときの向き |
|---|---|
| 聞き間違えやすい項目（日付・数など）を聞き違えた | その場の確認で相手が訂正する ⇒ 正しい値に直る。確かめる前に切られたら「確認済み」にならない ⇒ その項目は取れていない扱い（依頼主へは「-」） |
| 「はい／いいえ」などの答えを、逆に分類した | はっきり聞こえたと AI が思った答えには、その場の確認をかけない。代わりに、通話後の検証（6-12 の (a)）で別の音声認識でも聞き、食い違えば「-」にする ⇒ 誤った値は渡らず、「-」に落ちる |
| 分類を誤った（違う分岐へ進んだ） | 必須項目が埋まらない、またはその場の確認で食い違いが出る ⇒ 「未完了」か「要確認」 |
| 留守番電話を人と見誤った | その場の確認に「はい」が返らない ⇒ 聞き間違えやすい項目が「確認済み」にならない ⇒ 「未完了」 |
| 相手の「やめて」を聞き逃した | **通話中には防げない。** 通話後の検証（6-12 の (c)）で、拒否の言葉を探して発信禁止に登録する（取り逃しの回収）。次の発信の前に必ず検証が終わるので、二度目の発信は起きない |

### 1-2. 残る誤り（ゼロにはできないもの）
次の2つは作りでは消せないので、16-3 の誤判定率として測る。
- **相手が誤った確認に「はい」と言い、それを正しく聞き取った場合**：「確認済み」なのに値が誤っている。
- **その場の確認をかけない項目**（「はい／いいえ」・選択肢など）で、**会話AIと別の音声認識が、そろって同じように聞き違えた場合**：別の耳（6-10 の (5)）でも見つけられない。

### 1-3. 「言ってはいけないこと」は、指示で防ぎ、記録で見つける
- Gemini Live は「音声のまま考えて音声のまま話す」ので、声が相手に届く前にプログラムが中身を確かめる場所は無い。
- **口に出す前にリアルタイムで確かめて止める仕組みは、作らない**（2026-10-12 ユーザー確定。「無理があるし、会話が成り立たない」ため）。
- **防ぎ方**：言ってはいけないことを、目的・業務設定・トークスクリプトと一緒に、**セッションの最初に指示として渡す**。セッションが替わるとAIは忘れるので、**どのセッションを始めるときも必ず渡し直す**（6-6）。
- **見つけ方**：通話後に、AIが言ったことの文字起こしを、言ってはいけないことに当てる。見つかったら、その業務を止めて人が見る（6-12 の (d)）。
- ⇒ Intent.md 1-3 の「AIによる許可されていない約束0件」は、作りで保証するものではなく、**指示で防ぎ、記録で見つけて止める**ものとして扱う。

## 2. 一本化の表 ── 問いごとに、答える場所は1つ

**この表が、設計の中心である。** 新しい処理を書くときは、まずこの表で「その問いに答える場所が、もう在るか」を見る。在れば、それを呼ぶ。2つ目を作らない。

| No. | 問い | 唯一の答える場所 | 読むだけの側 | ⛔やってはいけない二重化の例 |
|---|---|---|---|---|
| Q1 | この番号は、どの番号か（同じ相手か） | **番号の正規化**（`normalize_phone`）：表記ゆれをそろえ、種別（携帯・固定・フリーダイヤル等）を返す。正規化できなければ「不明」 | 取込、発信禁止の登録、門、折り返しの照合、重複判定 | 取込とは別に、門の中で独自に番号を整形する |
| Q2 | **今この相手にかけてよいか** | **発信の門**（`claim_dial`）：判定と予約を1つの取引で行う（5章） | スケジューラー（候補を出すだけ）、画面（理由を出すだけ） | スケジューラーや画面が、時間帯や発信禁止を自分で判定する |
| Q3 | この相手は、かけてはいけない相手か | **発信禁止台帳**（依頼主ごと＋システム共通。`core/dnc.py`）。番号で決まる「かけない理由」（不明・かけない種類・設定でかけない種類・発信禁止）は **`core/number_policy.py` の1か所**で答える | 門と取込（どちらも `number_policy` を通す。2026-10-14） | 業務設定の「除外条件」を、門の中で別に判定する（⇒ 番号で決まる除外は取込時に台帳へ入れる。データの条件で決まる除外は、取込時にタスクを作らず理由を残す） |
| Q4 | 次に、いつ・何をするか（かけ直す／終える） | **次の動きの決定**（`next_action`）：`scheduled_at` を書くのはここだけ | スケジューラー、画面 | 例外処理の中で、その場で再発信の予定を入れる |
| Q5 | **この業務は完了か** | **業務の判定**（`judge_task`）：入力から結果が1つに決まる処理。版番号を持つ | 出力、報告、画面、費用集計 | 出力の処理が「必須項目が埋まっていれば完了」と自分で判定する |
| Q6 | この項目は取れたか | **項目の状態**（4-4）：会話制御だけが書く。聞き返し・復唱・念のための確認の回数も、ここで数える（6-11） | 判定、出力 | 文字起こしからの抽出で、項目を「確認済み」に上げる。AIの記憶で回数を数える |
| Q7 | 会話はいま、どこにいるか | **流れの制御**（6章）：プログラムが持つ | 会話AI（AIの操作への返事で、次の質問を受け取る。張り替えのときは `start_session` が、いまの位置を渡す） | AIの記憶に流れを任せる |
| Q8 | 電話口の相手は誰か（受付・本人・留守電・自動音声・FAX） | **相手の種別**（4-3）：回線の信号と音声の分類を、決まった優先順位で1つにまとめる | 流れの制御、判定 | 回線モジュールとAIが、それぞれ別に留守電を判定する |
| Q9 | このエラーは何で、どうするか | **エラーの分類**（`classify_error`）＋**処置の表**（9章） | すべての呼び出し元 | 呼び出し元ごとに、その場で再試行やキー切替を書く |
| Q10 | この設定値は、結局いくつか | **設定の合成**（`resolve_settings`）：項目ごとに決めた合成の種類で解く（8章） | すべての処理 | 処理の中で「業務設定に無ければ依頼主設定」と個別に読む |

| Q13 | 止まっているか | **運転の状態**（全体・依頼主ごとの停止） | 門だけが読む | 各処理が、それぞれ停止の印を見て止まる |
| Q14 | このデータを、この人が見てよいか | **アクセスの確認**（依頼主IDを必須にした、データの読み書きの層1つ） | すべての画面・API | 画面ごとに、依頼主IDで絞り込む処理を書く |
| Q15 | どのAPIキーを使うか | **キーの選択**（キーとプロジェクトの対応表つき。12章） | 会話AI接続 | 接続処理の中で、エラーのたびに次のキーへ進む |
| Q16 | いくら使ったか | **利用量の台帳**（実測と推定を区別する） | 画面、採算、門（予算の上限） | 画面が通話時間から料金を計算し直す |
| Q17 | 結果を、どこへ送ったか | **連携の台帳**（送り先ごと。二重登録防止の鍵つき） | 画面、再送 | 再送の処理が、送ったかを外部システムに聞いて判断する |
| Q18 | 会話AIのセッションを、何を渡して始めるか | **セッションの開始**（`start_session`）：1回の通話（試行）につき新しいセッションを開き、版つきの指示文（目的・業務設定・スクリプト・言ってはいけないこと）と、流れの制御が持つ「いまの位置・取れた項目」を、**必ず**渡す（6-6） | 会話AI接続（新規・つなぎ直し・キー切替のすべて） | つなぎ直しやキー切替の処理が、自分でセッションを開く（⇒ 指示の渡し忘れが起きる） |
| Q19 | この項目は、その場で確かめるか | **項目の型の一覧**：型（日付・時刻・数・金額・名前・電話番号・メール・住所・はい/いいえ・選択肢 など）ごとに、確かめるかを決める（4-4） | 指示文を作る処理（確かめ方の決まりを指示に書く）、流れの制御（確かめが済むまで次へ進めない） | 業務ごと・質問ごとに、確かめるかをばらばらに書く |
| Q21 | 通話のあとに、何を確かめるか | **通話後の検証**（6-12）：1つの処理が、決まった4つを順に行う | 判定（結果を読む）、発信禁止台帳（登録を受ける）、運転の状態（業務の停止を受ける） | 別の音声認識・拒否の言葉探し・禁止事項の当て込みを、それぞれ別の処理で書く |
| Q20 | 依頼主へ渡すとき、取れなかった項目をどう書くか | **出力の書き方**（7-1b）：既定は「-」（わからない）と「✕」（拒否）。依頼主の指定があれば、その書き方 | 出力・報告・書き戻し | 出力先ごとに、空欄・「不明」・「なし」などをばらばらに書く |

**機械での見張り**：Q2・Q4・Q5・Q9 の「書く側」が1か所であることは、静的検査で確かめる（14章 I-12）。

## 3. データの単位（何が、何を持つか）

Intent.md 10-1 は「状態を4つの軸に分ける」と決めたが、**どの軸を、どのデータが持つか**が決まっていなかった。そのため「再発信をまたいで業務状態はどこにあるのか」が曖昧だった。ここで決める。

**【変更 2026-10-13 CL-2】** 依頼主の上に「契約者」の層を足した（Intent.md 11-2・14-1。サブスクで他の人も使う方向への備え）。業務の状態・次の予定は「追記だけの記録」の最新を正本にした（3-0）。番号の台帳から「進行中」の旗を外した（3-1）。

```
契約者 ─┬─ 利用者（ログインする人。ログインの仕組みはあとで決める）
        ├─ 回線（電話をかける線。どの契約者のものか。見守り役が借りる）
        └─ 依頼主 ─┬─ 業務 ── 業務設定の版（変更不可）── 質問（変更不可）
                   ├─ 実施回（取込単位）── 版の割り当ての記録（追記だけ。最新が、いま使う版）
                   │      └─ タスク（実施回 × 連絡先）
                   │             ├─ 試行（1回の発信。通話の状態を持つ）
                   │             │     └─ 区間（相手が替わるごと：受付 → 担当者）
                   │             ├─ 項目の値（項目ごとの状態と、根拠の発話）
                   │             ├─ 結果の版（業務の状態を持つ。追記だけ。最新が、いまの業務の状態）
                   │             ├─ 送ってよい印（結果の版ごと。承認の部分だけが付ける）
                   │             ├─ 次の動きの記録（追記だけ。最新が、いまの予定）
                   │             └─ 連携（送り先ごと。連携の状態を持つ）
                   ├─ 連絡先（正規化した番号。依頼主ごと）
                   ├─ 発信禁止台帳
                   └─ 利用量の台帳
システム共通：発信禁止（緊急通報番号など）、APIキーとプロジェクトの対応表、停止の記録（追記だけ。全体・契約者・依頼主）、
            番号の台帳（正規化した番号ごとに「最後に予約した時刻」だけを持つ。依頼主をまたいだ間隔の制限と、
            同じ番号の予約を順番にする鍵に使う。どの依頼主かは持たない）
```

### 3-0. 作りで守る3つの決まり【追加 2026-10-13 CL-2】
1. **依頼主の取り違えは、データベースが拒む。** 依頼主のデータの表は、どれも契約者IDと依頼主IDを持つ。親への参照は「（依頼主ID, 親のID）の組」で張る。⇒ 別の依頼主の親（連絡先・実施回・タスクなど）を指す行は、処理に誤りがあっても作れない。試行が持つ番号も「（依頼主ID, 連絡先ID, 番号）の組」で連絡先を参照し、連絡先の番号と食い違えない。
2. **同じことを2か所に書かない（状態の正本は1つ）。** 進行中かどうかは試行の状態だけ、業務の状態は結果の版の最新だけ、次の予定は次の動きの記録の最新だけ、止まっているかは停止の記録の最新だけ。⛔「進行中」などの旗を別に持たない（落ちたときに降ろし忘れて、二度とかけられない／降ろし間違えて二重にかける）。
3. **変えてはいけない記録は、データベースが変更を拒む。** 業務設定の版・質問・版の割り当ての記録・結果の版・送ってよい印・次の動きの記録・停止の記録・試行の状態の履歴は、足すことしかできない（書き換え・消しは拒む）。

### 3-1. 一意の約束（データベースの制約で守る）
| 約束 | 制約 | 防ぐ害 |
|---|---|---|
| 同じ依頼主の中で、同じ番号は1つの連絡先 | 一意（依頼主ID, 正規化番号） | 表記ゆれで、同じ相手が2件になる |
| 1つの実施回で、同じ連絡先は1タスク | 一意（実施回ID, 連絡先ID） | 同じファイルを2回取り込んで二重にかける |
| 1つの連絡先に、進行中の試行は1つだけ | 部分一意（連絡先ID, 状態が進行中＝`claimed`〜`ending` のもの） | 同時に2つの処理が、同じ相手へかける |
| **1つの番号に、依頼主・契約者をまたいで進行中の試行は1つだけ** | **【変更 2026-10-13】部分一意（正規化番号, 状態が進行中のもの）を、試行の表に張る。** 制約はすべての依頼主の行にまたがって効く（行ごとの読む制限には左右されない）。前は番号の台帳に「進行中」の旗を立て、試行が終わったら降ろす形だった（3-0 の2に反する。15-2 の8） | 別々の依頼主の業務が、同じ番号へ同時にかける（依頼主ごとの連絡先の制約では防げない） |
| 1回線に、進行中の試行は1つだけ | 部分一意（回線ID, 状態が進行中のもの） | 1台の電話で2通話を始めようとする |
| 依頼主の発信禁止台帳で、同じ番号の有効な登録は1つ | 部分一意（依頼主ID, 正規化番号, 取り消されていないもの） | 登録の重なり・取り消しの取り違え |
| 1タスクの1項目は、値が1つ | 一意（タスクID, 項目ID） | 値の取り違え |
| 1タスクの結果の版は、重ならない | 一意（タスクID, 版の番号） | 「どれが最新か」が2つになる |
| 1つの送り先へは、同じ結果を1回だけ | 一意（タスクID, 送り先ID, 結果の版） | 再送による二重登録 |
| 子の行は、親と同じ依頼主 | 組の参照（3-0 の1） | 別の依頼主のデータの混入 |

### 3-2. 業務設定の版をどこで固定するか（Intent.md では未定義だった）
- **実施回が、版を固定する。** 実施の途中で業務設定を直しても、実施中のタスクは古い版のまま進む。
- 新しい版に切り替えるには、「この実施回を版 N に切り替える」という操作を、記録つきで行う。**【変更 2026-10-13】実施回に「いまの版」の欄を持たず、版の割り当ての記録（追記だけ。誰が・いつ・なぜ）の最新を、いまの版とする**（記録の書き忘れが起きない）。割り当てる版は、その実施回の業務の版に限る（組の参照）。
- 試行は、実際に使った版を必ず記録する（A/Bテストと誤判定の調査が、版ごとに正しく割れるようにするため）。**試行を作るとき、その版が「その時点の実施回の版」と同じであることを、データベースが確かめる。**

### 3-3. 「取込単位」と「再実施」の区別（Intent.md では区別が無かった）
- 同じ相手に、来月もう一度同じ業務をする場合は、**新しい実施回**を作る。
- 実施回をまたいだ「前回いつかけたか」は、門が連絡先の履歴で見る（5-2）。

### 3-4. 発信対象の取込の決まり【追加 2026-10-13 CL-2・2026-10-14 作った形に合わせて直した】
5-1 の「全部か何も無いか」と、Intent.md 7-2 の「問題のある行は、エラー理由と行番号を見せ、自動発信には回さない」が、どちらの意味にも読めた。次の1つに決める。コードは `app/src/salescall/core/importer.py`（行の合否）・`import_files.py`（ファイルを読む）。
1. 読み込んだ行をすべて検証し、行ごとに「登録する」「止める（理由）」「もう登録済み」「空の行」を出す（プレビュー）。**行の合否を決めるのは1つの処理だけで、プレビューと登録の両方がそれを呼ぶ。**
2. 人が依頼主名を確かめて登録を押すと、**合格の行だけを、1つの取引で全部登録する**（1行でも保存に失敗したら、何も登録しない）。止めた行は、理由と行番号を記録に残す（値は残さない）。
   - **【2026-10-14】登録されるのは、人が見たプレビューとまったく同じもの**：プレビューは行ごとの結果の指紋を返す。登録は、登録の取引の中で合否をもう一度出し、指紋が同じときだけ書く。プレビューのあとで発信禁止・設定・ほかの取込が変わっていたら、何も書かずに「もう一度プレビューを」と返す。
3. 止める行（上から順に、最初に当たった理由）：列の数が見出しと合わない（CSV）／対応付けた欄の問題（エラーの値・結果の無い式・15桁を超える数）／番号が無い／管理番号の列を選んだのに管理番号が無い・指数の書き方で桁が失われている／番号で決まる「かけない理由」（下の6）／**同じファイルの上の行と同じ番号**（まとめると、片方の行の管理番号に結果が出ないため。CL-3 のお願い）／上の行と同じ管理番号／その実施回に同じ番号のタスクがあり、管理番号が違う／その実施回に、同じ管理番号で別の番号のタスクがある。
   - その実施回に同じ番号・同じ管理番号のタスクがあれば「もう登録済み」（同じファイルを取り込み直しても、新しいタスクは増えない）。
   - 「上の行」は、合格か登録済みになった行だけ（止めた行は番号・管理番号を取らない＝止めた行のせいで、ほかの行を止めない）。
   - **1つの実施回で、同じ管理番号は1つのタスクだけ**（データベースの約束でも守る。依頼主が結果を自分の表と突き合わせる鍵が重ならない）。
4. **表計算ソフトで先頭の 0 が消えた番号**（数として保存され「0312345678」が「312345678」になる）：1つの値だけを見て 0 を足さない（打ち間違いと見分けられない）。
   - xlsx：**その欄が数の型なら**、0 を足す（数は先頭の 0 を持てないので、確かな証拠。欄ごとに決める＝同じ列に文字と数が混ざっていても正しい）。文字の欄は証拠にしない。
   - CSV（すべて文字）：**列の番号が1つ残らず**「0 で始まらず、0 を足すと日本の番号の決まりにぴったり合う」ときだけ、その列に 0 を足す。混ざっていれば足さない（その行は「不明」で止まり、理由を出す）。
   - 0 を足した行は、プレビューと記録に印を出す。番号の書き方のゆれの扱いは、すべて番号の正規化の1か所（`core/phone.py`）。
5. タスクは、依頼主のファイルの**管理番号と、取込のときの表記（名前・番号）・行番号**と、どの取込で作ったかを持つ（依頼主が結果を自分の表と突き合わせる鍵。CL-3 のお願い）。連絡先は番号だけを持つ（実施回ごとに表記や管理番号が違いうるため）。登録したタスクには、最初の予定「いまから、かけてよい」（データベースの時刻）を次の動きの記録に入れる（実際にいつかけるかは門。予定が無いタスクを残さない）。**タスクを作るのは取込だけ**（機械の見張り I-12）。
6. **番号で決まる「かけない理由」は1か所**（`core/number_policy.py`。取込と門の両方が呼ぶ。取込と門で別々に判断すると、取込では通ったのに門で止まる・その逆が起きる）：番号が不明／システムが決してかけない種類（特番・有料の情報番号・機械どうし・海外）／**業務の設定でかけない種類**（フリーダイヤル `calling.allow_toll_free`・ナビダイヤル `calling.allow_navi_dial`。依頼主ごとに上書きできる。⏳ 初めの値はユーザーの決定待ち＝15-2-1 の3）／発信禁止（依頼主の台帳・システム共通）。
7. **ファイルの読み方**（推測で読まない。読めないものは理由をつけて断る）：
   - 1行目が見出し。行番号は表計算ソフトで見える行番号。末尾の空の行は読まない。対応付けは見出しの名前で選ぶ（同じ見出しが2つある列は選べない）。
   - CSV の文字の決まり：BOM があれば UTF-8。無ければ UTF-8 と Shift_JIS の両方で厳密に読み、片方だけ読めればそれ。**両方で読めて中身が違うときは推測しない**：両方の読み方の先頭の数行を見せ、人が選ぶ（測った結果：日本語が2文字だけの UTF-8 は約5割が Shift_JIS としても読め、Shift_JIS の2文字は約2%が UTF-8 としても読める。「UTF-8 を先に試す」では、短いファイルで社名が化け、会話で化けた社名を読み上げうる）。
   - CSV で列の数が見出しと合わない行は止める（値の中の「,」が囲まれていないと列がずれ、別の列の番号――FAX・担当者の携帯など――を電話番号として読む恐れ）。
   - xlsx：シートが2つ以上なら、どのシートかを選ぶ（黙って1枚目を読まない）。エラーの値（#N/A など）は「#」で始まる番号として読まない。結果が保存されていない式は空として読まない。
8. 発信禁止の台帳（Q3。`core/dnc.py`）：登録は番号の正規化を通した番号だけ（そろえられない番号は登録できない）。同じ番号の有効な登録は1つ（何度登録しても同じ）。**登録した取引の中で、その番号のまだ発信していない予約を取り消す**（システム共通の登録は、全依頼主の予約を取り消す）。取り消しは人だけ・理由つき・1回だけ（データベースが守る）。⏳ 同じ会社の別の番号に、発信禁止をどこまで広げるかは、ユーザーの決定待ち（15-2-1 の2）。

### 3-5. 相手が言った別の番号へかけ直す【追加 2026-10-14。ユーザー決定：基本はかける】
- 相手が「こちらの番号にかけ直して」と別の番号を言ったとき、**その番号へかけ直す**（業務設定で「かけない」も選べる。設定 `callback.call_alternate_number`、初めの値は「かける」）。
- **依頼主の一覧の1行（タスク）は1つのまま**、その行に「別の番号」を足す（タスクの番号：もとの番号＋相手が言った番号）。結果は同じ1行に返る（依頼主が自分の表と突き合わせられる）。

- ⏳ データの形（タスクの番号の表）は、会話の処理が書き込む入口を作るときに足す。

### 4-1. タスク（業務の状態）

```
                  do_not_call / out_of_scope / needs_human（2026-10-13 から使わない：人は仲介しない） / unknown

```
- **書くのは、`judge_task`（業務の状態）と `next_action`（次の予定）だけ。**
- `do_not_call` は、どの業務設定よりも優先する（Intent.md 原則14）。
- **【変更 2026-10-13 CL-2】業務の状態の正本は「結果の版」の最新**（版が1つも無ければ `open`）。タスクの行に状態の欄を持たない（3-0 の2）。結果の版は次のときに足す（CL-3 のお願い）：
  1. 試行のあと、通話後の検証（6-12）が済み、`judge_task` が判定したとき（1回の試行につき1つ）。
  2. 検証モードで、人が結果を直したとき（システムの版は残し、人の版を足す。10章）。
  3. 判定の処理の版が変わって判定し直すとき（記録つきの操作でだけ。自動ではしない）。
- **次の予定の正本は「次の動きの記録」の最新**（「かけ直す（日時）」か「終える（理由）」）。書くのは `next_action` だけ。タスクを取り込んだときの最初の予定も `next_action` が書く。
- 終える理由の例：業務が終わった（completed など）・回数の上限・発信禁止（門で分かった）・人の対応が要る。⇒ 依頼主への「通話の終わり方」で、一度もかけずに終えたタスクを「まだかけていない」と区別できる（CL-3 の 7-3-3 へ伝える）。

### 4-2. 試行（通話の状態）
```
claimed（門が予約した）─▶ dialing ─▶ ringing ─▶ answered ─▶ in_conversation ─▶ ending ─▶ ended
   │          │           │              │
   └─ call_failed / no_answer / busy / dropped（途中切断）/ technical_error
claimed ─(期限切れ・門の前提が変わった)─▶ released
```
- **検証モードの承認は、門の"前"に置く**（タスクに対する承認）。承認されたタスクだけが門へ進み、門の予約の直後に発信する。
  - 理由：門の予約のあとに人の承認を待つと、待っている間に時間帯・停止・発信禁止が変わっても、古い判定のまま発信してしまう。門の判定と発信の間には、人の待ちを挟まない。
- **`claimed` から `dialing` へ進めるのは、電話接続モジュールの1か所だけ。** 予約証が「期限内で、まだ使っていない」ことを確かめ、使用済みに書き換えるのを1つの操作で行う（5-3）。
- **途中で処理が落ちた試行**（`dialing` 〜 `ending` のまま残ったもの）は、`technical_error`（結果不明）にする。
  - ⛔**すぐにかけ直さない。** 実際には話していた可能性があるので、すぐかけ直すと「二重発信」と同じ害になる。最小の間隔を `next_action` が守る。
- **【追加 2026-10-13 CL-2】移ってよい組は、データベースが持つ表1つだけ**（下）。それ以外の移り方は、データベースが拒む。移るたびに、履歴（いつ・どこから・どこへ）をデータベースが自動で残す。
  | いまの状態 | 移ってよい先 | 移す処理 |
  |---|---|---|
  | （無し） | `claimed` | 門（5-2）だけ |
  | `claimed` | `dialing` | 発信の出口（5-3）だけ |
  | `claimed` | `released` | 門（期限切れの予約を戻す）と、門の前提を変える操作（5-2 の作りの決まり (2)） |
  | `dialing` | `ringing`・`answered`・`busy`・`no_answer`・`call_failed`・`technical_error` | 回線の部品（`technical_error` は復旧も） |
  | `ringing` | `answered`・`busy`・`no_answer`・`call_failed`・`technical_error` | 同上 |
  | `answered` | `in_conversation`・`ending`・`dropped`・`technical_error` | 同上 |
  | `in_conversation` | `ending`・`dropped`・`technical_error` | 同上 |
  | `ending` | `ended`・`dropped`・`technical_error` | 同上 |
  - 終わりの状態（`ended`・`released`・`call_failed`・`no_answer`・`busy`・`dropped`・`technical_error`）からは、どこへも移らない。
- **【追加 2026-10-13】進行中＝`claimed`・`dialing`・`ringing`・`answered`・`in_conversation`・`ending`。** 3-1 の部分一意は、この集まりに張る。
- **【追加 2026-10-13】予約証の期限は、データベースの時刻で決める**（PCごとの時計のずれに左右されない）。期限が切れた予約は、門が次の取引の最初に `released` に戻す（その連絡先・番号・回線の分）。戻す処理が無いと、期限切れの予約が部分一意をふさぎ続け、その相手に二度とかけられなくなる。
- **【追加 2026-10-13】落ちた試行の見つけ方（復旧）**：回線は、見守り役が「借用」する（期限つき。動いている間、一定の間隔で延ばす）。借用の期限が切れた回線（PCが落ちた・ネットが切れた）と、起動した見守り役の自分の回線の、進行中の試行を `technical_error` にする。⇒ クラウドのデータベースに複数のPCがつながっても、ほかのPCの通話を誤って終わらせない。PCが戻らなくても、試行が進行中のまま残り続けない。

    - 「目的の人ではない人」が用件を聞いてきたら、用件の一文を言ってから、もう一度だけ呼ぶ一言を言う。
    - 不在のときは、**必ず「いつ戻られるか」を聞く**（ユーザーの指示。CL-2 から）。戻る時刻は、システムが足す日時の質問で取る（言い直して確かめる）。取れたら `callback_scheduled`、取れなければ `not_reached`（不在。かけ直すかは業務の再発信の方針。CL-2 の 7-1・7-2）。
  - **相手ごとの人**は、相手ごとに名前が違うので、**業務ごとに1回作って人が聞いて承認する録音（6-13）には入れられない**。⇒ 名乗りは録音で流し、目的の人を呼ぶ一言は (a) AIが言う、または (b) その相手の分を発信の前に同じ声で作り、別の耳で確かめて流す。⚠️ (a) はAIの最初の発話なので、名乗りの崩れ（約5%）と同じことが名前に起きうる（「岡田」が別の名前に聞こえる）。(b) は件数が多く、人の承認ができない。⏳ どちらも、名前の崩れを測ってから決める。
  - 相手ごとの人のデータ（役職・名前・読み）は、発信対象データの列（Intent.md 7-1・6-8 の3。CL-2）。読みの列が無いときの扱いは Intent.md 6-8 のとおりフェーズ1で決める（名前を間違えて呼ぶのは、相手に一番失礼な誤り）。
  - 場面：同じ名字の人が複数いる（「どちらの岡田でしょうか」）⇒ 役職・部署で答える。「岡田は私ですが」⇒ 目的の人。
  - 宣言の無い業務は取込で止める（既定値で埋めない。原則10）。
  - `target`（上の種別）は「**目的の人**」を指す。流れの制御は、相手の種別が `target` になるまで、最初の質問を渡さない（「誰でも」の業務は、最初の相手が `target`）。目的の人かは、AIが相手の言葉（「私が社長です」「店長の〇〇です」）から申告する（`report_party`）。根拠の発話を区間に残す。
  - 繋がるまでの場面と扱い（Intent.md 9-4）：
    - 本人が出た ⇒ そのまま質問へ。
    - 受付・別の人 ⇒ 決まった言い方で取り次ぎを頼む ⇒ 保留は黙って待つ（上限あり。6-8）⇒ 相手が替わったら新しい区間にし、**短く名乗り直す**（社名・名前・用件）⇒ 質問へ。
    - 不在 ⇒ 戻る時刻を聞く（システムが足す日時の質問。折り返しの日時と同じ取り方。15-2-3 への意見）⇒ 折り返し（`callback_scheduled`）。伝言を断って終えるかは業務設定（Intent.md 9-4）。
    - 「どういったご用件でしょうか」 ⇒ 用件の一文を言う（決まった文）。
    - 断られた ⇒ 断りの扱い（6-2 の「断りは3つに分ける」）。
  - **質問の途中の「担当ではない」は、目的の人の決め方が正しければ、まれになる**（目的の人に聞いているため）。それでも起きたら、15-2-3 の宣言どおりに扱う。
  - ⚠️ 録音の名乗り（6-13）の終わりは、「誰でも」の業務では最初の質問、それ以外では**目的の人を呼ぶ一言**になる。G-22（録音の途中で話し始めた・聞き返した）は最初の質問の形で測っている。⏳ 目的の人を呼ぶ形でも測る。

### 4-4. 項目（項目ごとの状態）
```
empty ─(はっきり聞き取れた)─▶ heard（値・根拠の発話）
empty ─(聞き取れない・曖昧)─▶ unclear ─(聞き返し：1項目1回まで)─▶ heard（聞き返して聞けた値）
                                     └(聞き返しも使い切った)─▶ unresolved（「-」。念のための確認を待つ）
  │
  ├─【確かめる型】、または【聞き返して聞けた値】
  │     heard ─(復唱して確かめる)─▶ checking
  │     checking ─(相手が肯定)─▶ confirmed
  │              ├(相手が訂正)─▶ 訂正された値をもう1回だけ復唱 ─(肯定)─▶ confirmed
  │              │                                              └(また違う)─▶ unresolved
  │              └(答えない・その前に切られた)─▶ unresolved
  │
  └─【確かめない型で、はっきり聞き取れた値】 heard ─(形式の検査に合格)─▶ accepted
unresolved ─(念のための確認：1項目1回まで。会話の最後か、切りの良いとき)─▶ heard ⇒ 復唱 ⇒ confirmed
           └(それでも聞けない・相手が急いでいる・切られた)─▶ unresolved のまま（依頼主へは「-」）
heard / empty / unresolved ─(相手が答えを拒んだ)─▶ refused（依頼主へは「✕」。二度と聞かない）
empty / unclear ─(相手が「わからない」と答えた)─▶ dont_know（「取れた」には入らない。依頼主へは「-」。答えは聞けたので、念のための確認はしない）
（どこからでも）─(時間切れ・通話終了)─▶ そのまま残る（自動で confirmed・accepted にはならない）
confirmed / accepted ─(通話後の検証で食い違い：6-12)─▶ unresolved（理由つき）
```
- **状態の名前は、この図のものだけを使う**：`empty`（まだ聞いていない）、`heard`（聞き取った）、`unclear`（聞き取れない・曖昧）、`checking`（復唱中）、`confirmed`（確認済み）、`accepted`（確かめない型で取れた）、`dont_know`（相手が「わからない」と答えた。2026-10-13 に足した）、`unresolved`（「-」）、`refused`（「✕」）。
- 聞き返し・復唱・念のための確認の決まりは、6-11 に1つにまとめた（2026-10-12 ユーザー提案）。
- **その場で確かめるかは、項目の「型」で決める**（2026-10-12 ユーザー確定：聞き間違えやすい項目だけ）。決めるのは、型の一覧の1か所だけ（2章 Q19）。
  - **確かめる型**：日付、時刻、数、金額、名前（会社名・担当者名などの固有名詞）、電話番号、メールアドレス、住所。
  - **確かめない型**：はい／いいえ、決まった選択肢、自由な意見・感想。
  - 中の名前（2026-10-13。CL-2 のデータの形と同じ11＋1）：日付 `date`・時刻 `time`・日時 `datetime`・数 `number`・金額 `amount`・名前 `name`・電話番号 `phone`・メール `email`・住所 `address`／はい・いいえ `yes_no`・決まった選択肢 `choice`・**自由な意見 `free_text`**（CL-2 の依頼で名前を決めた）。
  - 確かめる型は、言い直しに使うので、値の言い終わり（「です」「。」など）を外す。**確かめない型は、相手の言葉のまま**（自由な意見の「よかったです」を「よかった」に変えない）。
  - **【追加 2026-10-13】電話番号の型**（折り返しの番号など。CL-2 の依頼）：会話の側は、**話し言葉の数字を数字の並びに直すだけ**（漢数字を数字に・番号の区切りの「の」を外す）。そのあと必ず**番号の正規化（Q1。CL-2 の `core/phone.py` の `normalize`）**を通す。「+81」の組み立てや種類の判断を、会話の側でしない（番号を整えるのは1か所）。
    - 正規化が「不明」を返したら（桁が合わない など）、その値は受け付けずに差し戻す（6-2 の値の形式）。差し戻しの文に、正規化が返した理由（日本語）を入れる ⇒ AIは聞き返す（1回まで。6-11）。
    - 言い直しは、相手が言った区切りのまま読み上げる（区切りの無い数字の並びは、相手が確かめにくい）。記録には、正規化が返した番号（`national`・`e164`）と種類を残す。
    - かけてはいけない種類（有料の情報番号など）の番号を相手が言ったときは、聞いたとおりに記録し、かけるかは門が決める（会話の側では判断しない）。
  - 型の一覧に無い型は、業務設定の読み込みで落とす（確かめるかが決まっていない項目を残さない）。
  - 業務設定で、型の既定と違う扱いにする項目は、理由つきで宣言する。
  - **型ごとの決まりも、この一覧に持つ**（2026-10-12 の G-6 で見つかった穴から）。例＝**時刻：午前か午後かを必ずはっきりさせる。相手が言わなければ聞く。AIが補わない**（G-6 で、相手の「2時」を AI が自分で「午後2時」と記録した）。
- **確かめ方**：最後にまとめて読み上げない。**聞いたその場で、会話の流れの中で言い直す**（例：相手「15日の午後2時で」→ AI「15日の午後2時で、よろしいでしょうか。」→ 相手「はい」。言い直しの言い方は決まった言い方で、場面ごとに複数を順番に回す＝6-11。2026-10-13 ユーザー確定）。途中で切られても、確かめ済みの項目は残る。
- **この決まりは、セッションの最初の指示に入れる**（2026-10-12 ユーザー指摘）。指示文を作る処理（6-3）が、型の一覧から「どの型を、どう確かめるか」を書き出す。業務ごとに手で書かない。
- **プログラムの役目は、抜けと先回りを防ぐこと**：
  - 確かめる型の答えを受け付けたら、確かめの結果（`confirm_field`）が届くまで、次の質問を渡さない。⇒ AIが確かめを飛ばしても、そのまま次へは進めない。
  - **言い直す値は、プログラムが記録した値そのもの**を、返事に書いて渡す（G-6 で、声で言い直した値と記録した値が違った）。
  - **確かめの結果は、言い直しを求めたあとに相手の発話が届いていなければ、受け付けない**（I-24）。G-6 で、AI が相手の返事を待たずに「肯定された」と報告した。⇒ 相手の「はい」を独立の証拠にする決まり（6-4）を、AIの先回りで崩させない。相手の発話が届いたかは、相手の音声の文字起こし・発話の検出で、プログラムが数える。
- **「取れた」の定義**（判定・出力が使う唯一の定義）：
  - 確かめる型、または聞き返して聞けた値 ⇒ `confirmed`（相手の肯定と、形式の検査に合格の両方）
  - 確かめない型で、はっきり聞き取れた値 ⇒ `accepted`（形式の検査に合格）
  - **この2つの状態だけ**。「取れた」かは状態だけで決まる（条件や理由を見なくてよい）。
  - **【変更 2026-10-13 ユーザー決定（CL-2 から依頼）】相手が「わからない」と答えた項目は「取れた」に入れない**（`dont_know`）。必須の質問が「わからない」なら、業務は完了ではない（判定 7-1。扱いは 15-2-3 の案）。⛔ 前は `accepted`（条件＝わからない）＝「取れた」にしていたので、ほかの必須項目がそろうと完了になっていた。条件を見て除く形にしなかったのは、「取れた」を使う処理（判定・出力・画面・張り替えの指示文）が、みな条件も見なければならなくなるため（試作では、張り替えの指示文が条件の中の名前＝英字をそのままAIに見せていた）。
- 形式の検査の例：日付として正しいか、選択肢の中にあるか、電話番号の形か。

`pending` → `sending` → `sent` ／ `failed` → `retrying`（回数の上限まで）→ `dead`（人の対応が要る）

### 5-2. 門（`claim_dial`）が1つの取引の中で行うこと
すべてを確かめ、すべて通ったときだけ「試行（`claimed`）」の行を作り、予約証を返す。**1つでも判断できなければ、通さない。**

1. 運転の状態：全体・依頼主ともに止まっていない（Q13）。
2. 時間帯：日本時間・祝日の暦で、システムの上限と依頼主の設定の両方の内側にある（Q12）。
3. 発信禁止台帳：依頼主の台帳にもシステム共通の台帳にも、載っていない（Q3）。
4. 番号：正規化できていて、発信してよい種別である（Q1）。
5. 間隔と回数：
   - 同じ連絡先への前回の試行から、決まった間隔が空いている。
   - 1日・合計の回数が上限の内側にある。
   - 前回が「結果不明」なら、その分の長い間隔が空いている。
   - **前回の試行の通話後の検証（6-12）が終わっている。** 終わっていなければ通さない（検証で拒否の言葉が見つかるかもしれないため）。
   - **依頼主をまたいで**、同じ番号への前回の発信から、システムで決めた間隔が空いている（2026-10-12 ユーザー確定）。門が見るのは番号の台帳の「最後に発信した時刻」だけで、どの依頼主がかけたかは見ない・出さない（依頼主の分離を崩さない）。
6. 進行中の試行：同じ連絡先に進行中の試行が無く、**番号の台帳でも、その番号が進行中になっていない**（依頼主をまたいだ同時発信を防ぐ）。通れば、同じ取引の中で番号の台帳を「進行中」にし、「最後に発信した時刻」を書く（3-1）。
   - ⛔「最後に発信した時刻」を読むだけで、書くのを取引の外にすると、同時に来た2つの予約が両方とも通る。**読むのと書くのは、同じ取引の中で行う。**
7. 回線：空いている回線があり、その番号の1日の上限の内側にある（Intent.md 8-6）。回線を借りる。
8. 予算：依頼主・全体の、その日の費用の上限の内側にある（Q16）。
9. 会話AI：使えるキーと枠がある（Q15）。**【追加】枠には「1分あたりの入力トークン数（TPM）」を含める。** 🔴**【訂正 2026-10-12】入力の量は、AIが返事をするたびに「指示文＋それまでの会話の全部」が数え直される**（実測：4ターン・約30秒の短い通話で、ターンごとに 619→830→1,075→1,221 トークン、合計 3,745。1分あたりにすると約7,500）。前の見込み「相手の声だけで1分あたり約1,500トークン」は少なすぎた（相手の声そのものは1秒あたり約25トークン）。⇒ 1本の見込みは「ターンごとの入力の量の合計」で数え、通話が長いほど1分あたりの量が増えることを入れる。⏳ Google が TPM に何を数えるかは公式の資料で確かめる（フェーズ0 G-10）。⇒ 門は、プロジェクトごとに「いま進行中の通話の見込みの使用量」を数え、この発信を足すと上限を超えるなら通さない。同時に何本かけられるかは、ここで決まる（2026-10-12：利用拒否の理由は、管理画面で TPM の上限と確かめられた）。**【追加 2026-10-13】上限の値は、管理画面の値を設定の値として持つ**（ユーザーが確かめた値：会話の gemini-3.8-live は TPM 65,000。無料枠の値と見られる）。実測の量（短い通話で1分あたり約7,500）では、1つのプロジェクトで同時に8本ほど。**別の耳（gemini-3.5-transcribe-live。6-12）も TPM 20,000 の上限があるので、門は、通話後の検証の順番待ちの量も数える**（検証が追いつかない量の発信をしない）。

- 返すもの：「許可（予約証）」か「不許可（理由）」の2つだけ。不許可の理由はダッシュボードに出す（Intent.md 5-2「門で止めた件数」）。
- 予約証には期限がある。期限内に発信しなければ `released` に戻し、回線を返す。

#### 5-2-1. 門の作りの決まり【追加 2026-10-13 CL-2。見直しで見つけた穴をふさぐ。15-2】
1. **時計は、データベースの時刻1つだけ。** 時間帯・予約証の期限・間隔は、取引の中のデータベースの時刻で決める（日本時間・祝日への直しも1か所）。PCの時計は使わない。
2. **取引は、直列化の水準（ほかの取引と1つずつ順に行ったのと同じ結果になる水準）で行う。** 門だけでなく、**門の判定に効く変更**（停止・発信禁止の登録・時間帯や回数の設定の変更）も、同じ水準の取引で行い、**同じ取引の中で、まだ発信していない予約（`claimed`）を `released` に戻す**。発信の出口は「`claimed` かつ期限内」でなければ `dialing` に進めないので、⇒ **停止を押したあとに、押す前の予約で発信することは無い**（予約と停止がぶつかったら、データベースがどちらかの取引を止めて、最初からやり直させる）。取引を始める・ぶつかったらやり直す、は読み書きの層の1か所で行う（11章）。
3. **取引の最初に、期限切れの予約を戻す**（その連絡先・番号・回線の分。4-2）。
4. **時間帯は「予約証の期限の終わり」まで内側にあること。** 時間帯の終わりの直前に予約して、終わったあとに発信することを防ぐ。
5. **祝日の暦は、持っている範囲を持つ。** 範囲の外の日は「判断できない」⇒ 通さない（暦の入れ忘れで、祝日にかけない）。
6. **進行中の判定は、試行の部分一意の制約だけで行う**（3-1）。先に番号の台帳のその番号の行を固定し（同じ番号の予約を、依頼主をまたいで順番にする）、試行の行を足す。制約にぶつかったら、その部分だけ取り消して「不許可（理由）」を返す。
7. **「最後に予約した時刻」は予約のときに書く。** 予約が使われずに戻っても、書き戻さない（ほかの依頼主の次の予約が少し遅れるだけで、害の無い向き）。
8. **回数と間隔の数え方は、門の1か所だけ**（「その連絡先に次にかけてよい最も早い時刻と、残りの回数」を返す処理）。次の動き（7-2）と画面は、これを読む。数えるのは**発信まで進んだ試行だけ**（予約だけで戻ったものは数えない）。依頼主へ渡す「かけた回数」も同じ数え方。
9. **前回の試行の通話後の検証**は「済み」「不要」のときだけ通す（4-2）。**【変更 2026-10-13 ユーザー決定：人は仲介しない】** 検証は、決まった回数まで自動でやり直す（Q21。CL-1）。それでも「確かめられなかった」なら、その行は自動で処理済みにする（拒否を聞き逃したかもしれないので、かけない側に倒す。7-2）。人を待たない。
10. **会話AIの枠（5-2 の9）**：どのプロジェクトの枠で話すかを、予約のときに決めて試行に記録する（キーの選択 Q15 は CL-1 の持ち場。門は、選ばれたプロジェクトの見込みの使用量を数える）。⏳ CL-1 と形を決める。
11. **不許可の理由は、決まった名前の一覧で返す**（画面で理由ごとに数えるため。CL-3 のお願い）：止まっている／時間帯の外／暦の範囲の外／発信禁止（依頼主）／発信禁止（システム）／番号が不明／発信してはいけない種別／同じ連絡先の間隔／回数の上限／前回の検証が済んでいない／同じ連絡先が進行中／**ほかの依頼主の間隔（同じ契約者）**／**ほかの依頼主の間隔（契約者の外）**／**同じ番号が進行中（同じ契約者のほかの依頼主）**／**同じ番号が進行中（契約者の外）**／回線が無い／番号ごとの1日の上限／予算／会話AIの枠／版が無い／判断できない。
    - 「同じ契約者」と「契約者の外」を分ける（CL-3 のお願い）：契約者の外の理由は、どの画面にも中身を出さない（ほかの契約者が同じ番号へかけていることが分かってしまうため）。⇒ 番号の台帳に「最後に予約した契約者」を持つ（依頼主は持たない。台帳は門だけが読む）。進行中の相手が同じ契約者かは、門だけが使う確かめの処理が「同じか、違うか」だけを返す（ほかの契約者の行の中身は返さない）。
    - ⏳ 依頼主をまたいだ間隔を、**契約者をまたいでも**効かせるかは未決（`docs/TECH_CHOICE_CL-2.md` 7-4 の1）。決まるまでは、いまの設計どおり**またいで効かせる**（害の無い向き）。進行中の制限（同じ番号に同時に2本かけない）は、契約者をまたいでも必ず効かせる。
12. **不許可は、次の動き（7-2）へ渡す。** 次にいつ候補に出すかを決めるのは次の動きだけ（スケジューラーや門が予定を書かない。Q4）。

### 5-3. 発信の出口は1か所
- 実際に電話をかける操作（各回線モジュールの `start_call`）は、**予約証を受け取る共通の入口1か所からしか呼べない**形にする。
- その入口で、予約証が `claimed` のままで期限内であることを確かめ、`dialing` に書き換える。これを1つの操作（他と割り込めない書き換え）で行う。
- ⛔各回線モジュールを、直接呼べる道を作らない（静的検査で見張る。14章 I-1）。

## 6. 会話の設計

### 6-1. 役割分担
| 担当 | 受け持つこと | 受け持たないこと |
|---|---|---|
| **流れの制御**（プログラム） | いまの質問、取れた項目と残りの必須項目、時間と発話の予算、終了の判断、聞き返し・確かめの回数、確かめが済むまで次の質問を渡さないこと | 言い回し、確かめ方（どちらもセッションの最初の指示で AI が知っている） |
| **会話AI** | 指示された質問を自然に話す、相手の答えを、その質問に宣言された条件のどれかに分類する、範囲内の雑談と聞き返し | 次の質問を決める、終了を決める、完了を決める |

### 6-2. AIが呼べる操作（これだけ）
| 操作 | 中身 | 制御が確かめること |
|---|---|---|
| `record_answer(質問ID, 条件ID, 値, 発話の位置)` | 答えを、宣言された条件に分類して報告する | 質問IDが、いまの質問と一致するか（違えば差し戻し）。値の形式（値の要る型で値が無ければ差し戻す。選択肢の型と「わからない」「答えたくない」は値が無くてよい）。⇒ 合格なら、次の質問を返す（確かめる型なら、復唱の結果が届くまで返さない） |
| `report_unclear(項目ID, 発話の位置)` | 聞き取れない・曖昧だった | 聞き返しの回数を見て、「聞き返す」か「「-」にして次へ」かを返す（6-11） |

### 6-3. 指示文は1か所で作る
- 業務設定の版から、会話AIへの指示文を作る処理は1つだけにする。版と結びつけて保存する。
- **会話の決まりは、すべてこの指示文に入れる**（セッションの最初に渡すもの。6-6）。材料は次の3つで、どれも1か所から読む。
  1. 業務設定の版：目的、トークスクリプト、質問と選択肢、言ってはいけないこと、名乗り、終了の条件、**相手が「忙しい」と言ったときの一言**（空なら丁寧に終える＝既定。文があれば1回だけそれで聞く。Intent.md 9-4。2026-10-13 ユーザー）
  2. 項目の型の一覧（Q19）：どの型をその場で確かめるか、どう確かめるか
  3. システム共通の会話の決まり：曖昧な答えの聞き直し方（6-10 の (3)）、相づちの扱い、断られたとき・「AIですか」と聞かれたときのふるまい
  4. **【追加】話し方の指示（声の調子と速さ）**：タスクに記録された「声の型」（Q11）から読む。声の型は、声の名前と話し方の指示の組で、版を持つ。⇒ 同じ声でも話し方の指示だけ違う型どうしで A/B ができる（2026-10-12 ユーザー：Sadachbia の S2 と S4 で比べたい）。
- **相手のデータ**（会社名・備考など、依頼主のファイル由来のもの）は、指示文の中に「データ」として区切って入れる。指示としては入れない。
- **相手の発話**は、指示文に入れない。
- **【追加 2026-10-13】名前は「」でくくって入れる。くくるのは、この処理だけ**（Intent.md 6-8）。名前（自社名・担当者名・商品名など、取込で印を付けたもの。相手の会社名・相手の名前も）は「表記」と「読み」を持つ項目として受け取り、この処理が「」でくくる。ほかの処理は「」を足さない。読みの伝え方は、フェーズ1で試してから決める。
- ⇒ Intent.md 原則13 の言い方を、ここに合わせて直した：
  - 運営者が作り、検証し、承認した業務設定＝指示（信頼する）
  - 依頼主のファイルの中身・相手の発話・外部システムのデータ＝材料（指示として扱わない）

### 6-4. 聞き間違えやすい項目を、その場で確かめる理由
- Intent.md 9-5 は「通話中に記録した値」と「通話後の文字起こしからの抽出」の**二者一致**を、完了の証拠にしていた。
- **しかし、この2つは独立していない。** どちらも、同じ会話AIが同じ音声を聞いた結果である。聞き違えていれば、2つとも同じように聞き違える。**一致は、正しさの証拠にならない。**
- **独立した証拠は、相手本人の確認だけである。** そこで、聞き間違えやすい型の項目は、聞いたその場で言い直して確かめ、相手の肯定をもって `confirmed` にする（4-4）。
- **確かめ方の決まりは、セッションの最初の指示に入れる**（4-4）。プログラムは、確かめの結果が届くまで次の質問を渡さないことで、抜けを防ぐ。
- 通話後の文字起こしと別の音声認識は、**食い違いを見つける側**にだけ使う（6-12）。一致しても、`confirmed`・`accepted` には上げない。

### 6-5. 終了
- 終了を決めるのは制御である。AIは求めることしかできない。
- 締めに入る前に、「-」の項目の念のための確認を1回だけ行う（6-11）。相手が切った・断った・急いでいるときは、しない。
- **【追加 2026-10-13 ユーザー】相手が「忙しい」と言ったとき**：業務設定の「忙しいと言われたときの一言」が空なら、丁寧に終える（既定）。文があれば、流れの制御がその一言を**1回だけ**AIに言わせ、相手が応じれば続け、2回目の「急いでいる」で終える。通話そのものを断られたときは、設定にかかわらず終える（Intent.md 原則14）。
- 終わってよいとき：
  - 必須項目がすべて「取れた」（4-4 の定義）
  - 拒否・範囲外・留守電など、終了してよい理由がある
  - 時間や発話の予算が尽きた
  - 一定時間、相手が黙っている
- 締めの言葉も、業務設定から作る。

### 6-6. 「言ってはいけないこと」を防ぐ：すべてのセッションの最初に、必ず指示を渡す
- **方式は Gemini Live（音声のまま考え、音声のまま話す）に決めた。** 口に出す前にリアルタイムで中身を確かめて止める方式は、作らない（2026-10-12 ユーザー確定）。
- **防ぎ方**：目的・業務設定・トークスクリプト・**言ってはいけないこと**を、指示文（6-3 で作る、版つきのもの）として、セッションの最初に渡す。
- **セッションは、1回の通話（試行）ごとに新しく開き、使い回さない。**
  - 別の依頼主の架電に入るときは、必ず立ち上げ直す（2026-10-12 ユーザー指摘）。
  - さらに、**同じ依頼主・同じ業務でも、相手が替われば立ち上げ直す。** 前の相手の会話がセッションに残っていると、その内容（相手の名前・答え）が次の相手との会話に混ざるおそれがあるためである（依頼主の分離、Intent.md 原則4 と同じ理由）。
  - 通話が終わったら、そのセッションは閉じる。
- **セッションが替わると、AIは前の指示を忘れる。** そこで、セッションを始める処理を1つにし（2章 Q18 の `start_session`）、次の**すべての**場面で、その処理を通す。
  1. 通話の最初（＝別の依頼主・別の業務・別の相手に替わるとき）
  2. セッションの上限による張り替え（6-9）
  3. 通信の切断からのつなぎ直し
  4. APIキーの切り替え（9章）
- **張り替え・つなぎ直しのときに渡すもの**：指示文に加えて、流れの制御が持っている「いまの質問・取れた項目・確かめ済みの項目・相手の種別」。
  - 会話の位置をプログラムが持っている（6-1）ので、AIが前のセッションを忘れていても、続きから正しく話せる。
  - ⇒ **「AIの記憶に頼らない」作り（芯の3）が、ここで効く。**
- **見つけ方（通話後）**：6-12 の (d)。
- **機械での見張り**：会話AIのセッションを開く場所が `start_session` の1か所だけで、指示文を渡さずには開けないことを、静的検査と試験で確かめる（14章 I-15）。
- **考える量**も、`start_session` が設定の値から渡す（2026-10-12 の G-11）。⛔「考えるレベル」は gemini-3.8-live では受け付けられない。使えるのは「考える量の予算」。予算0（考えない）は速く（真ん中の値 0.81秒・最大 1.16秒）、既定（自動）は 0.99秒・最大 2.07秒。決まりを守れるかは、既定が10回中10回、予算0が10回中9回（1回は原因不明）。⇒ どちらにするかは、通話の記録の文字起こし（6-12）で測り直してから決める。

### 6-7. 通話中に、会話AIのセッションが切れたとき（この決まり1つだけ）
- **つなぎ直しは、1回だけ、決まった秒数以内に試す。** `start_session` を通し（6-6）、指示文といまの位置を渡し直す。使うキーは、キーの選択（12-2）が決める（切れた原因がキー固有なら、別のキー）。
  - つなぎ直している間、相手を無言にしない。待ってもらう短い音声（「少々お待ちください」）を、電話接続モジュールが直接流す。
- **つながらなければ、終える。** 声ごとに、あらかじめ作っておいた**おわびの音声**を、電話接続モジュールが直接流して終える。どちらの音声も会話AIに頼らない。
  - 試行は `technical_error` にし、次の動きは最小の間隔を空ける（4-2）。
- 秒数とつなぎ直しの回数は、システム共通の設定の値で持つ（8章の「厳しいほう（上限）」）。
- **【追加】AIが黙ったとき（セッションはつながっているのに、相手が話し終えてから決まった秒数、AIが話さない）も、この決まりの中で扱う**（2026-10-12 の G-11：48回中1回、AIが30秒黙った）。
  - 「話した」かは、**実際に届いた声の長さ**で判断する（文字起こしや、区切りの合図では判断しない）。G-3 で、文字起こしには全文があるのに声が 0.77秒・0.82秒しか届かない回があった（相手には途中から無言に聞こえる）。
  - **話し終わりの合図が来たのに、届いた声が、そのターンの文字起こしの長さに比べて短すぎる**ときも、「AIが黙った」と同じ扱いにする。2回とも、Google が返した出力の音声の量は約1秒ぶん（25〜26 トークン）だけで、Google の側で声が作られていなかった。どこからを「短すぎる」とするか（1秒あたりの文字数の上限）は、ふつうの発話の速さ（G-3 の会話の形で 1秒に 6.7〜8.2文字）から、設定の値として決める。
  - 【追加 2026-10-12 の G-17】**声が約1秒で止まる現象は、短い一言でも起き、終わりが切れる**（「失礼いたし」「ありがとうございま」で止まった。204ターン中4回）。どれも、出力の音声が 25〜26トークン（約1秒）で止まっていた。⇒ 「1秒あたりの文字数の上限」だけでは見つけられない（切れた一言は1秒に9〜10文字にしか見えない）。見分け方は、(a) 出力の音声の量が約1秒ぶんで止まり、かつ (b) その声の、ふつうの話す速さ（声の型ごとに実測して設定の値で持つ）で言い切るのに要る長さより短い、の2つで判断する。どこで線を引くかは、フェーズ1の通話の記録で、見逃しと誤りの数を数えてから決める。
  - 【追加】**反対に、声が長すぎるとき**（同じ文を2回言った。G-17 で1回。AI自身の文字起こしには1回しか無かった）も、通話後の検証（6-12）で拾う。会話中には止めない（言ってしまった後なので、止めても相手には届いている）。
  - 【追加 2026-10-13 G-16 の3回目】**AIが、日本語の文のあとに、英語の説明を声に出した**（「念のため確認させてください。15日の午後2時でお間違いございませんか。」のあとに「Confirming the date and time, 15th at 2:00 p.m.」。AI自身の文字では「*Confirming the date and time "15th at 2 PM".*」と、星印で囲まれていた＝自分の動きの説明を、そのまま声にした）。
    - 起きた割合：会話の形で 606ターン中1回、台本を1文ずつ読ませる形で 240ターン中1回（G-17 の「To read this script, I'll project ...」）。⇒ **少なすぎて、指示文に決まりを足して減ったかを数で確かめることはできない**（何千回も要る）。⇒ 起きる割合に頼らず、**起きたら止める**形にする。
    - 見分け方：AIの1ターンの見分け方（`turn_check` の `wrong_language`：ローマ字の単語が4つ以上続く）。会話の中では、AI自身の文字が届くたびに同じ見分け方を当てる。
    - 【案・測ってから決める】英語を見つけたら、**電話接続モジュールが、その時点で相手への声を止める**。止めた所より前の日本語の文が言い切れていれば、それ以上は何もしない（相手は日本語の文にだけ答える）。言い切れていなければ、言い直しの合図（G-18 で18本中18本働いた）を使う。どちらの場合も、通話後の検証（6-12）に回す。
    - **止められるかは、AIの文字が、声より先に届くかで決まる**（声は話す速さで届き、届いたそばから相手に流れる）。⇒ 測った（G-16 の4回目、文字のかたまり 359）：**先に届いたのは29%、先行の中央は 0.00秒**。⇒ ⛔ **英語を文字で見つけてから止めても、相手にはもう聞こえている＝止める案は、防ぐ手段にならない**（言いかけを短くするだけ）。声を遅らせて流せば先に見つけられるが、返事が毎回その分だけ遅れる（ふつうの返事の速さは中央 0.88秒。G-11）。⇒ 防ぐ手段は、まだ無い。⏳ ユーザーと決める。
    - ⚠️ **AI自身の文字は、声と違う文字で書かれることがある**（G-5：声は「ご契約の確定については、私からはお答えできません」＝日本語なのに、AI自身の文字は「ご 계약의 확정에 대해서는私からは…」と韓国語だった。会話の形で 606ターン中1回）。⇒ AI自身の文字だけで止めると、正しい日本語の発話を止めうる。誤って止めたときの害（言いかけで止まり「失礼いたしました」と言い直す）と、止めないときの害（相手に英語が聞こえる）を、起きる割合（どちらも約600回に1回）と合わせて比べて決める。
    - 通話後の検証と、試験の判定では、**何語を話したかは、別の耳の文字（口から出た声）で決める**（`turn_check.classify` の `heard_text`）。日本語の文字・ローマ字以外の文字（ハングルなど）も、日本語以外として見分ける。
  1. ~~まず1回だけ、プログラムからAIへ「相手の発言に返事をしてください」と送る（文字で送る指示。相手には聞こえない）。~~ ⛔**【2026-10-13 取り下げ】** G-19 で試すと、AIが「合図」と「もとの相手の発言」の両方に返事をして、会話が1つずれた（6本中5本）。AIが本当に止まったときも約30秒で返事が来るので、合図のあとに2回話すことになる。
  1. 【案・ユーザーの承認待ち】**AIへは合図を送らない。** 声が出ないまま決まった秒数（案：4秒）たったら、電話接続モジュールが「少々お待ちください」の録音（6-13 の定型の音声）を流す。
  2. さらに決まった秒数（案：10秒）たっても声が出なければ、**セッションを張り替える**（`start_session` を通し、指示文といまの位置を渡し、**相手の最後の発言の録音を、新しいセッションへ送り直す**）。止まっていた古いセッションは閉じるので、遅れて来る返事は相手に届かない。張り替えにも失敗したら、上の決まりどおり、おわびの音声で終える。
  - 待つ秒数は設定の値。相手を無言で待たせないよう、短く決める（フェーズ1で、ふつうの返事の遅さ＝0.8〜2秒の分布から決める）。

### 6-8. 取次ぎ・保留
- 相手が替わったら、新しい区間にする（4-3）。
- **【案 2026-10-13】目的の人に繋がるまでの流れは 4-3 の「目的の人」**（取り次ぎを頼む言い方・名乗り直し・不在のときの戻る時刻は、決まった言い方にする。6-11 と同じ考え方）。

### 6-9. セッションの上限
- 制御が、経過時間を持つ。上限の少し前に締めに入る。

### 6-10. 聞き取りの精度を上げる仕組み（2026-10-12 ユーザー指示）
> 背景：ChatGPT での実験では、聞き取りの精度が悪かった（ユーザーの実測）。とくに、その場で確かめない「はい／いいえ」・選択肢の答えは、聞き違えるとそのまま結果に入る。

**原因を5つに分け、それぞれ1か所で手当てする。** 業務ごと・会社ごとの手当ては作らない。

| No. | 原因 | 仕組み | 置き場所（1か所） |
|---|---|---|---|
| (1) | **音が悪い**（電話の音は細い・雑音・音量の上下・エコー） | 音の変換を正しく行う（サンプリングレートの変換、音割れ防止、音量をそろえる、雑音とエコーを除く）。フェーズ1で、変換の前後の音を録って比べる | 音声の変換（8-3。電話接続と会話AIの間の1か所） |
| (1b) | **【追加】AIの話す速さが遅い**（2026-10-12 ユーザーの評価：留守番電話のよう。目標は実際の速さで 1.15〜1.2倍くらい） | **速さと声の調子は、話し方の指示（6-3 の材料4＝声の型）で決める。** ⛔声の調子に「明るく」「はきはき」は使わない（ユーザーの評価：営業には不向きな、強引で怪しいニュアンスになる）。⛔**【2026-10-13 ユーザー確定】速さの数字（「2倍速」「1.5倍速」）は入れない**：実際の会話の形では速さが変わらず、出だしの崩れ・途中で切れる・繰り返し・返事が無い、が増えた（G-17）（2026-10-13 訂正：前に「数字の無い指示 42回中1回 ⇔ 数字の指示 36回中11回」「出だしの崩れは6回とも数字の指示の回」と書いたのは、少ない回数を手で数えた誤り。同じ基準で数え直すと、大きな問題が出た回は **数字の指示 27回中11回（41%）⇔ 数字なし（声の調子だけ）66回中19回（29%）⇔ 指示なし 8回中1回**。数字を外すと減るが、無くならない。出だしの崩れも、数字なしで5回あった。PHASE0_VERIFICATION.md G-17 の訂正）。会話の形は、もともと台本を一度に読む形より1割ほど速い（文と文の間の休みが入らない）。以下は、それまでの経緯の記録： 指示の文面は声の型の一部（9-8。どの型を使うかは8章の「上書き」：システム共通の既定 → 依頼主 → 業務、A/B のときは割当）。ユーザーの経験：「2倍速」と指示すると実際は 1.3倍前後になる。⛔**音の変換で速める方式は取り下げた**（理由は15章の32）。速く話させると台本の言葉を言い換えることがある（G-3：「確認させてください」→「確認させていただきました」）ので、決まった言い回し（名乗り・言い直す値）は通話後の検証（6-12 の (b)）で確かめる | 指示文を作る処理（6-3） |
| (2) | **自由に答えさせている**（何が正解か決まっていないと、AIが近い言葉に寄せてしまう） | 業務設定の質問ごとに、**答えの選択肢**と、その言い方の例を宣言する。選択肢には必ず「わからない」を入れる（2026-10-13：システムが「わからない」「答えたくない」を自動で足す。6-2）。AIは、宣言された選択肢の中からしか選べない（`record_answer` の条件IDは、宣言の中のものだけ受け付ける） | 業務設定の書き方の決まり（Intent.md 6-4 の取込の検証で、選択肢の無い質問を落とす） |
| (3) | **日本語の曖昧な答え**（「結構です」「大丈夫です」「いいです」は、受け入れにも断りにも取れる） | 曖昧な言い方の一覧を、システム共通で1つ持つ。当たったら「聞き取れない・曖昧」と同じに扱い、6-11 の決まり（1回だけ聞き返す → 復唱）に乗せる。曖昧な答えのときの聞き返しは、意味を確かめる言い方にする（例：「ご不要ということでよろしいでしょうか」） | システム共通の会話の決まり（6-3 の材料3） |
| (4) | **相づちを答えと取り違える**（AIが話している途中の「はい、はい」） | AIが質問を言い終える前の、**相づちだけの短い発話**（はい・ええ・うん など）は、答えとして受け付けない。発話の時刻で、流れの制御が判定する。言い終える前でも、中身のある答え（「15日でお願いします」など）は受け付ける | 流れの制御（6-1） |
| (5) | **会話AIの耳が1つしかない** | 答えの部分の音声を、**会話AIとは別の音声認識**でも聞く。会話AIの答えと食い違えば、その項目は「-」（わからない）にし、誤った値を渡さない。別の音声認識は「独立した証拠」になる（材料は同じ音でも、聞く仕組みが違う） | 通話後の検証（6-12） |

- **(5) は、まず通話後に行う**（会話の速さに影響しないため）。食い違いが多い業務だけ、通話中に行って「その場で聞き直す」形を、測ってから考える。
- 別の音声認識の候補（クラウドの日本語音声認識、PC の中で動く音声認識）は、フェーズ0で比べる（PHASE0 G-15）。
- Gemini のライブラリ（google-genai 2.29.0）にある次の設定も、(1)・(4) の手当ての候補として効き目を測る（PHASE0 G-14）。設定するのは、セッションの設定を作る1か所（`start_session`）だけ。
  - 文字起こしの言葉のヒント（会社名・担当者名など。業務設定と相手のデータから、その通話のぶんだけ作る）
  - 相手が話し始めた・話し終えたと判断する感度
- **効き目は、必ず数字で確かめる**：電話の音質で録った答えの試験集を作り、仕組みを1つ足すたびに、聞き取りの正しさを測る（PHASE0 G-14・16-2）。⛔**足しても数字が上がらない仕組みは、外す。**

### 6-11. 聞き返し・復唱・念のための確認（1つの決まり。2026-10-12 ユーザー提案）
**3つとも、項目の状態（4-4）の上で動く1つの決まりにする。** 回数を数えるのはプログラム（Q6）、言い方はセッションの最初の指示（6-3）。

| 場面 | ふるまい | 回数の上限 |
|---|---|---|
| **その場で聞き取れない・曖昧**（必須項目） | 「聞き取りにくかったので、もう一度、おっしゃっていただいてよろしいでしょうか」と聞き返す。聞けたら、その値を**復唱**して確かめる（確かめない型の項目でも、聞き返したあとは復唱する） | 聞き返しは**1項目1回まで**（何度も聞き返すと失礼になるため） |
| **復唱して、相手が訂正した** | 訂正された値を、もう1回だけ復唱する | 訂正のあとの復唱は1回まで。それでも違えば「-」 |

- **【2026-10-13 ユーザー確定】復唱の言い方も、決まった言い方にする。基本は「（値）で、よろしいでしょうか。」**（聞き返し・念のための確認と同じく、言い方はシステム共通の1か所。`phase0/phrases.py` の `CONFIRM`）
  - ただし、同じ言い方の連発は機械っぽいので、**場面ごとに複数用意し、同じ場面の中では順番に回す**（ユーザー）。場面は流れの制御が決める。差し戻しのときも、待っている言い直しと同じ言い方を使う。
    | 場面（流れの制御が決める） | 言い方（順番に回す） |
    |---|---|
    | ふつう（その場ではっきり聞けた値） | 「（値）で、よろしいでしょうか。」／「（値）で、大丈夫でしょうか。」 |

  - 🔴**AIの発話の文字起こしは、実際に口から出た音ではなく、AIが言うつもりだった文字である**（2026-10-12 の G-3）。AIが「お忙しいところ」を「おも忙しいところ」と言い間違えた回に、文字起こしは「お忙しいところ」だった（ユーザーが聞いて見つけた）。また、声が約1秒しか作られなかった回にも、文字起こしは全文だった。⇒ AIの言い間違い・言い漏れは、録った音声を別の耳で聞く (b)(d) でしか見つけられない。ただし、別の音声認識も、言い間違いを正しい言葉に直して書き出すことがありうる。⇒ この録音を試験集に入れて、別の耳が言い間違いを見つけられるかを G-15 で確かめる。

- 4つのどれかが実行できなかった（音声認識が落ちた等）ときは、「確かめられなかった」として記録し、**検証に合格したことにしない**。(a) が実行できなかった項目のうち、確かめない型で取れた値（`accepted`）は、`unresolved` に落とす（「わからない」を「取れた」として渡さない。芯の5）。
- 検証が終わるまで、判定（7-1）と出力（7-1b）は動かない。
- **【追加 2026-10-13】検証は順番待ちにして、1件ずつ行う。** 別の耳のモデルにも1分あたりの上限がある（gemini-3.5-transcribe-live は TPM 20,000。2分の通話で約3,000〜6,000トークン ⇒ 1分あたり3〜6本ぶん）。順番待ちの量は、門（5-2 の 9）が数える。

  - **どの結果のときに、かけ直すか・終えるかは、業務設定で宣言する**（「再発信の方針」。依頼主ごと・業務ごと）。宣言の無い組は取込で止める（既定値で埋めない）。例：
    | 業務の結果 | 依頼主A（全部埋めたい） | 依頼主B（1回かけて、聞けた分でよい） |
    |---|---|---|
    | `incomplete`（一部だけ取れた） | かけ直す（3回まで・1日あける） | 終える |
    | `not_reached`・不在 | かけ直す（3回まで） | かけ直す（1回まで） |
    | `not_reached`・取り次いでもらえなかった | かけ直す（日を改めて1回） | 終える |
    | `open`（応答なし・留守電など） | かけ直す（3回まで） | かけ直す（2回まで） |
    - **宣言で変えられないもの（システムだけ。8章）**：`do_not_call`（発信の拒否）は必ず終える（原則14）。`completed`・`declined`・`out_of_scope` も終える（目的を果たした・用件を断られた・番号違い）。戻る時刻・折り返しの時刻が取れたら、その時刻にかける。苦情があった・拒否を確かめられなかった・判定できない、は終える（上の順2）。回数の上限は、システムの上限より緩められない。
    - **人は仲介しない**（2026-10-13 ユーザー決定）。「人が見るまで待つ」行は作らない。
    - **画面では一括で登録できるようにする**（2026-10-13 ユーザー：表の最上段に、レ点のような形式で、選んだ行にまとめて同じ値を入れる）。画面の作りは CL-3。データは、結果ごとの行のまま持つ（まとめて入れても、行ごとに値が残る）。
  - 依頼主への報告には、両方を出す：**処理**（済み／かけ直し待ち）と、**結果**（目的を果たした／一部だけ取れた（どの項目が取れたか）／断られた／…）。⇒ 「リストの1行として完了」＝処理が済み、「業務として完了」＝目的を果たした、と読み分けられる（CL-3 の出力の型へ伝える）。
  - 上の表の順7 は「宣言どおり」に置き換わる（承認のあと）。
- 守ること：
  - 回数の上限
  - 間隔（「結果不明」のあとは長めの最小間隔）
  - 時間帯（実際の判定は門が行う）
  - 終わった状態（`completed`・`declined`・`do_not_call`）は、二度とかけない

## 8. 設定の合成

| 上書き | 業務 ＞ 依頼主 ＞ システム共通の順で、最初に値があるもの | 声の型（声の名前＋話し方の指示）、スクリプトの言い回し、出力の形式 |

### 9-1. 停止と、自動の解除（2026-10-13 CL-2。ユーザー：「運用や仕組み、判定の精度を上げることで、人がいない仕組みを構築して」）
**止めるのも解くのも、原因ごとに決めた条件で、システムが行う。** 人が解くのは、人が自分で押した緊急停止だけ。
| 止める原因（データベースの名前） | 止める範囲 | 自動で解く条件（確かめはシステムが行い、結果を記録に残す） |
|---|---|---|
| 保存の失敗（`storage_failure`） | 全体 | 試しの書き込みと読み戻しが、決めた回数続けて成功した |
| 回線の異常が続いた（`line_failure`） | その回線（続けば依頼主） | 回線の状態の確かめ（アプリ・端末の応答）が、決めた回数続けて正常 |
| 会話AIにつながらない（`ai_connection`） | 全体 | 試しのセッション（指示文つき・相手なし）が、決めた回数続けて開けた |
| 会話AIの混雑・1分あたりの上限（`project_denied`） | そのプロジェクト（キーの選択 Q15） | 待ってから1回だけ試して通った。**待ちは、当たるたびに 10秒→30秒→2分→10分→30分**（2026-10-13 ユーザー決定。10/12 の閉じる番号 1008 は、長い利用拒否ではなく、1分あたりの上限に当たっただけだった）。値は設定 `stop.ai_rate_limit.backoff` |
| 言ってはいけないことを言った（`forbidden_speech`。2つの耳で確かめたもの） | その業務 | **その版では再開しない。** 新しい版が、その場面を含む模擬通話（16-2）に合格したら、新しい版で、段階的な立ち上げ（10-1）の最初の段から再開 |
| 品質の基準を外れた（`quality_gate`。10-1） | その業務 | 同上 |
| 費用の上限（`budget`） | 依頼主・全体 | 上限の期間（日など）が替わった |
| 人が押した緊急停止（`manual`） | 押した範囲 | **押した人（運営者）が解く**（人が自分で止めたものは、人の意思で解く） |
- **止まっているか（Q13）は、「まだ解かれていない停止が1つでもあるか」で決める。** 原因が2つ重なっていれば、片方を解いても止まったまま（前の「最新の記録が状態」では、別の原因の解除で再開してしまう）。
- 解除は、どの停止を解いたかを指して記録する（1つの停止は1回だけ解ける）。**システムが解けるのは、システムが止めた停止だけ**（人の緊急停止をシステムは解けない）。データベースが守る。
- 止めるときは、同じ取引で、まだ発信していない予約を取り消す（5-2-1 の2）。
- 止まる・解けるを短い間に繰り返す（ばたつく）ときは、解く前の待ちを、回数に応じて自動で伸ばす（上限つき）。
- 止めた・解いたは、運営者に知らせる（知らせるだけ。返事は待たない）。
- 「決めた回数」「決めた時間」は設定の値（8章。システムだけ）。**値の正本は設定の表（`app/db/migrations/0005_settings.sql`。2026-10-13 に仮の値を入れた：ユーザー「忘れないように、最適だと思う値を入れておいた方がよい」）**。どの値も「仮」で、根拠といつ見直すかを持つ。

## 10. 検証モード

### 10-1. 自動の品質の門（人の承認の代わり。2026-10-13 CL-2。ユーザー：人がいない仕組みを）
**立ち上げ期も、人の承認を前提にしない。** 人が確かめていたこと（この業務設定で、正しく話し・正しく取り・正しく判定できているか）を、**数で測って、基準を満たしたときだけ進める**。置き場所は承認と同じ2か所（発信の前＝門の前／結果を送る前）で、判定の処理は持たない（原則9のまま。モードを読むのも、ここだけ＝I-13）。
1. **依頼主の最初の業務を本番に上げる前：模擬通話に合格する**（Intent.md 6-6・16-2。**2026-10-13 ユーザー決定：依頼主ごとに最初のみ、10本**。品質の基準を外れて止まった業務を再開するとき（9-1）も行う）。相手役のAIが、**正解の答えを知っている台本**で何度も話す。⇒ 取れた値・業務の判定が、正解と一致した割合を**自動で**数える（実際の通話では正解が分からないので、正解のある模擬通話で、判定の精度を測る）。言ってはいけないことの検出は0件であること。
2. **段階的な立ち上げ**：新しい版は、まず決めた件数（例：20件）だけ発信する。その件数の指標が基準の内側なら、自動で次の段（例：100件 → 全部）へ進む。外れたら、自動でその業務を止める（9-1 の `quality_gate`）。指標（どれも自動で数える）：
   - 通話後の検証で、2つの耳が食い違った割合（聞き取りの精度の代わりの物差し）
   - 判定できない（`unknown`）の割合（0 であるべき）
   - 言ってはいけないことの検出（0 件であるべき）
   - 苦情・発信の拒否・途中で切られた・技術的な失敗の割合
3. **結果を送る前**：通話後の検証が済み、判定が済んだ版に、自動で「送ってよい」の印を付ける。段階的な立ち上げの最初の段だけは、その段の指標が基準を満たしてから、まとめて印を付ける（基準を外れた版の結果を、確かめないまま依頼主へ送らない）。
- ⚠️ 正直に書く：**実際の通話の「正しさ」そのものは、正解が無いので測れない。** 測れるのは、(1) 模擬通話での正解との一致、(2) 実際の通話での2つの耳の一致、の2つ。(2) は正解ではない（2つの耳がそろって聞き違えたものは見えない。1-2）。
- 基準の値（件数・割合）は設定の値（8章。システムだけ）。**値の正本は設定の表（0005）。仮の値を入れてある**（模擬通話と最初の実測で見直す）。
- 人の承認（下の検証モード）は、**依頼主が契約で求めたときだけ使う選択**として残す（既定は使わない）。

### 10-2. 人の承認を使うとき（依頼主が求めた場合だけ）
- 流れは、フルオートと完全に同じにする。違いは次の2か所の「人の承認」だけである。
  - 発信の前：タスクの承認（門の前。4-2）
  - 結果を送る前：人が確かめる
- **人が結果を直した場合**：
  - システムが判定した結果は、そのまま残す。
  - 人の判断は「正解」として別に記録する。誤判定率（Intent.md 16-3）の材料にする。
  - 依頼主へ送るのは、人が承認した結果とする。
  - ⇒ 判定の処理（`judge_task`）は、両モードで1文字も変わらない。
- **機械での見張り**：「いまどちらのモードか」を読む場所が、承認の部分だけであることを静的検査で確かめる（14章 I-13）。
- **【追加 2026-10-13 CL-2】「送ってよい版」の印**（CL-3 のお願い）：結果の版に「送ってよい」の印を付けるのは、**結果を送る前の承認の部分だけ**。フルオートでは、承認の部分が素通りして、判定した版に印を付ける。検証モードでは、人が承認した版（人が直したなら人の版）に印を付ける。送るのは、印の付いた版のうち最新のもの。⇒ モードを読むのは承認の部分だけのまま（I-13）。

## 11. 依頼主の分離

- データの読み書きは、**依頼主IDを必ず受け取る層1つ**だけを通す。それ以外からデータベースを直接読む道を作らない（静的検査）。
- 利用するデータベースに「行ごとに読める人を制限する」機能があれば、それも重ねる（製品はフェーズ0の後に決める）。
- テストでは、**わざと別の依頼主のIDで**、すべての画面とAPIを叩く。
- **【追加 2026-10-13 CL-2】分離は2段**（契約者どうし・依頼主どうし。Intent.md 11-2）。読み書きの層は「誰が（利用者と、その種類：運営者／システムの処理／あとで依頼主の利用者）・どの契約者の・どの依頼主のデータを」を必ず受け取り、取引ごとにデータベースへ渡す。
- **データベースは PostgreSQL の「行ごとに読める人を制限する機能」を使う**（2026-10-13 決定。Intent.md 14-1）。システムの処理はデータベースの持ち主とは別の役で接続し、制限を外せない形にする。取引で渡された契約者・依頼主の行しか、読めない・書けない・作れない。
- 3-0 の1（組の参照）と合わせて、**3重**で守る：(1) 層が依頼主IDを必ず受け取る (2) データベースが行を制限する (3) 別の依頼主の親を指す行は作れない。
- システム共通の表（番号の台帳・システムの発信禁止・停止の記録）は、依頼主を持たない。番号の台帳には、どの依頼主かを書かない（5-2）。

## 12. 費用・APIキー

### 12-1. 利用量の台帳
- 1行ごとに、出どころ（会話AI・電話）、種類（**実測**か**推定**か）、量、単価の版を持つ。

### 12-2. キーの選択
- キーとプロジェクトの対応表を持つ。どのプロジェクトか分からないキーは「同じプロジェクト」とみなす。
- 選択の処理は1つだけにする。エラーへの反応は、9章の表に従う。
- キーの値は、選択の処理の外へ出さない。ログには識別名だけを残す。

## 16. 決まったこと（2026-10-12 ユーザー確定）

1. **依頼主をまたいで、同じ番号への発信の間隔を、システムで制限する**（5-2）。
2. **その場の確認は、聞き間違えやすい項目だけ**に行う。最後にまとめて読み上げない（4-4・6-4）。
3. **途中で切られた・断られた通話は、取れた内容と、切られた・断られたことを記して渡す**（7-1b）。
4. **方式は Gemini Live。** 言ってはいけないことは、セッションの最初に指示として渡し、セッションが替わるたびに渡し直す。口に出す前にリアルタイムで止める仕組みは作らない（1-3・6-6）。
5. **別の依頼主の架電に入るときは、セッションを立ち上げ直す**（ユーザー指摘）。⇒ 設計では、さらに広げて**1回の通話ごとに新しいセッション**にした（6-6・I-17）。
6. **その場の確認の決まりも、セッションの最初の指示に入れる**（ユーザー指摘）。プログラムは、確かめが済むまで次の質問を渡さないことで抜けを防ぐ（4-4）。
7. **取れなかった項目は、依頼主の指定が無ければ「-」（わからない）・「✕」（拒否）で書く**（7-1b）。
8. **聞き取りの精度を上げる仕組みを入れる**（ChatGPT の実験で精度が悪かったため）。5つの原因ごとに1か所で手当てし、効き目は数字で確かめる（6-10）。
9. **その場で聞き取れない必須項目は、1回だけ聞き返して復唱する。「-」の項目は、会話の最後や切りの良いときに、念のため1回だけ聞き直す**（ユーザー提案。6-11）。

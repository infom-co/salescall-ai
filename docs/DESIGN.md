## 0. この設計の芯（5つ）

1. **判断は、問いごとに1か所だけ。** 「今かけてよいか」「完了か」「次はいつか」「このエラーはどうするか」は、それぞれ**1つの処理だけ**が答える。ほかの場所は、その答えを読むだけにする（2章）。
2. **取り消せない操作は、「判定」と「予約」を1つの取引で行う門だけが許す。** 判定と実行の間にすき間があると、同時に動く2つの処理が両方とも門を通り、同じ相手に二重にかける（5章）。
3. **会話のいまの位置は、プログラムが持つ。AIは持たない。** AIは「聞く・話す・答えを分類する」だけを受け持つ。次にどの質問へ進むかは、プログラムが決める（6章）。
4. **聞き間違えやすい項目は、聞いたその場で相手に確かめる。** 相手本人の「はい」だけが、AIとは独立した証拠になる。AIが聞き取った値どうしが一致しても、同じ耳で聞いた結果どうしなので、独立した証拠にはならない（6-4）。最後にまとめて読み上げるのではなく、その場で確かめるので、途中で切られても確かめた分は残る（2026-10-12 ユーザー確定）。
5. **「わからない」は、第3の値として最後まで運ぶ。** 0・空・既定値で埋めない。わからないものは、完了にも発信可にも倒れない（1章）。

## 1. 「精度100%」について ── 作りで保証できること・できないこと

**正直に書く。AIと音声に頼る部分は、作りだけでは100%にできない。** そこで、次の2つに分ける。

| 区分 | 中身 | どう扱うか |
|---|---|---|
| **作りで100%にする**（不変条件） | (1) 門を通らない発信は0件 (2) 同じ番号への同時の二重発信は0件（依頼主をまたいでも） (3) 発信禁止台帳に載った番号への発信は0件 (4) 停止中の新規発信は0件 (5) 必須項目が「取れた」（4-4）でない「完了」は0件 (6) 別の依頼主のデータの参照・更新は0件 (7) 取込に失敗したときの部分的な更新は0件 (8) 書き戻しの二重登録は0件 (9) キーの値がログ・画面に出るのは0件 | データベースの一意制約・取引・静的検査・テストで、**機械が守る**。わざと壊したら本当に止まるかも試す（14章） |
| **作りでは100%にできない**（AI・音声・人に依存） | 聞き取りの誤り、回答の分類の誤り、AIが言ってはいけないことを言う、相手が誤って「はい」と言う、留守番電話や自動音声の見分け | 測って下げる。**誤りが起きても、取り消せない側（完了・発信可）には倒れず、「不明」「要確認」に落ちる**ように、誤りの向きを作りで決めておく |

### 1-1. 誤りの向きを決める、とは
| 誤り | 起きたときの向き |
|---|---|
| 聞き間違えやすい項目（日付・数など）を聞き違えた | その場の確認で相手が訂正する ⇒ 正しい値に直る。確かめる前に切られたら「確認済み」にならない ⇒ その項目は取れていない扱い（依頼主へは「-」） |
| 「はい／いいえ」などの答えを、逆に分類した | はっきり聞こえたと AI が思った答えには、その場の確認をかけない。代わりに、通話後の検証（6-12 の (a)）で別の音声認識でも聞き、食い違えば「-」にする ⇒ 誤った値は渡らず、「-」に落ちる |
| 分類を誤った（違う分岐へ進んだ） | 必須項目が埋まらない、またはその場の確認で食い違いが出る ⇒ 「未完了」か「要確認」 |
| 留守番電話を人と見誤った | その場の確認に「はい」が返らない ⇒ 聞き間違えやすい項目が「確認済み」にならない ⇒ 「未完了」 |
| 相手の「やめて」を聞き逃した | **通話中には防げない。** 通話後の検証（6-12 の (c)）で、拒否の言葉を探して発信禁止に登録する（取り逃しの回収）。次の発信の前に必ず検証が終わるので、二度目の発信は起きない |

### 1-2. 残る誤り（ゼロにはできないもの）
次の2つは作りでは消せないので、16-3 の誤判定率として測る。
- **相手が誤った確認に「はい」と言い、それを正しく聞き取った場合**：「確認済み」なのに値が誤っている。
- **その場の確認をかけない項目**（「はい／いいえ」・選択肢など）で、**会話AIと別の音声認識が、そろって同じように聞き違えた場合**：別の耳（6-10 の (5)）でも見つけられない。

### 1-3. 「言ってはいけないこと」は、指示で防ぎ、記録で見つける
- Gemini Live は「音声のまま考えて音声のまま話す」ので、声が相手に届く前にプログラムが中身を確かめる場所は無い。
- **口に出す前にリアルタイムで確かめて止める仕組みは、作らない**（2026-10-12 ユーザー確定。「無理があるし、会話が成り立たない」ため）。
- **防ぎ方**：言ってはいけないことを、目的・業務設定・トークスクリプトと一緒に、**セッションの最初に指示として渡す**。セッションが替わるとAIは忘れるので、**どのセッションを始めるときも必ず渡し直す**（6-6）。
- **見つけ方**：通話後に、AIが言ったことの文字起こしを、言ってはいけないことに当てる。見つかったら、その業務を止めて人が見る（6-12 の (d)）。
- ⇒ Intent.md 1-3 の「AIによる許可されていない約束0件」は、作りで保証するものではなく、**指示で防ぎ、記録で見つけて止める**ものとして扱う。

## 2. 一本化の表 ── 問いごとに、答える場所は1つ

**この表が、設計の中心である。** 新しい処理を書くときは、まずこの表で「その問いに答える場所が、もう在るか」を見る。在れば、それを呼ぶ。2つ目を作らない。

| No. | 問い | 唯一の答える場所 | 読むだけの側 | ⛔やってはいけない二重化の例 |
|---|---|---|---|---|
| Q1 | この番号は、どの番号か（同じ相手か） | **番号の正規化**（`normalize_phone`）：表記ゆれをそろえ、種別（携帯・固定・フリーダイヤル等）を返す。正規化できなければ「不明」 | 取込、発信禁止の登録、門、折り返しの照合、重複判定 | 取込とは別に、門の中で独自に番号を整形する |
| Q2 | **今この相手にかけてよいか** | **発信の門**（`claim_dial`）：判定と予約を1つの取引で行う（5章） | スケジューラー（候補を出すだけ）、画面（理由を出すだけ） | スケジューラーや画面が、時間帯や発信禁止を自分で判定する |
| Q3 | この相手は、かけてはいけない相手か | **発信禁止台帳**（依頼主ごと＋システム共通） | 門だけが読む | 業務設定の「除外条件」を、門の中で別に判定する（⇒ 番号で決まる除外は取込時に台帳へ入れる。データの条件で決まる除外は、取込時にタスクを作らず理由を残す） |
| Q4 | 次に、いつ・何をするか（かけ直す／終える） | **次の動きの決定**（`next_action`）：`scheduled_at` を書くのはここだけ | スケジューラー、画面 | 例外処理の中で、その場で再発信の予定を入れる |
| Q5 | **この業務は完了か** | **業務の判定**（`judge_task`）：入力から結果が1つに決まる処理。版番号を持つ | 出力、報告、画面、費用集計 | 出力の処理が「必須項目が埋まっていれば完了」と自分で判定する |
| Q6 | この項目は取れたか | **項目の状態**（4-4）：会話制御だけが書く。聞き返し・復唱・念のための確認の回数も、ここで数える（6-11） | 判定、出力 | 文字起こしからの抽出で、項目を「確認済み」に上げる。AIの記憶で回数を数える |
| Q7 | 会話はいま、どこにいるか | **流れの制御**（6章）：プログラムが持つ | 会話AI（AIの操作への返事で、次の質問を受け取る。張り替えのときは `start_session` が、いまの位置を渡す） | AIの記憶に流れを任せる |
| Q8 | 電話口の相手は誰か（受付・本人・留守電・自動音声・FAX） | **相手の種別**（4-3）：回線の信号と音声の分類を、決まった優先順位で1つにまとめる | 流れの制御、判定 | 回線モジュールとAIが、それぞれ別に留守電を判定する |
| Q9 | このエラーは何で、どうするか | **エラーの分類**（`classify_error`）＋**処置の表**（9章） | すべての呼び出し元 | 呼び出し元ごとに、その場で再試行やキー切替を書く |
| Q10 | この設定値は、結局いくつか | **設定の合成**（`resolve_settings`）：項目ごとに決めた合成の種類で解く（8章） | すべての処理 | 処理の中で「業務設定に無ければ依頼主設定」と個別に読む |
| Q11 | どの声・話し方で話すか | **声の割当**（`assign_voice`）：**「声の型」＝声の名前＋話し方の指示（声の調子と速さ）の組**を、A/Bの割当も含め、タスクに1回だけ記録する（2026-10-12 改：A/B は声の型どうしで比べる。9-8） | 会話AI接続、指示文を作る処理（話し方の指示は、記録された声の型から読む）、集計 | 再発信のたびに割り当て直す。話し方の指示を、声の型とは別の設定から読む |
| Q12 | 今は、かけてよい時刻か | **時間帯の判定**（日本時間・祝日の暦つき）：門の中で使う | 門、画面 | スケジューラーが独自に時間帯を見る |
| Q13 | 止まっているか | **運転の状態**（全体・依頼主ごとの停止） | 門だけが読む | 各処理が、それぞれ停止の印を見て止まる |
| Q14 | このデータを、この人が見てよいか | **アクセスの確認**（依頼主IDを必須にした、データの読み書きの層1つ） | すべての画面・API | 画面ごとに、依頼主IDで絞り込む処理を書く |
| Q15 | どのAPIキーを使うか | **キーの選択**（キーとプロジェクトの対応表つき。12章） | 会話AI接続 | 接続処理の中で、エラーのたびに次のキーへ進む |
| Q16 | いくら使ったか | **利用量の台帳**（実測と推定を区別する） | 画面、採算、門（予算の上限） | 画面が通話時間から料金を計算し直す |
| Q17 | 結果を、どこへ送ったか | **連携の台帳**（送り先ごと。二重登録防止の鍵つき） | 画面、再送 | 再送の処理が、送ったかを外部システムに聞いて判断する |
| Q18 | 会話AIのセッションを、何を渡して始めるか | **セッションの開始**（`start_session`）：1回の通話（試行）につき新しいセッションを開き、版つきの指示文（目的・業務設定・スクリプト・言ってはいけないこと）と、流れの制御が持つ「いまの位置・取れた項目」を、**必ず**渡す（6-6） | 会話AI接続（新規・つなぎ直し・キー切替のすべて） | つなぎ直しやキー切替の処理が、自分でセッションを開く（⇒ 指示の渡し忘れが起きる） |
| Q19 | この項目は、その場で確かめるか | **項目の型の一覧**：型（日付・時刻・数・金額・名前・電話番号・メール・住所・はい/いいえ・選択肢 など）ごとに、確かめるかを決める（4-4） | 指示文を作る処理（確かめ方の決まりを指示に書く）、流れの制御（確かめが済むまで次へ進めない） | 業務ごと・質問ごとに、確かめるかをばらばらに書く |
| Q21 | 通話のあとに、何を確かめるか | **通話後の検証**（6-12）：1つの処理が、決まった4つを順に行う | 判定（結果を読む）、発信禁止台帳（登録を受ける）、運転の状態（業務の停止を受ける） | 別の音声認識・拒否の言葉探し・禁止事項の当て込みを、それぞれ別の処理で書く |
| Q20 | 依頼主へ渡すとき、取れなかった項目をどう書くか | **出力の書き方**（7-1b）：既定は「-」（わからない）と「✕」（拒否）。依頼主の指定があれば、その書き方 | 出力・報告・書き戻し | 出力先ごとに、空欄・「不明」・「なし」などをばらばらに書く |

**機械での見張り**：Q2・Q4・Q5・Q9 の「書く側」が1か所であることは、静的検査で確かめる（14章 I-12）。

## 3. データの単位（何が、何を持つか）

Intent.md 10-1 は「状態を4つの軸に分ける」と決めたが、**どの軸を、どのデータが持つか**が決まっていなかった。そのため「再発信をまたいで業務状態はどこにあるのか」が曖昧だった。ここで決める。

```
依頼主 ─┬─ 業務 ── 業務設定の版（変更不可）
        │
        ├─ 実施回（取込単位。どの版で実施するかを固定する）
        │      └─ タスク（実施回 × 連絡先。業務の状態を持つ）
        │             ├─ 試行（1回の発信。通話の状態を持つ）
        │             │     └─ 区間（相手が替わるごと：受付 → 担当者）
        │             ├─ 項目の値（項目ごとの状態と、根拠の発話）
        │             └─ 連携（送り先ごと。連携の状態を持つ）
        ├─ 連絡先（正規化した番号。依頼主ごと）
        ├─ 発信禁止台帳
        └─ 利用量の台帳
システム共通：発信禁止台帳（緊急通報番号など）、APIキーとプロジェクトの対応表、運転の状態、
            番号の台帳（正規化した番号ごとに「最後に発信した時刻」と「いま進行中か」だけを持つ。
            依頼主をまたいだ間隔の制限と同時発信の防止に使う。どの依頼主かは持たない）
```

### 3-1. 一意の約束（データベースの制約で守る）
| 約束 | 制約 | 防ぐ害 |
|---|---|---|
| 同じ依頼主の中で、同じ番号は1つの連絡先 | 一意（依頼主ID, 正規化番号） | 表記ゆれで、同じ相手が2件になる |
| 1つの実施回で、同じ連絡先は1タスク | 一意（実施回ID, 連絡先ID） | 同じファイルを2回取り込んで二重にかける |
| 1つの連絡先に、進行中の試行は1つだけ | 部分一意（連絡先ID, 状態が「予約〜通話中」のもの） | 同時に2つの処理が、同じ相手へかける |
| **1つの番号に、依頼主をまたいで進行中の試行は1つだけ** | 番号の台帳の「進行中」を、門の取引の中で立てる（立っていれば不許可）。試行が終わったら降ろす | 別々の依頼主の業務が、同じ番号へ同時にかける（依頼主ごとの連絡先の制約では防げない） |
| 1回線に、進行中の試行は1つだけ | 部分一意（回線ID, 同上） | 1台の電話で2通話を始めようとする |
| 1タスクの1項目は、値が1つ | 一意（タスクID, 項目ID） | 値の取り違え |
| 1つの送り先へは、同じ結果を1回だけ | 一意（タスクID, 送り先ID, 結果の版） | 再送による二重登録 |

### 3-2. 業務設定の版をどこで固定するか（Intent.md では未定義だった）
- **実施回が、版を固定する。** 実施の途中で業務設定を直しても、実施中のタスクは古い版のまま進む。
- 新しい版に切り替えるには、「この実施回を版 N に切り替える」という操作を、記録つきで行う。
- 試行は、実際に使った版を必ず記録する（A/Bテストと誤判定の調査が、版ごとに正しく割れるようにするため）。

### 3-3. 「取込単位」と「再実施」の区別（Intent.md では区別が無かった）
- 同じ相手に、来月もう一度同じ業務をする場合は、**新しい実施回**を作る。
- 実施回をまたいだ「前回いつかけたか」は、門が連絡先の履歴で見る（5-2）。

## 4. 状態の移り変わり

### 4-1. タスク（業務の状態）
```
open ──(判定)──▶ completed / callback_scheduled / incomplete / declined /
                  do_not_call / out_of_scope / needs_human / unknown
   ▲                         │
   └──(next_action: かけ直す)─┘   ※ completed・declined・do_not_call は終わり（かけ直さない）
```
- **書くのは、`judge_task`（業務の状態）と `next_action`（次の予定）だけ。**
- `do_not_call` は、どの業務設定よりも優先する（Intent.md 原則14）。

### 4-2. 試行（通話の状態）
```
claimed（門が予約した）─▶ dialing ─▶ ringing ─▶ answered ─▶ in_conversation ─▶ ending ─▶ ended
   │          │           │              │
   └─ call_failed / no_answer / busy / dropped（途中切断）/ technical_error
claimed ─(期限切れで発信しなかった)─▶ released
```
- **検証モードの承認は、門の"前"に置く**（タスクに対する承認）。承認されたタスクだけが門へ進み、門の予約の直後に発信する。
  - 理由：門の予約のあとに人の承認を待つと、待っている間に時間帯・停止・発信禁止が変わっても、古い判定のまま発信してしまう。門の判定と発信の間には、人の待ちを挟まない。
- **`claimed` から `dialing` へ進めるのは、電話接続モジュールの1か所だけ。** 予約証が「期限内で、まだ使っていない」ことを確かめ、使用済みに書き換えるのを1つの操作で行う（5-3）。
- **途中で処理が落ちた試行**（`dialing` 〜 `in_conversation` のまま残ったもの）は、起動時に `technical_error`（結果不明）にする。
  - ⛔**すぐにかけ直さない。** 実際には話していた可能性があるので、すぐかけ直すと「二重発信」と同じ害になる。最小の間隔を `next_action` が守る。

### 4-3. 相手の種別（区間ごと）
`unknown` ／ `reception`（受付）／ `target`（担当者本人）／ `voicemail`（留守番電話）／ `ivr`（自動音声）／ **`fax`（FAX）** ／ `wrong_party`（番号違い・別の会社）
- **【追加】FAX**：法人の代表番号には FAX 回線が混ざっていることがある。Intent.md には無かった。
- **1つにまとめる優先順位**：

### 4-4. 項目（項目ごとの状態）
```
empty ─(はっきり聞き取れた)─▶ heard（値・根拠の発話）
empty ─(聞き取れない・曖昧)─▶ unclear ─(聞き返し：1項目1回まで)─▶ heard（聞き返して聞けた値）
                                     └(聞き返しも使い切った)─▶ unresolved（「-」。念のための確認を待つ）
  │
  ├─【確かめる型】、または【聞き返して聞けた値】
  │     heard ─(復唱して確かめる)─▶ checking
  │     checking ─(相手が肯定)─▶ confirmed
  │              ├(相手が訂正)─▶ 訂正された値をもう1回だけ復唱 ─(肯定)─▶ confirmed
  │              │                                              └(また違う)─▶ unresolved
  │              └(答えない・その前に切られた)─▶ unresolved
  │
  └─【確かめない型で、はっきり聞き取れた値】 heard ─(形式の検査に合格)─▶ accepted
unresolved ─(念のための確認：1項目1回まで。会話の最後か、切りの良いとき)─▶ heard ⇒ 復唱 ⇒ confirmed
           └(それでも聞けない・相手が急いでいる・切られた)─▶ unresolved のまま（依頼主へは「-」）
heard / empty / unresolved ─(相手が答えを拒んだ)─▶ refused（依頼主へは「✕」。二度と聞かない）
empty / unclear ─(相手が「わからない」と答えた)─▶ dont_know（「取れた」には入らない。依頼主へは「-」。答えは聞けたので、念のための確認はしない）
（どこからでも）─(時間切れ・通話終了)─▶ そのまま残る（自動で confirmed・accepted にはならない）
confirmed / accepted ─(通話後の検証で食い違い：6-12)─▶ unresolved（理由つき）
```
- **状態の名前は、この図のものだけを使う**：`empty`（まだ聞いていない）、`heard`（聞き取った）、`unclear`（聞き取れない・曖昧）、`checking`（復唱中）、`confirmed`（確認済み）、`accepted`（確かめない型で取れた）、`dont_know`（相手が「わからない」と答えた。2026-10-13 に足した）、`unresolved`（「-」）、`refused`（「✕」）。
- 聞き返し・復唱・念のための確認の決まりは、6-11 に1つにまとめた（2026-10-12 ユーザー提案）。
- **その場で確かめるかは、項目の「型」で決める**（2026-10-12 ユーザー確定：聞き間違えやすい項目だけ）。決めるのは、型の一覧の1か所だけ（2章 Q19）。
  - **確かめる型**：日付、時刻、数、金額、名前（会社名・担当者名などの固有名詞）、電話番号、メールアドレス、住所。
  - **確かめない型**：はい／いいえ、決まった選択肢、自由な意見・感想。
  - 中の名前（2026-10-13。CL-2 のデータの形と同じ11＋1）：日付 `date`・時刻 `time`・日時 `datetime`・数 `number`・金額 `amount`・名前 `name`・電話番号 `phone`・メール `email`・住所 `address`／はい・いいえ `yes_no`・決まった選択肢 `choice`・**自由な意見 `free_text`**（CL-2 の依頼で名前を決めた）。
  - 確かめる型は、言い直しに使うので、値の言い終わり（「です」「。」など）を外す。**確かめない型は、相手の言葉のまま**（自由な意見の「よかったです」を「よかった」に変えない）。
  - **【追加 2026-10-14 G-34】日付・時刻・日時・数・金額の型は、値の中の空白も外す**（相手の声を文字にしたもの「15 日の午後 2 時」を、AIがそのまま写して報告した。依頼主へ渡す値に空白が入る）。名前・住所・メールは、空白に意味がありうるので外さない。⇒ 型の一覧の決まり（`core/value_types.py` に移す）。
  - **【✅ 2026-10-14 ユーザー承認】同じ型の値の漢数字は、数を数える言葉（日・時・分・秒・月・年・週・人・名・歳・個・枚・件・回・円 など）の前にあるものだけ、数字に直す**（「十五日の午後二時」⇒「15日の午後2時」・「三人」⇒「3人」・「三万五千円」⇒「35000円」。`flowctl.normalize_value`）。⛔ G-36：AIが値を漢数字で報告した（1回目・2回目に1本ずつ）＝意味は正しいが、依頼主へ渡す値の書き方がそろわない。数える言葉の前にない漢数字（「一緒」「一度」）と「一番」は直さない。「十分」は「時」のすぐあとのとき（「2時十分」）だけ直す（「十分です」は「足りる」の意味）。
  - **【追加 2026-10-13】電話番号の型**（折り返しの番号など。CL-2 の依頼）：会話の側は、**話し言葉の数字を数字の並びに直すだけ**（漢数字を数字に・番号の区切りの「の」を外す）。そのあと必ず**番号の正規化（Q1。CL-2 の `core/phone.py` の `normalize`）**を通す。「+81」の組み立てや種類の判断を、会話の側でしない（番号を整えるのは1か所）。
    - 正規化が「不明」を返したら（桁が合わない など）、その値は受け付けずに差し戻す（6-2 の値の形式）。差し戻しの文に、正規化が返した理由（日本語）を入れる ⇒ AIは聞き返す（1回まで。6-11）。
    - 言い直しは、相手が言った区切りのまま読み上げる（区切りの無い数字の並びは、相手が確かめにくい）。記録には、正規化が返した番号（`national`・`e164`）と種類を残す。
    - かけてはいけない種類（有料の情報番号など）の番号を相手が言ったときは、聞いたとおりに記録し、かけるかは門が決める（会話の側では判断しない）。
  - 型の一覧に無い型は、業務設定の読み込みで落とす（確かめるかが決まっていない項目を残さない）。
  - 業務設定で、型の既定と違う扱いにする項目は、理由つきで宣言する。
  - **型ごとの決まりも、この一覧に持つ**（2026-10-12 の G-6 で見つかった穴から）。例＝**時刻：午前か午後かを必ずはっきりさせる。相手が言わなければ聞く。AIが補わない**（G-6 で、相手の「2時」を AI が自分で「午後2時」と記録した）。
- **確かめ方**：最後にまとめて読み上げない。**聞いたその場で、会話の流れの中で言い直す**（例：相手「15日の午後2時で」→ AI「15日の午後2時で、よろしいでしょうか。」→ 相手「はい」。言い直しの言い方は決まった言い方で、場面ごとに複数を順番に回す＝6-11。2026-10-13 ユーザー確定）。途中で切られても、確かめ済みの項目は残る。
- **この決まりは、セッションの最初の指示に入れる**（2026-10-12 ユーザー指摘）。指示文を作る処理（6-3）が、型の一覧から「どの型を、どう確かめるか」を書き出す。業務ごとに手で書かない。
- **プログラムの役目は、抜けと先回りを防ぐこと**：
  - 確かめる型の答えを受け付けたら、確かめの結果（`confirm_field`）が届くまで、次の質問を渡さない。⇒ AIが確かめを飛ばしても、そのまま次へは進めない。
  - **言い直す値は、プログラムが記録した値そのもの**を、返事に書いて渡す（G-6 で、声で言い直した値と記録した値が違った）。
  - **確かめの結果は、言い直しを求めたあとに相手の発話が届いていなければ、受け付けない**（I-24）。G-6 で、AI が相手の返事を待たずに「肯定された」と報告した。⇒ 相手の「はい」を独立の証拠にする決まり（6-4）を、AIの先回りで崩させない。相手の発話が届いたかは、相手の音声の文字起こし・発話の検出で、プログラムが数える。
- **「取れた」の定義**（判定・出力が使う唯一の定義）：
  - 確かめる型、または聞き返して聞けた値 ⇒ `confirmed`（相手の肯定と、形式の検査に合格の両方）
  - 確かめない型で、はっきり聞き取れた値 ⇒ `accepted`（形式の検査に合格）
  - **この2つの状態だけ**。「取れた」かは状態だけで決まる（条件や理由を見なくてよい）。
  - **【変更 2026-10-13 ユーザー決定（CL-2 から依頼）】相手が「わからない」と答えた項目は「取れた」に入れない**（`dont_know`）。必須の質問が「わからない」なら、業務は完了ではない（判定 7-1。扱いは 15-2-3 の案）。⛔ 前は `accepted`（条件＝わからない）＝「取れた」にしていたので、ほかの必須項目がそろうと完了になっていた。条件を見て除く形にしなかったのは、「取れた」を使う処理（判定・出力・画面・張り替えの指示文）が、みな条件も見なければならなくなるため（試作では、張り替えの指示文が条件の中の名前＝英字をそのままAIに見せていた）。
- 形式の検査の例：日付として正しいか、選択肢の中にあるか、電話番号の形か。

### 5-2. 門（`claim_dial`）が1つの取引の中で行うこと
すべてを確かめ、すべて通ったときだけ「試行（`claimed`）」の行を作り、予約証を返す。**1つでも判断できなければ、通さない。**

1. 運転の状態：全体・依頼主ともに止まっていない（Q13）。
2. 時間帯：日本時間・祝日の暦で、システムの上限と依頼主の設定の両方の内側にある（Q12）。
3. 発信禁止台帳：依頼主の台帳にもシステム共通の台帳にも、載っていない（Q3）。
4. 番号：正規化できていて、発信してよい種別である（Q1）。
5. 間隔と回数：
   - 同じ連絡先への前回の試行から、決まった間隔が空いている。
   - 1日・合計の回数が上限の内側にある。
   - 前回が「結果不明」なら、その分の長い間隔が空いている。
   - **前回の試行の通話後の検証（6-12）が終わっている。** 終わっていなければ通さない（検証で拒否の言葉が見つかるかもしれないため）。
   - **依頼主をまたいで**、同じ番号への前回の発信から、システムで決めた間隔が空いている（2026-10-12 ユーザー確定）。門が見るのは番号の台帳の「最後に発信した時刻」だけで、どの依頼主がかけたかは見ない・出さない（依頼主の分離を崩さない）。
6. 進行中の試行：同じ連絡先に進行中の試行が無く、**番号の台帳でも、その番号が進行中になっていない**（依頼主をまたいだ同時発信を防ぐ）。通れば、同じ取引の中で番号の台帳を「進行中」にし、「最後に発信した時刻」を書く（3-1）。
   - ⛔「最後に発信した時刻」を読むだけで、書くのを取引の外にすると、同時に来た2つの予約が両方とも通る。**読むのと書くのは、同じ取引の中で行う。**
7. 回線：空いている回線があり、その番号の1日の上限の内側にある（Intent.md 8-6）。回線を借りる。
8. 予算：依頼主・全体の、その日の費用の上限の内側にある（Q16）。

### 6-1. 役割分担
| 担当 | 受け持つこと | 受け持たないこと |

### 6-3. 指示文は1か所で作る
- 業務設定の版から、会話AIへの指示文を作る処理は1つだけにする。版と結びつけて保存する。
- **会話の決まりは、すべてこの指示文に入れる**（セッションの最初に渡すもの。6-6）。材料は次の3つで、どれも1か所から読む。
  1. 業務設定の版：目的、トークスクリプト、質問と選択肢、言ってはいけないこと、名乗り、終了の条件、**相手が「忙しい」と言ったときの一言**（空なら丁寧に終える＝既定。文があれば1回だけそれで聞く。Intent.md 9-4。2026-10-13 ユーザー）
  2. 項目の型の一覧（Q19）：どの型をその場で確かめるか、どう確かめるか
  3. システム共通の会話の決まり：曖昧な答えの聞き直し方（6-10 の (3)）、相づちの扱い、断られたとき・「AIですか」と聞かれたときのふるまい
  4. **【追加】話し方の指示（声の調子と速さ）**：タスクに記録された「声の型」（Q11）から読む。声の型は、声の名前と話し方の指示の組で、版を持つ。⇒ 同じ声でも話し方の指示だけ違う型どうしで A/B ができる（2026-10-12 ユーザー：Sadachbia の S2 と S4 で比べたい）。
- **相手のデータ**（会社名・備考など、依頼主のファイル由来のもの）は、指示文の中に「データ」として区切って入れる。指示としては入れない。
- **相手の発話**は、指示文に入れない。
- **【追加 2026-10-13】名前は「」でくくって入れる。くくるのは、この処理だけ**（Intent.md 6-8）。名前（自社名・担当者名・商品名など、取込で印を付けたもの。相手の会社名・相手の名前も）は「表記」と「読み」を持つ項目として受け取り、この処理が「」でくくる。ほかの処理は「」を足さない。読みの伝え方は、フェーズ1で試してから決める。
- ⇒ Intent.md 原則13 の言い方を、ここに合わせて直した：
  - 運営者が作り、検証し、承認した業務設定＝指示（信頼する）
  - 依頼主のファイルの中身・相手の発話・外部システムのデータ＝材料（指示として扱わない）

### 6-4. 聞き間違えやすい項目を、その場で確かめる理由
- Intent.md 9-5 は「通話中に記録した値」と「通話後の文字起こしからの抽出」の**二者一致**を、完了の証拠にしていた。
- **しかし、この2つは独立していない。** どちらも、同じ会話AIが同じ音声を聞いた結果である。聞き違えていれば、2つとも同じように聞き違える。**一致は、正しさの証拠にならない。**
- **独立した証拠は、相手本人の確認だけである。** そこで、聞き間違えやすい型の項目は、聞いたその場で言い直して確かめ、相手の肯定をもって `confirmed` にする（4-4）。
- **確かめ方の決まりは、セッションの最初の指示に入れる**（4-4）。プログラムは、確かめの結果が届くまで次の質問を渡さないことで、抜けを防ぐ。
- 通話後の文字起こしと別の音声認識は、**食い違いを見つける側**にだけ使う（6-12）。一致しても、`confirmed`・`accepted` には上げない。

### 6-5. 終了
- 終了を決めるのは制御である。AIは求めることしかできない。
- 締めに入る前に、「-」の項目の念のための確認を1回だけ行う（6-11）。相手が切った・断った・急いでいるときは、しない。
- **【追加 2026-10-13 ユーザー】相手が「忙しい」と言ったとき**：業務設定の「忙しいと言われたときの一言」が空なら、丁寧に終える（既定）。文があれば、流れの制御がその一言を**1回だけ**AIに言わせ、相手が応じれば続け、2回目の「急いでいる」で終える。通話そのものを断られたときは、設定にかかわらず終える（Intent.md 原則14）。
- 終わってよいとき：
  - 必須項目がすべて「取れた」（4-4 の定義）
  - 拒否・範囲外・留守電など、終了してよい理由がある
  - 時間や発話の予算が尽きた
  - 一定時間、相手が黙っている
- 締めの言葉も、業務設定から作る。

### 6-6. 「言ってはいけないこと」を防ぐ：すべてのセッションの最初に、必ず指示を渡す
- **方式は Gemini Live（音声のまま考え、音声のまま話す）に決めた。** 口に出す前にリアルタイムで中身を確かめて止める方式は、作らない（2026-10-12 ユーザー確定）。
- **防ぎ方**：目的・業務設定・トークスクリプト・**言ってはいけないこと**を、指示文（6-3 で作る、版つきのもの）として、セッションの最初に渡す。
- **セッションは、1回の通話（試行）ごとに新しく開き、使い回さない。**
  - 別の依頼主の架電に入るときは、必ず立ち上げ直す（2026-10-12 ユーザー指摘）。
  - さらに、**同じ依頼主・同じ業務でも、相手が替われば立ち上げ直す。** 前の相手の会話がセッションに残っていると、その内容（相手の名前・答え）が次の相手との会話に混ざるおそれがあるためである（依頼主の分離、Intent.md 原則4 と同じ理由）。
  - 通話が終わったら、そのセッションは閉じる。
- **セッションが替わると、AIは前の指示を忘れる。** そこで、セッションを始める処理を1つにし（2章 Q18 の `start_session`）、次の**すべての**場面で、その処理を通す。
  1. 通話の最初（＝別の依頼主・別の業務・別の相手に替わるとき）
  2. セッションの上限による張り替え（6-9）
  3. 通信の切断からのつなぎ直し
  4. APIキーの切り替え（9章）
- **張り替え・つなぎ直しのときに渡すもの**：指示文に加えて、流れの制御が持っている「いまの質問・取れた項目・確かめ済みの項目・相手の種別」。
  - 会話の位置をプログラムが持っている（6-1）ので、AIが前のセッションを忘れていても、続きから正しく話せる。
  - ⇒ **「AIの記憶に頼らない」作り（芯の3）が、ここで効く。**
- **見つけ方（通話後）**：6-12 の (d)。
- **機械での見張り**：会話AIのセッションを開く場所が `start_session` の1か所だけで、指示文を渡さずには開けないことを、静的検査と試験で確かめる（14章 I-15）。
- **考える量**も、`start_session` が設定の値から渡す（2026-10-12 の G-11）。⛔「考えるレベル」は gemini-3.8-live では受け付けられない。使えるのは「考える量の予算」。予算0（考えない）は速く（真ん中の値 0.81秒・最大 1.16秒）、既定（自動）は 0.99秒・最大 2.07秒。決まりを守れるかは、既定が10回中10回、予算0が10回中9回（1回は原因不明）。⇒ どちらにするかは、通話の記録の文字起こし（6-12）で測り直してから決める。

### 6-7. 通話中に、会話AIのセッションが切れたとき（この決まり1つだけ）
- **つなぎ直しは、1回だけ、決まった秒数以内に試す。** `start_session` を通し（6-6）、指示文といまの位置を渡し直す。使うキーは、キーの選択（12-2）が決める（切れた原因がキー固有なら、別のキー）。
  - つなぎ直している間、相手を無言にしない。待ってもらう短い音声（「少々お待ちください」）を、電話接続モジュールが直接流す。
- **つながらなければ、終える。** 声ごとに、あらかじめ作っておいた**おわびの音声**を、電話接続モジュールが直接流して終える。どちらの音声も会話AIに頼らない。
  - 試行は `technical_error` にし、次の動きは最小の間隔を空ける（4-2）。
- 秒数とつなぎ直しの回数は、システム共通の設定の値で持つ（8章の「厳しいほう（上限）」）。
- **【追加】AIが黙ったとき（セッションはつながっているのに、相手が話し終えてから決まった秒数、AIが話さない）も、この決まりの中で扱う**（2026-10-12 の G-11：48回中1回、AIが30秒黙った）。
  - 「話した」かは、**実際に届いた声の長さ**で判断する（文字起こしや、区切りの合図では判断しない）。G-3 で、文字起こしには全文があるのに声が 0.77秒・0.82秒しか届かない回があった（相手には途中から無言に聞こえる）。
  - **話し終わりの合図が来たのに、届いた声が、そのターンの文字起こしの長さに比べて短すぎる**ときも、「AIが黙った」と同じ扱いにする。2回とも、Google が返した出力の音声の量は約1秒ぶん（25〜26 トークン）だけで、Google の側で声が作られていなかった。どこからを「短すぎる」とするか（1秒あたりの文字数の上限）は、ふつうの発話の速さ（G-3 の会話の形で 1秒に 6.7〜8.2文字）から、設定の値として決める。
  - 【追加 2026-10-12 の G-17】**声が約1秒で止まる現象は、短い一言でも起き、終わりが切れる**（「失礼いたし」「ありがとうございま」で止まった。204ターン中4回）。どれも、出力の音声が 25〜26トークン（約1秒）で止まっていた。⇒ 「1秒あたりの文字数の上限」だけでは見つけられない（切れた一言は1秒に9〜10文字にしか見えない）。見分け方は、(a) 出力の音声の量が約1秒ぶんで止まり、かつ (b) その声の、ふつうの話す速さ（声の型ごとに実測して設定の値で持つ）で言い切るのに要る長さより短い、の2つで判断する。どこで線を引くかは、フェーズ1の通話の記録で、見逃しと誤りの数を数えてから決める。
  - 【追加】**反対に、声が長すぎるとき**（同じ文を2回言った。G-17 で1回。AI自身の文字起こしには1回しか無かった）も、通話後の検証（6-12）で拾う。会話中には止めない（言ってしまった後なので、止めても相手には届いている）。
  - 【追加 2026-10-13 G-16 の3回目】**AIが、日本語の文のあとに、英語の説明を声に出した**（「念のため確認させてください。15日の午後2時でお間違いございませんか。」のあとに「Confirming the date and time, 15th at 2:00 p.m.」。AI自身の文字では「*Confirming the date and time "15th at 2 PM".*」と、星印で囲まれていた＝自分の動きの説明を、そのまま声にした）。
    - 起きた割合：会話の形で 606ターン中1回、台本を1文ずつ読ませる形で 240ターン中1回（G-17 の「To read this script, I'll project ...」）。⇒ **少なすぎて、指示文に決まりを足して減ったかを数で確かめることはできない**（何千回も要る）。⇒ 起きる割合に頼らず、**起きたら止める**形にする。
    - 見分け方：AIの1ターンの見分け方（`turn_check` の `wrong_language`：ローマ字の単語が4つ以上続く）。会話の中では、AI自身の文字が届くたびに同じ見分け方を当てる。

    - **止められるかは、AIの文字が、声より先に届くかで決まる**（声は話す速さで届き、届いたそばから相手に流れる）。⇒ 測った（G-16 の4回目、文字のかたまり 359）：**先に届いたのは29%、先行の中央は 0.00秒**。⇒ ⛔ **英語を文字で見つけてから止めても、相手にはもう聞こえている＝止める案は、防ぐ手段にならない**（言いかけを短くするだけ）。声を遅らせて流せば先に見つけられるが、返事が毎回その分だけ遅れる（ふつうの返事の速さは中央 0.88秒。G-11）。⇒ 防ぐ手段は、まだ無い。⏳ ユーザーと決める。

      - ⏳ G-34 の「長い間」の場面で、AIが「はい。」のあと黙って待てるか（黙っている間にAIが話し出すと、この一言とぶつかる）を確かめる。
    - ⚠️ 前の試験（G-30〜G-32）を流し直すときは、測ったときの決まり（「ごゆっくりどうぞ」）を試験の側で指定する（`g30_latency.OLD_THINKING_RULE`）。
    - ⚠️ **2026-10-14 ユーザー（G-34 の通話全体を聞いて）**：「S2 や S4 の『えーとですね』の後の『はい』が、物欲しそうな、期待しているような『はい』に聞こえるので、相づち風の『はい』でいい。L4 の『はい』は問題なし」。⇒ 2つの形を G-36 で比べる：
      - **A（言い方を足す）**：AIが自分で「はい。」と言う。指示に「軽い相づちとして、落ち着いた声で、語尾を上げずに短く（相手の答えを期待するような言い方にしない）」を足す。⚠️ AIの声の調子は指示どおりにならないことがある（6-11 の「声は言うつもりの言葉どおりではない」と同じ）。
      - **B（録音の相づち）**：AIは声を出さずに「相手が考えている」と報告する（操作 `report_thinking`。返事を待たない宣言にし、返事はAIに話させない形＝SILENT で返す）。報告が届いた瞬間に、プログラムが相づち風に読んだ「はい。」の録音（`phrases.ACK` の `aizuchi`。運営者が承認する）を流す。⇒ 声の調子は録音で決まる。さらに、この報告を「相手が黙っている秒数（5秒で『いかがなさいましたか？』）」の数え始めに使える（いまは数え始めの合図が無い）。⚠️ AIが答えを「考えている」と取り違えて報告すると、答えを聞き逃して5秒待つことになる（G-36 で数える）。
      - 採らなかった形のコードは、決まったら外す（G-33 と同じ）。
      - **✅ 2026-10-14 ユーザー（G-36 を聞いて）：「これまでより、良くなりました」「形 A が良い」⇒ A にした**。B の操作・指示・録音の相づち・受け取りの処理は外した（B は12回中11回でねらいどおり黙ったが、答え「家族で行こうと思ってます。」を考えている途中と読み違えて黙った回があった。G-36 の記録）。
      - ⇒ 「いかがなさいましたか？」の5秒は、**AIの「はい。」が終わってから**数える（6-7 と同じ見張り：最後に話したのがAIで、相手が黙っている秒数）。

## 7. 判定の処理（唯一の正本）

### 7-1. 業務の判定（`judge_task`）
入力（項目の状態・相手の種別・申告・通話の事実）から、結果が1つに決まる処理にする。外の状態は読まない。版番号を持ち、その版を結果と一緒に記録する。

**上から順に、最初に当たったものが答え：**

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | 拒否の申告がある（通話中、または通話後の文字起こしで検出） | `do_not_call` |
| 2 | 番号違い・別の会社 | `out_of_scope`（その番号を連絡先から外す） |
| 3 | 範囲外の求めで終えた | `out_of_scope` |
| 4 | 断られた（業務設定の「断り」の条件に当たった） | `declined` |
| 5 | 必須項目がすべて「取れた」（4-4 の定義） | `completed` |
| 6 | 折り返しの日時が `confirmed` | `callback_scheduled` |
| 7 | 苦情・怒りの申告がある | `needs_human` |
| 8 | 必須項目が1つでも「取れた」になっていない（`empty`・`unclear`・`checking`・`unresolved`） | `incomplete` |
| 9 | 会話に至らなかった（留守電・応答なし・話し中・FAX など） | `open` のまま（次の動きに回す） |
| 10 | 上のどれにも当たらない | `unknown` |

- 苦情・怒りの申告は、結果がどれになっても「人へ知らせる」印を別に持つ（順7 は、ほかに当たらないときの結果を決めるだけ）。

### 7-1b. 依頼主へ渡す内容（2026-10-12 ユーザー確定）
業務の結果が何であっても、依頼主へは次を渡す。作るのは出力の処理1か所で、判定の結果を読むだけにする（判定し直さない）。
- **取れた内容**（4-4 の「取れた」の項目だけ）。
- **通話の終わり方**：最後まで話せた／相手が途中で切った／断られた／留守番電話／応答なし など。試行の終わり方と業務の結果から作る。
- **項目の書き方（Q20 の唯一の場所）**（2026-10-12 ユーザー確定）：
  | 項目の状態 | 既定の書き方 |
  |---|---|
  | 取れた（4-4） | 値 |
  | 拒まれた（`refused`） | ✕ |
  | 相手が「わからない」と答えた（`accepted`・条件＝わからない） | - |
  | それ以外（`empty`・`unclear`・`checking`・`unresolved`。聞けていない・聞き返しと念のための確認でも聞けなかった・確かめる前に切られた・通話後の検証で食い違った） | - |
  - 依頼主から書き方の指定があれば、出力の設定でその書き方にする（8章の「上書き」）。
  - 確かめる前に切られた値などは、依頼主へは「-」で渡す。内部には根拠の発話つきで残し、誤判定の調査に使う。

### 7-2. 次の動き（`next_action`）
- 入力：業務の状態、試行の履歴、再発信の決まり（8章で合成したもの）。
- 出力：「かけ直す（日時）」か「終える（理由）」の2つだけ。
- `scheduled_at` を書くのは、この処理だけ。
- 守ること：
  - 回数の上限
  - 間隔（「結果不明」のあとは長めの最小間隔）
  - 時間帯（実際の判定は門が行う）
  - 終わった状態（`completed`・`declined`・`do_not_call`）は、二度とかけない

## 8. 設定の合成

Intent.md 5-4 には「具体的なほうを優先する」と「緩められない」という2つの決まりが並び、項目ごとにどちらを使うかが決まっていなかった。**項目ごとに、合成の種類を設定の定義の中で宣言する。** 合成するのは `resolve_settings` の1か所だけ。

| 合成の種類 | 解き方 | 例 |
|---|---|---|
| 上書き | 業務 ＞ 依頼主 ＞ システム共通の順で、最初に値があるもの | 声の型（声の名前＋話し方の指示）、スクリプトの言い回し、出力の形式 |
| 厳しいほう（上限） | すべての階層のうち、いちばん小さい値 | 1日の発信上限、同時通話数、費用の上限、再発信の回数 |
| 厳しいほう（範囲） | すべての階層の範囲の重なり | 発信してよい時間帯 |
| 足し合わせ（禁止） | すべての階層の和 | 発信禁止、除外条件、禁止事項 |
| システムだけ | 依頼主・業務からは変えられない | 認証情報、緊急停止、拒否の扱い |

- 定義に合成の種類が書かれていない項目は、読み込みの時点で落とす（書き忘れを残さない）。

## 9. エラーの分類と処置（1つの表）

**どこで起きたエラーも、`classify_error` が種類に分け、処置はこの表だけが決める。** 呼び出し元は、表の処置を実行するだけにする。

| 種類 | 例 | 処置 |
|---|---|---|
| キー固有 | 認証失敗、キーの無効化（実測：閉じる番号 1007＋文面「API key not valid」） | そのキーを使わない印を付ける。次のセッションからは別のキーを使う（通話の途中なら、6-7 のつなぎ直しの1回に使う） |
| **プロジェクトの利用拒否** | **実測：閉じる番号 1008＋文面「Your project has been denied access」**（2026-10-12、10個中4個のキーで発生）。ユーザーが管理画面で確かめた理由は**「1分あたりの入力トークン数（TPM）の上限」** | そのプロジェクトを、しばらく「使えない」にし、**人に知らせる**。⛔同じプロジェクトかもしれないキーへは切り替えない（対応表で別のプロジェクトと分かっているキーだけ候補）。⛔ほかのキーへ次々に切り替えない（上限を避ける使い方に見え、ほかのプロジェクトも止められうる）。戻すのは、決めた時間を空けてから、そのプロジェクトで1回だけ試して通ったとき。根本の手当ては、門の TPM の数え方（5-2 の 9） |
| **設定の誤り** | **実測：閉じる番号 1007＋文面「…is not supported for this model」**（例：考えるレベルの設定） | ⛔キーは切り替えない（キーのせいではない）。新しい発信を止め、人に知らせる（設定を直すまで、どのキーでも同じ結果になる） |
| プロジェクトの枠 | プロジェクト単位のクォータ超過（実測：閉じる番号 1011＋文面「You exceeded your current quota」） | ⛔同じプロジェクトのキーへは切り替えない。対応表で「別のプロジェクト」と分かっているキーだけ候補にする。無ければ新しい発信を止める（門が不許可を返す） |
| 一時的な混雑 | 一時的なレート制限、タイムアウト | 間隔を伸ばしながら、回数の上限まで |
| 通話中の切断 | 会話AIのセッションの切断 | 6-7（1回だけつなぎ直し、駄目ならおわびして終える） |
| 回線の切断 | 通話そのものが切れた | 試行は `dropped`。相手が切ったのか回線が切れたのかを区別して記録する（依頼主へ渡す「終わり方」に使う。7-1b） |
| 回線 | 発信失敗、回線の上限、端末・アプリの異常 | その回線を休ませる。続いたら、依頼主ごと止める |
| 保存 | データの保存失敗 | ⛔**新しい発信を止める。** 記録できない状態でかけ続けない |
| 連携 | 書き戻しの失敗 | 連携だけ再送（4-5）。通話の結果は失わない |
| **不明** | 上のどれにも当たらない | **キーは切り替えない**（原因が分からないまま回すと、無料枠の回避と同じ形になる）。続いたら止める |

- 連続回数で止める条件（Intent.md 10-3）も、この表の種類ごとに持つ。
- **【変更】種類は、閉じる番号ではなく、番号と文面の組で見分ける**（2026-10-12 の実測）。同じ 1007 が「キーの誤り」と「設定の誤り」の両方で返った。番号だけで「キー固有」と決めると、設定の誤りのたびにキーを次々切り替えてしまう。見分けに使う番号と文面の対応は、`classify_error` の1か所に持ち、実測した組だけを入れる（見たことのない組は「不明」）。

## 10. 検証モード

- 流れは、フルオートと完全に同じにする。違いは次の2か所の「人の承認」だけである。
  - 発信の前：タスクの承認（門の前。4-2）
  - 結果を送る前：人が確かめる
- **人が結果を直した場合**：
  - システムが判定した結果は、そのまま残す。
  - 人の判断は「正解」として別に記録する。誤判定率（Intent.md 16-3）の材料にする。
  - 依頼主へ送るのは、人が承認した結果とする。
  - ⇒ 判定の処理（`judge_task`）は、両モードで1文字も変わらない。
- **機械での見張り**：「いまどちらのモードか」を読む場所が、承認の部分だけであることを静的検査で確かめる（14章 I-13）。

## 11. 依頼主の分離

- データの読み書きは、**依頼主IDを必ず受け取る層1つ**だけを通す。それ以外からデータベースを直接読む道を作らない（静的検査）。
- 利用するデータベースに「行ごとに読める人を制限する」機能があれば、それも重ねる（製品はフェーズ0の後に決める）。
- テストでは、**わざと別の依頼主のIDで**、すべての画面とAPIを叩く。

## 12. 費用・APIキー

### 12-1. 利用量の台帳
- 1行ごとに、出どころ（会話AI・電話）、種類（**実測**か**推定**か）、量、単価の版を持つ。
- 会話AI：APIが利用量を返すなら、それを実測として記録する（3.8 で返るかは要確認）。返さないなら、通話時間からの推定とする。
- 電話：事業者が明細を返す方式は実測、Rakuten Link のように返さない方式は「料金表 × 通話時間」の推定とする。
- 画面には、実測と推定を分けて出す。採算の判断（Intent.md フェーズ9）には、推定の割合も添える。

### 12-2. キーの選択
- キーとプロジェクトの対応表を持つ。どのプロジェクトか分からないキーは「同じプロジェクト」とみなす。
- 選択の処理は1つだけにする。エラーへの反応は、9章の表に従う。
- キーの値は、選択の処理の外へ出さない。ログには識別名だけを残す。

## 13. 電話接続の方式（フェーズ0で確かめる候補）

### 13-1. 方式によらない入口
- Intent.md 8-2 の操作を、共通の入口にする。
- 発信は、予約証を受け取る1か所からしか呼べない（5-3）。

### 13-2. 候補と、確かめる形
| 候補 | 想定する形 | 一番の不確かさ |
|---|---|---|
| Rakuten Link デスクトップ版（Windows） | PC の音声装置を仮想の装置に差し替えて、AIとつなぐ。発信は画面操作で行う | 画面操作は壊れやすい。スマホとの連携の条件（同じネットワークに居る必要があるとの報道）。規約 |
| 携帯回線＋Bluetooth のハンズフリー | PC（または専用の小さな機器）を「ハンズフリー装置」として電話につなぐ。発信・切断・通話状態・音声の受け渡しを、ハンズフリーの決まった命令で行う | PC 側でその命令を扱えるか（扱えない場合は専用の機器が要る）。音質。キャリアの規約 |

## 14. 不変条件と、機械での見張り

**「守っているつもり」を許さないため、条件ごとに見張り方と、わざと壊す試験を決める。** 見張りが本当に落ちることを確かめていないものは、見張っていないのと同じに扱う。

| No. | 不変条件 | 見張り方 | わざと壊す試験 |
|---|---|---|---|
| I-1 | 発信は、予約証の入口1か所からしか呼ばれない | 静的検査（回線モジュールの発信関数を呼ぶ場所を数える） | 2か所目の呼び出しを足すと、検査が落ちる |
| I-2 | 同じ連絡先に、進行中の試行は1つ | 部分一意の制約 | 2つの処理から同時に予約すると、片方が失敗する |
| I-3 | 発信禁止の番号は、門を通らない | 門の試験 | 台帳に入れた番号で予約すると、不許可になる |
| I-4 | 停止中の新規予約は0件 | 門の試験 | 停止の印を立てて予約すると、不許可になる |
| I-5 | `completed` ⇒ 必須項目がすべて「取れた」（4-4） | 判定の試験＋保存時の検査 | 確かめる型の1項目を `heard` のまま判定すると、`completed` にならない |
| I-6 | 「不明」を既定値で埋めない | 項目の型が「不明」を持つ。既定値の禁止を静的検査 | 既定値を足すと、検査が落ちる |
| I-7 | `scheduled_at` を書くのは `next_action` だけ | 静的検査 | 例外処理に予定の書き込みを足すと、検査が落ちる |
| I-8 | 取込は、全部か何も無いか | 取引の試験 | 途中の行でわざと失敗させると、何も変わっていない |
| I-9 | 書き戻しは二重登録されない | 一意の制約 | 同じ結果を2回送ると、1件になる |
| I-10 | キーの値がログ・画面に出ない | ログの出口で伏せる処理＋試験 | わざとキーを含むエラーを起こすと、伏せられている |
| I-11 | 別の依頼主のデータを読めない | 読み書きの層の静的検査＋試験 | 別の依頼主のIDで叩くと、拒否される |
| I-12 | 2章の「唯一の答える場所」が1つずつ | 静的検査（書き込みの場所を数える） | 2か所目を足すと、検査が落ちる |
| I-13 | モードを読むのは承認の部分だけ | 静的検査 | 判定の中でモードを読むと、検査が落ちる |
| I-14 | 設定の項目は、すべて合成の種類を持つ | 読み込み時の検査 | 種類の無い項目を足すと、起動で落ちる |
| I-15 | 会話AIのセッションを開くのは `start_session` だけで、指示文を渡さずには開けない | 静的検査＋試験 | 別の場所からセッションを開くと検査が落ちる。指示文を空にすると開けない |
| I-16 | 業務設定の項目は、すべて型の一覧にある型を持つ | 読み込み時の検査 | 一覧に無い型の項目を足すと、読み込みで落ちる |
| I-17 | 1つのセッションは、1回の通話（試行）だけに使う | セッションを試行IDに結びつけ、別の試行から使おうとしたら止める＋試験 | 終わった通話のセッションで次の相手にかけようとすると、止まる |

## 16. 決まったこと（2026-10-12 ユーザー確定）

1. **依頼主をまたいで、同じ番号への発信の間隔を、システムで制限する**（5-2）。
2. **その場の確認は、聞き間違えやすい項目だけ**に行う。最後にまとめて読み上げない（4-4・6-4）。
3. **途中で切られた・断られた通話は、取れた内容と、切られた・断られたことを記して渡す**（7-1b）。
4. **方式は Gemini Live。** 言ってはいけないことは、セッションの最初に指示として渡し、セッションが替わるたびに渡し直す。口に出す前にリアルタイムで止める仕組みは作らない（1-3・6-6）。
5. **別の依頼主の架電に入るときは、セッションを立ち上げ直す**（ユーザー指摘）。⇒ 設計では、さらに広げて**1回の通話ごとに新しいセッション**にした（6-6・I-17）。
6. **その場の確認の決まりも、セッションの最初の指示に入れる**（ユーザー指摘）。プログラムは、確かめが済むまで次の質問を渡さないことで抜けを防ぐ（4-4）。
7. **取れなかった項目は、依頼主の指定が無ければ「-」（わからない）・「✕」（拒否）で書く**（7-1b）。
8. **聞き取りの精度を上げる仕組みを入れる**（ChatGPT の実験で精度が悪かったため）。5つの原因ごとに1か所で手当てし、効き目は数字で確かめる（6-10）。
9. **その場で聞き取れない必須項目は、1回だけ聞き返して復唱する。「-」の項目は、会話の最後や切りの良いときに、念のため1回だけ聞き直す**（ユーザー提案。6-11）。

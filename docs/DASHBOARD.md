# DASHBOARD.md — ダッシュボードの設計（持ち主 CL-3）

> **この文書の役割**：ダッシュボード（管理者と契約者が使う画面）の「あるべき形」を、1か所に書く。
> - 目的と守る決まりの正本は `Intent.md` 5章（要点だけ。詳しくはここを指す）。依頼者へ渡す出力の形の正本は `docs/DESIGN.md` 7-3・7-1b・4-5。データの形と判定は CL-2（`docs/DESIGN.md` 3〜12章）、会話は CL-1。**この文書は、それらを読むだけで、決め直さない。**
> - 人の呼び方は4つだけ（`Intent.md` 1-4）：**管理者**（ユーザー。ただ1人）・**契約者**（サブスクでシステムを使う人・会社。最初の契約者は管理者自身）・**依頼者**（契約者に電話業務を頼む会社。システムには一切かかわらない）・**お客様**（電話をかける相手）。
> - 作成：2026-11-18（CL-3）。CL-1・CL-2 の連絡帳の 2026-11-18 までの決定を入れた。

## 0. この設計の芯（6つ）

1. **画面は読むだけ。決めない。** 完了か・止まっているか・かけてよいか・設定はいくつか・割合はいくつか、は答える場所（`docs/DESIGN.md` 2章の一本化の表）が決める。画面はその答えを出すだけ。
2. **人は「確かめて、承認する」だけ。** 2026-11-01 管理者「人は甚大な問題以外で介入しない」。画面の仕事の中心は、**承認待ちを1つの受け箱に集めて、根拠と一緒に見せ、ボタン1つで決めてもらうこと**（4章）。
3. **分離はデータベースが守り、画面は試験で確かめる。** 依頼者どうし・契約者どうしのデータは、読み書きの層（Q14）と行ごとのセキュリティが守る。画面はわざと別の ID で叩く試験を必ず持つ（8章）。
4. **同じ判断・同じ言葉・同じ形は、画面の中でも1か所。** 取引の始め方・言葉・操作の確かめ方・画面の部品・数え方を、それぞれ1つの部品にする（6章）。機械の見張りで、2か所目を落とす。
5. **依頼者へは、仕組みのことを一切出さない。** 依頼者は、契約者に電話業務を頼んでいると思っている（2026-10-16）。依頼者へ出すものは出力の処理1か所（`docs/DESIGN.md` 7-3）を通り、使ってはいけない言葉の一覧で確かめる。
6. **迷ったら止める側、分からないものは「分からない」と出す。** 空欄・0・既定値で埋めない（原則10）。画面がデータベースに届かないときは、古い数を出さず「読めません」と出す。

## 2. 画面の地図（どこに何があるか）

### 2-1. 3つの場所と、いつも見える帯
```
┌ いつも見える帯 ───────────────────────────────────────────────┐
│ SalesCall │ 契約者名 │ [依頼者を選ぶ ▼] │ ⚠止まっている 1 │ ✓承認待ち 3 │ 🔔知らせ │ [緊急停止] │ 名前 ▼ │
└──────────────────────────────────────────────────────────────┘
┌ 左の道しるべ ─────┐┌ 中身 ───────────────────────────────┐
│ ■ 全体（契約者）   ││                                        │
│   ホーム           ││                                        │
│   承認待ち         ││                                        │
│   止まっているもの ││                                        │
│   知らせ           ││                                        │
│   回線と PC        ││                                        │
│   契約者の設定     ││                                        │
│ ■ 依頼者：○○商事   ││                                        │
│   概要             ││                                        │
│   業務             ││                                        │
│   お客様リスト     ││                                        │
│   結果と報告       ││                                        │
│   発信禁止         ││                                        │
│   報酬と費用       ││                                        │
│   設定             ││                                        │
│ ■ 管理者の場所 ※   ││                                        │
└────────────────────┘└────────────────────────────────────────┘
※ 管理者のときだけ出る
```
- **【今の設計より良くした点】依頼者は「上のタブ」でなく「選ぶ欄（検索つき）」にした。** Intent.md 5-1 の「依頼者ごとのタブ」は、依頼者が100を超えうる（2026-10-16 管理者）と横に並ばない。選ぶ欄で依頼者を選ぶと、左の「依頼者」の場所の中身が**全部**その依頼者に切り替わる（5-1 の「すべてが切り替わる」はそのまま守る）。最近使った依頼者を上に出す。
- **【今の設計より良くした点】「全体（契約者）」の場所を足した。** 承認待ち・止まっているもの・知らせは、依頼者をまたいで1か所に集まらないと見落とす。依頼者を1つずつ開いて探す形にしない。
- いつも見える帯の「止まっている」「承認待ち」の数は、ホームと同じ部品から読む（6-5）。0 のときは出さない（注意を引くものだけを出す）。

### 2-2. 住所（URL）の決まり
- 依頼者の中の画面は、住所に依頼者を必ず含める：`/c/{依頼者ID}/rows`。**サーバーは、住所の依頼者で取引を始める**（画面が覚えている「いまの依頼者」には頼らない。ブラウザのタブを2つ開いても、片方の操作がもう片方の依頼者に効かない＝8-3 の S-5）。
- 全体の画面は `/t/...`、管理者の場所は `/admin/...`、PC のログインは `/pc-login/...`、PC とのつなぎ口は `/link`。

## 3. あるべき流れ（端から端まで）と、画面の受け持ち

各段の「読む・呼ぶ」は CL-2 の部品。画面はそれを呼ぶだけで、判断を足さない。

### 3-1. 立ち上げ（依頼者を迎える）
| 段 | 人がすること | 画面 | 読む・呼ぶ |
|---|---|---|---|
| (1) | 依頼者を作る | 全体 → 依頼者を作る | `registry.create_client` |
| (2) | 回線（発信番号）を割り当てる | 依頼者 → 設定 → 「回線（発信番号）」 | `registry.assign_line`。業務が違えば同じ声・同じ番号は絶対に使わない（2026-11-17）＝門が守る。画面は理由（`gate.REASONS`）を出すだけ |
| (3) | 業務を作り、資料一式を取り込む | 依頼者 → 業務 → 取り込む → プレビュー → 登録 | `business_import.preview` → `register`（指紋 `digest` が違えば `PreviewChanged`＝「中身が変わりました。もう一度確かめてください」）。決まらなかった所だけ契約者が選ぶ（2026-11-05 案A） |
| (4) | トークスクリプトを確かめる | 業務 → トークスクリプト | `business_settings.answer_rows`（標準／上書き／業務／使わない）。保存は `save_version`。標準を直すのは管理者だけ（`save_standard`） |
| (5) | 録音が足りているか | 業務 → 録音 | `recordings.version_needs`（足りない部分の警告）・`unapproved_parts`・`approve`（まだ承認していない部分だけ聞かせる） |
| (6) | 実施回を作り、お客様リストを取り込む | お客様リスト → 取り込む → プレビュー → 登録 | `registry.create_run`・`importer.preview` → `register`（止めた行の理由は `RowPlan.reason` の日本語をそのまま＝5-8）。取り込み直しは違いと担当の替わりを省かずに出す（4-410） |
| (7) | 品質の段（検証モードの業務だけ） | 業務 → 品質 | `quality_stage.current`・`metrics`・`start_kind`（模擬通話の合格待ち など） |

### 3-2. 毎日（見て、承認する）
- ホームで「止まっているもの」「承認待ち」「警告」を見る → 承認待ちを片付ける（4章）→ 進み具合を見る。
- 何もしなくても電話は進む。**画面を開かないと進まない仕事を作らない**（承認待ちは、知らせのショートメールでも届く。4章）。

### 3-3. 結果を渡す
| 段 | 何が起きるか | 画面 |
|---|---|---|
| (1) | 判定・確定（本番の版に「送ってよい」の印＝`result_releases.stage = production`） | 読むだけ |
| (2) | 出力の型で整える（依頼者ごとの形。`docs/DESIGN.md` 7-3） | 依頼者 → 結果と報告 → 出す |
| (3) | ファイルを渡す／依頼者のシステムへ書き戻す | ファイルを渡したら `backup.record_submission` を1回。書き戻しは連携の台帳（Q17。`deliveries`）。**検証の段階の結果は依頼者へ出せない**（データベースが守る） |

### 3-4. 止まったとき
- 止まっているものの画面に `stops.explain` をそのまま出す（原因の意味・自動で解く決まり・人が解く前に確かめること・この停止でも出る電話・数えたエラー・確かめの記録）。
- 自動で解けるものは待つ。人が判断して解くときは「再開」（理由は必ず。`stops.resume`）。AI の不具合の一時停止では、`impossible_because` が空のときだけ「緊急の道で再開」（押す前に、お客様の言葉が米国の OpenRouter と Google へ送られることを名前つきで確かめる。`stops.emergency_pass`）。

## 4. 承認待ち（ひとつの受け箱）

**【今の設計より良くした点】** これまでの案は、お詫びの承認・取り消せない決定・解決策・1か月以上先の答え・前の担当の方の約束・録音の承認・赤字の確認を、それぞれ別の画面に置いていた。人は「確かめて承認するだけ」（2026-11-01）なので、**1つの受け箱に集め、同じ形で見せる**。種類ごとの違いは「表」（6-4 の受け箱の表）に書き、画面の部品は1つ。

### 4-1. 1件の見せ方（どの種類も同じ形）
```
┌───────────────────────────────────────────────┐
│ [種類のしるし] 断りの確定の承認        ○○商事 ／ 業務名   残り 2時間 │
│ なにを決めるか（1行）                                          │
│ ─────────────────────────────────────────── │
│ 根拠：録音 ▶ 0:00/1:12   やり取りの文字（お客様の発言だけ強調）   │
│       システムの読み・その理由                                 │
│ ─────────────────────────────────────────── │
│ 決めないと何が起きるか（例：このお客様には、決まるまでかけません）  │
│                         [差し戻す]  [ 承認する ]                │
└───────────────────────────────────────────────┘
```
- 並び順：**(1) 緊急**（`notification_events.urgent`。例：1か月以上先の約束の5分前）→ **(2) 期限が近い順**（約束の時刻など）→ **(3) 古い順**。並べ方は受け箱の部品1か所。
- 入力欄は原則無し（人は確認と承認だけ）。理由が要る操作（再開・発信禁止の取り消し）だけ、理由の欄を出し、空では押せない。
- 押したら、その場で受け箱から消え、「承認しました（取り消す方法：…）」を出す。取り消せない操作は、押す前に何に効くか（依頼者名・お客様の会社名）を見せる（Intent.md 5-1）。
- スマホの幅でも、この形のまま使える（契約者が外出先で、知らせのショートメールから開いて承認する）。

### 4-2. 受け箱に入る種類（画面の表＝1か所。足すときはここに1行足す）
| 種類 | 何を決めるか | 読む | 決める | 根拠に出すもの |
|---|---|---|---|---|
| 取り消せない決定（断り・番号違い・怒っていた） | 確定してよいか | `approval.pending_decisions`（`ask` が偽は「確かめ中」として出すがボタンは出さない） | `approval.approve_decision`／`send_back_decision` | 録音（`backup.recording_file_name`）・やり取り（`conversation_io.utterances`）・報告（`call_report.load`）・`ASK_WHY` |
| お詫びの電話 | 案の文でかけてよいか | 知らせ `forbidden_speech` の `refs.apology_order_id` | `apology.approve` | 案の文面・その録音（声ごと）・「承認するまで約束の電話もかけない」（4-351） |
| 解決策の確かめ（実施回ごと） | 手で外した・まだ確かめていない解決策でよいか | `client_solutions.not_in_line`・`unconfirmed` | `add_earlier`／`leave_out` | ご納得いただけなかった点と解決策の文 |
| 1か月以上先のかけ直し | その日にかけてよいか | `tasks.month_ahead_waiting`・`month_ahead_answerable` | `row_fixes.answer_month_ahead` | お客様の言葉・約束の日時。答えが無ければ5分前に緊急の知らせを出してかける（2026-11-12）と書く |
| 前の担当の方との約束 | 新しい方へ引き継ぐか | `tasks.old_promise_waiting`・`row_fixes.old_promise_choice_needed` | `row_fixes.choose_old_promise` | 前の方の約束・新しい方 |
| 録音の承認（業務の部分） | その録音で話してよいか | `recordings.unapproved_parts` | `recordings.approve` | 部分の名前・文・録音（空ならボタンを出さない＝4-196） |
| 赤字の確認 | 確かめたか（発信は止めていない） | `usage.deficit_notice` | `usage.confirm_deficit` | 報酬・費用の数（`figures`）。「発信は止めていません」と必ず書く（4-140） |
| 修正依頼（管理者だけ） | 直したプログラムを入れてよいか | `fix_requests.open_requests` | `fix_requests.approve` | 依頼の要約・指すもの |
| 名前の録音の審査（管理者だけ） | 名前の録音を入れてよいか | `recordings.name_reviews` | `recordings.review_names`（まとめて流して聞き、レ点で決める） | 契約者と業務・録音 |

- この表に無い承認を、別の画面に作らない。

## 5. 画面ごとの中身

各画面の共通の決まり：上に「どこを見ているか」（契約者名・依頼者名・業務名）。読み込めないときは「データベースに届きません（○秒ごとに確かめます）」と出し、古い数を出さない。空のときは「まだありません」と、次にすること（ボタン）を出す。

### 5-1. ホーム（全体）
| 区画 | 中身 | 読む |
|---|---|---|
| 要るもの | 止まっているもの（数と、いちばん重い原因）・承認待ち（数と、いちばん急ぐもの）・警告（録音が要る・AI の不具合・控えが遅れている・応答率が落ちた） | `salescall.blocking_stops`／受け箱の部品／知らせ |
| 今日 | 依頼者ごとの今日の数：かけた・話せた・完了・かけ直し待ち・判定待ち・門で止めた（理由ごと） | 6-5 の数える部品 |
| 費用 | 今月の費用（**実測と推定を分けて**）と報酬・割合。未単価の利用があれば「単価が入っていません」 | `reward.month`・`usage_entries` |

### 5-2. 承認待ち（全体）＝4章

### 5-3. 止まっているもの（全体）
- 一覧：原因（`stops.CAUSES[原因].label`）・範囲（`SCOPE_NAMES`）・いつから・**新しい電話を止めているか**（`blocking_stops`）。
- 1件を開くと `stops.explain` を区画ごとに：意味／自動で解く決まりと確かめの記録（`stop_checks`）／人が解く前に確かめること／この停止でも出る電話（`stop_lets_through`）／数えたエラー（意味と出どころ）／止まった AI（`ai_troubles`。「通話の中で」「通話後の確かめで」）／品質の数／まだ確定していない結果。
- ボタン：「再開」（理由の欄つき。全体の範囲は管理者だけ）。緊急の道の再開（上の 3-4）。本番の PC で押した停止は、画面から解けば PC の印も消える（4-123）。
- 回線の休みは停止ではない（回線の欄 `line_states`）。回線と PC の画面に出す。

### 5-4. 知らせ（全体）
- 表 `notification_events` を、新しい順。緊急（`urgent`）は上に固定し、色と文字で分ける。本文は `summary` をそのまま（入れた時の日本語）。種類の名前は `notify.KINDS`。
- 送れたか：送り方ごとの記録（`notification_deliveries`：ショートメール・ダッシュボード）。送れなかった知らせは「送れていません（理由）」を出す。
- 管理者あての写し（`for_admin`）は管理者のときだけ。
- **送り方（2026-10-13 ユーザー決定）：契約者（と管理者）の電話番号へのショートメールと、ダッシュボード。** 知らせを作る場所は1か所（`notify.emit`。2章 Q23）、送ってその記録 `notification_deliveries` を書くのは `output/`。
  - ⛔ **契約者・管理者の電話番号を、git・文書・記録・画面の一覧に書かない**（個人情報）。番号は動かすときにデータベースの設定へ直接入れる。画面では下4桁だけ。試験は架空の番号だけ。
  - ショートメールは日本語で1通70文字まで（超えると何通分にも分かれ、その分の料金がかかる）。短い決まった形にし、詳しいことはダッシュボードに出す。例：「【SalesCall】停止 ○○商事／業務名 AIの不具合 10:32 詳しくは画面で」。
  - 承認が要る知らせ（お詫びの電話など）も、ショートメールにはボタンを付けられないので、画面へのつながりだけを入れる。
  - 1つの出来事は1回だけ送る（出来事の鍵で一意）。送れなければ決まった回数まで送り直し、それでも駄目なら「送れていません」を画面に出す。**送れなくても、システムの動き（止める・解く・発信）は変わらない。**
  - 止まる・解けるを短い間に繰り返すときは、決まった間ごとに1通にまとめる（値は設定）。
  - **毎朝の要約**：前の日の停止・解除・承認待ち・送れなかった知らせ・費用の見込みを、何も起きていない日も1通送る。**届かなければ、知らせの道か見守り役が止まっていると気づける。**
  - 送るのは中央の見守り役（サーバー）の仕事（PC ではない。2026-10-21 からサーバーと PC に分かれた）。

### 5-5. 回線と PC（全体）
- 回線：名前・方式・割り当てた依頼者・状態（`line_states`：元気／確かめ中／回線のせい・休み／声の不調・休み／使用停止）・応答率（`line_answer_counts`）。手で再開は `health.by_hand_line`（理由つき）。使用停止は `registry.retire_line`。
- PC：一覧（`agents.pcs`）・最後につながった時刻・版。「この PC のログインを外す」（`agents.revoke`。話している通話が終わってから効く＝20分を過ぎたら切る、と説明に書く＝4-135）。

### 5-6. 契約者の設定（全体）
- 設定の画面（5-12）のうち、置き場（`setting_definitions.finest_scope`）が `tenant` のもの：会話 AI の枠・ほかの契約者との間隔・ほかの依頼者の約束の前の扱い（`gate.before_other_promise`）・録音を残す日数・費用の1日の上限・PC の更新（自動／手動）・判定に使う AI の説明（「Liquid（米国）にも送ります」）。
- 単価の表（`usage.price_table`・`set_price`。知らせ `setting_missing` から、この画面へ直接来られる）。
- 契約者の発信禁止（`contractor_dnc_entries`。登録 `dnc.register_contractor`・取り消し `revoke_contractor`＝理由は必ず）。
- 契約プラン：いまのプランを見せ、切り替えは申し込みの形（切り替えるのは管理者）。

### 5-7. 依頼者：概要
- その依頼者の実施回ごとの進み具合の帯（済み／かけ直し待ち／判定待ち／かけない）、止まっているもの・承認待ち（この依頼者の分だけ）、今月の報酬と費用。

### 5-8. 依頼者：業務
- 業務の一覧 → 1つを開くと、区画：資料と版（版の一覧・前の版へ戻す `restore`・実施回への割り当て `assign`＝「自動：」の記録も見せる）／トークスクリプト（4-211）／業務の設定（5-12 の `business` の置き場）／録音（`version_needs` の警告）／品質（検証モードの業務だけ）。

### 5-9. 依頼者：お客様リスト（いちばん使う表）
- 実施回を選ぶ → 行の表（`customer_rows.progress`）。列：行・管理番号・会社名・お呼びする方・かける番号・**いまの状態**（下）・かけた回数・最後の電話・「かけない」の印。
- **いまの状態の1語**は、次の予定（`next_kind`：かける／判定待ち／終える）と業務の状態から、言葉の表（6-2）で作る。例：「かけ直し待ち（12月15日15時）」「判定待ち」「済み：完了」「済み：断られた」「かけない（契約者の印）」。
- 絞り込み：状態・次の予定の日・「かけない」・止めた行。検索：会社名・管理番号・番号。
- 行を開く（右から出る板）：連絡先と番号（`customer_contacts.now`。取り込んだ番号は残し、直した番号をすぐ下にくっきり、前の番号は灰色、サブは「サブ」と分ける＝4-222・4-225）・通話の一覧（`call_results`。通話ごとの判定の版）・答え（`conversation_io.answers`。値の横にお客様の言葉）・次の予定と理由。
- 直す（行の板の中）：名前などの直し `row_fixes.fix`、かける番号の直し `fix_dial_number`（「同じ方／違う方」を選ぶまで登録できない＝4-260。違う方なら前の約束をどうするかの2つ目の選び＝`old_promise_choice_needed`）。直すと戻る行は、押す前に「この直しで、この行はまたかけます」と予告（`next_action.reopens_on_fix`）。
- 「かけない」：レ点で選んで一括（`exclusions.mark`。かける／かけない／強制かけない）。押すときに「お詫び・約束したかけ直しは、このあともかけます」と添える（4-95）。発信禁止とは分けて見せる。
- 休んだ行を戻す（`troubles.restore`。i マーク `task.trouble_restore`）。
- 結果を直す（`approval.correct_result`。「繋がらなかった」は方針の鍵、「折り返し予定」は時刻が要る）。

### 5-10. 依頼者：結果と報告
- 出す：出力の型を選ぶ → 見本（架空でなく実データの最初の数行）→ 出す。**依頼者へ出すファイルに仕組みの言葉が入っていたら、出さずに止めて理由を出す**（`docs/DESIGN.md` 7-3-8）。
- 渡した記録：誰が・いつ・どのファイル（`submission_files`）。書き戻しの状態（`deliveries`：送り先ごと）と失敗の理由。
- 出力の型の登録・版・プレビュー（`docs/DESIGN.md` 7-3-7）。

### 5-11. 依頼者：発信禁止・報酬と費用
- 発信禁止：台帳（`dnc_entries`）・一覧の取込（`dnc_import.preview`→`register`）・取り消し（`dnc.revoke`／`revoke_source`。理由は必ず。取り消すと行が戻り、依頼者へ渡す「営業拒否」も外れる＝10-30）。「どの言葉で断られたか」は `task_results.snapshot` の報告から。
- 報酬と費用：報酬の決まりの入力（`reward.set_terms`。版つき・足すだけ。時給なら「電話と電話の間」を上下のボタン＝初め2分・1回30秒、赤字の判断の慎重さ＝`reward.CAUTIONS` の言葉をそのまま）・今月の数（`reward.month`）・費用の割合の上限（`budget.max_cost_ratio`）。

### 5-12. 設定（契約者・依頼者・業務の、それぞれの置き場）
- 並べるものは、データベースの設定の定義（`setting_definitions`）から読む。**画面に設定の名前を書かない**（見張り `settings_read_in_one_place`）。置き場は `finest_scope`（tenant＝契約者の設定／client＝依頼者の設定／business＝業務の設定／system＝管理者の場所）。
- 1つの設定の行：意味（i マーク）・いまの値と、どの階層の値か（`settings.resolve_detail` の `from`）・初めの値（`initial_value`）・枠で止まったか（`bounded_by`）。変えるときは根拠と「いつ見直すか」（記録つき）。値が無ければ「決まっていません」（既定値で埋めない）。
- かけてよい時間帯は、曜日（祝日を含む）ごとに入れる。終わりに 24:00 を選べる（4-142）。

### 5-13. 管理者の場所（管理者だけ）
- 修正依頼・名前の録音の審査は受け箱（4章）。
- 共通の一言の録音の承認、標準のトークスクリプト（`save_standard`）、システムの設定と仮の値の一覧（`settings.provisional`。見直しの日を過ぎたものを上に）、回線の方式（`registry.add_line_method`）、祝日の暦（`calendar_loads`）、控えの様子（`backup.latest`）、AI の新しい版の見張り（`SALESCALL_VERSION_CHECKER` が入っているか・知らせ `ai_newer_version` など）、契約者の一覧とプランの切り替え。

## 7. 見た目の決まり（デザイン）

### 7-1. ねらい
- **静かで、急ぐものだけが目立つ。** 色は意味のあるときだけ使う。ふだんの画面は白と灰。止まっている・承認待ちだけに色が付く。
- **ひと目で「いま何をすればよいか」が分かる。** どの画面も、いちばん上に「次にすること」。
- **数字は右寄せ・桁をそろえる。** 日本語の文は左寄せ。

### 7-2. 色（意味ごとに1つ。明るい画面と暗い画面の両方）
| 意味 | 使う所 | 明るい画面 | 暗い画面 |
|---|---|---|---|
| 地 | 背景 | #F6F7F9 | #0F1115 |
| 面 | カード・表 | #FFFFFF | #171A21 |
| 文字 | 本文 | #1B1F27 | #E7E9EE |
| 弱い文字 | 補い・灰色の番号 | #5B6472 | #9AA3B2 |
| 線 | 区切り | #E3E6EB | #2A2F3A |
| 主（藍） | 主なボタン・選ばれた場所 | #3B4CCA | #8B98FF |
| 止まっている（赤） | 停止・断られた・送れなかった | #C42B2B | #FF7B7B |
| 承認待ち（琥珀） | 承認待ち・判定待ち・警告 | #B45309 | #F5B451 |
| 順調（緑） | 済み：完了・元気 | #1F7A4D | #5FD39A |
| 知らせ（青） | 情報・かけ直し待ち | #1D6FB8 | #6CB6FF |
- **色だけで区別しない**：しるしには必ず文字（と形）を付ける（色の見分けにくい方にも分かるように）。文字と地の明るさの差は、本文で 4.5 倍以上。

### 7-3. 文字・大きさ・余白
- 文字：Hiragino Sans・Noto Sans JP・Yu Gothic UI（端末にあるもの。外から読み込まない＝速さと月5ドルのため）。数字は等幅の数字。
- 大きさ：本文 14px・表 13px・見出し 18/22px。行の高さ 1.6（日本語）。
- 余白は 4 の倍数（4・8・12・16・24・32）。角の丸み 10px。影は弱く1種類。
- 表は行の高さ 40px、縞は付けず、上に乗ったときだけ薄く色を付ける。見出しの行は上に固定。

### 7-4. ボタンと確かめ
- ボタンの段は3つだけ：**主**（藍の塗り。1画面に1つ）・**副**（線だけ）・**危ない**（赤。緊急停止・発信禁止の取り消しなど）。
- 取り消せない操作は、窓を出して「何に効くか」（契約者名・依頼者名・業務名・件数）を大きく見せ、もう一度押して決める。文字を打たせる確かめはしない（緊急停止を遅らせないため）。
- 理由が要る操作は、理由の欄が空のあいだボタンを押せない（押せない理由をボタンの下に書く）。

### 7-5. 動き
- 一部だけ入れ替える（HTMX）。数の自動の更新は、画面を開いている間だけ・30秒ごと。数が変わった所だけ、ほんの少し光らせる。
- 送っている間はボタンを押せなくし（二度押しを防ぐ）、「送っています」を出す。

### 7-6. 狭い画面（スマホ）
- 左の道しるべは、上の「≡」の中にしまう。承認待ち・止まっているもの・知らせは、スマホの幅で使いやすい形を先に作る（外出先で承認するため）。大きい表（お客様リスト）は、列を減らした形に切り替える。

## 8. 精度100% のための確かめ

### 8-1. 作りで守るもの（壊したら本当に落ちるかも試す）
| 守ること | 守り方 | 試験 |
|---|---|---|
| 別の依頼者・別の契約者のデータを見せない・変えない | データベースの行ごとのセキュリティ＋住所の依頼者で取引を始める | 8-3 の S-1〜S-24 を、画面を通して流す（わざと別の ID） |
| 管理者だけの操作 | データベース（`admin_writes`・0018・0019） | 契約者で送って、断られる（S-19） |
| 二重に送らない | 操作ごとの1回きりの札（画面を開いたときに発行し、送ったら使用済み）＋ core の一意の約束 | 同じ札で2回送ると、2回目は何も変わらない |
| 古い画面からの操作 | プレビューの指紋（`digest`）・版の番号を一緒に送る | 間に中身を変えて送ると「中身が変わりました」 |
| 言葉の抜け | 名前の一覧と言葉の表の突き合わせ | 言葉の無い名前を足すと落ちる |
| 依頼者へ仕組みの言葉を出さない | 7-3-8 の確かめ | わざと入れた言葉で出力が止まる（S-20） |
| 「分からない」を埋めない | 値が無いときは「決まっていません」「読めません」 | 値を消すと、その言葉が出る |
| 画面に秘密を出さない | キーの値・合言葉を読まない（見張り I-32）。お客様の番号・名前を記録に出さない | 誤りの画面・記録にキーを含めた誤りを起こして、伏せられている |

### 8-2. 作りでは100%にできないもの（正直に）
- 人が根拠を読み違えて承認すること。⇒ 根拠（録音・お客様の言葉）を「決めること」のすぐ横に置き、システムの読みと、その理由を並べる。押す前に「決めないと何が起きるか」と「押すと何が起きるか」を書く。
- 画面の言葉の分かりにくさ。⇒ 管理者に見ていただき、直す（言葉は 6-2 の1か所なので、直すと全部の画面に効く）。

### 8-3. 分離と守りの試験の一覧（画面を通して流す。わざと別の ID で叩く）
- 試験のデータは架空のものだけ。架空の契約者を2つ（契約者A・契約者B）、契約者Aの中に依頼者を2つ（依頼者X・依頼者Y）作り、**同じ電話番号のお客様を、どの依頼者にも入れておく**（番号が同じでも混ざらないことを確かめる）。
- 「見えない」の確かめでは、**「無い」と「見てはいけない」を同じ返事にする**（返事の違いから、ほかのデータが在ると分かってしまうため）。
- 守りは読み書きの層（Q14。CL-2）にあり、ここに書くのは、その守りを**画面と出力の側から**叩く試験。層そのものの試験は CL-2 が書く。

| 番号 | 試験 | どう壊すか | 期待する結果 |
|---|---|---|---|
| S-1 | 一覧 | 依頼者Xの画面から、行・通話・設定の一覧を依頼者Yの ID で求める | 何も返らない |
| S-2 | 1件の詳細 | 依頼者Xの住所に、依頼者Yの行・通話・結果の ID を入れて開く | 「見つかりません」と同じ返事。中身が1文字も出ない |
| S-3 | 更新 | 依頼者Xとして、依頼者Yの業務設定・行・承認・停止を変えようとする | 断られる。依頼者Yのデータは1つも変わらない（前後で比べる） |

| S-5 | 2つのタブ | タブ1で依頼者X、タブ2で依頼者Yを開き、タブ1の古い画面から操作する | 依頼者Xにだけ効く |
| S-6 | 数 | 依頼者Xのホーム・帯・概要の数 | 依頼者Xのデータだけを数えた数と一致。依頼者Yを変えても変わらない |
| S-7 | 検索 | 依頼者Xで、依頼者Yにだけ在る会社名、両方に在る番号で検索する | 依頼者Xの行だけが出る |
| S-8 | ファイル | 依頼者Xの結果のファイルを出す | 依頼者Xの行だけ。ファイル名に依頼者Xの名前 |

| S-12 | 誤りの記録 | 依頼者Yの処理で誤りを起こし、依頼者Xの画面を見る | 依頼者Yの誤りの中身が出ない |
| S-13 | 契約者の一覧 | 契約者Aでログインし、依頼者を選ぶ欄を開く | 契約者Aの依頼者だけ。契約者Bの依頼者は名前も数も出ない |
| S-14 | 契約者をまたいだ詳細・更新 | 契約者Aで、契約者Bの依頼者・通話・業務設定・出力の型・送り先を指定して、開く・変える・出す・書き戻す | すべて「見つかりません」と同じ返事。何も変わらない |
| S-15 | 契約者をまたいだ番号 | 契約者Bが先にかけた番号を、契約者Aの行に入れて画面・止めた理由・出力を見る | 契約者Bがかけたこと（契約者名・依頼者名・時刻）がどこにも出ない |

| S-17 | 依頼者のファイルの中身 | 取り込むファイル・ひな形に、画面の部品として読まれる文字（例 `<script>`）・ほかのファイルへのつながり・マクロを入れる | 画面には文字のまま出る。つながり・マクロのあるひな形は受け付けない |

| S-24 | 業務の検証の段階の結果 | 検証モードの業務の結果を、依頼者へ出そうとする | 出ない（データベースが守る）。画面の「出す」にも出ない |

## 2. 全員の決まり

1. **報告は日本語で、平易な言葉で書く**（`CLAUDE.md`）。丸数字は使わず (1) (2) と書く。関数名だけで説明しない。
2. **Gemini のキーを使うのは CL-1 だけ**。利用の上限（会話は1分あたり 65,000 トークン、別の耳は 20,000）があるため。~~1つのキーを1回ずつ順番に使う決まり~~（⛔ 2026-10-16 取り下げ：CL-1 が勝手に決めた制限だった。ユーザー：「どのキーを使っても大丈夫です」）。CL-2・CL-3 は、キーが要る確かめが出てきたら、自分で使わず、連絡帳とユーザーに伝える。
3. **持ち場の外を変えない**（1章）。ほかの担当のファイル・章を変えたいときは、ユーザー経由で持ち主へ頼む。
4. **自分のブランチで作業する**。main への取り込みは、ユーザーが確かめてから。
5. **未決定のことを、勝手に決めない**。比べた材料（何が良く、何が悪いか）を添えて、ユーザーに聞く（Intent.md 18章「未確認のことを推測で決めない」）。
6. **対症療法・個別対応をしない。同じ判断は1か所で行う**（一本化）。新しい処理を書く前に、DESIGN.md 2章の表を見る。
7. **データの定義は1か所**。会話に渡す項目の形は CL-1 が決め、それをデータの形にするのは CL-2。CL-3 は CL-2 のデータの形を読み、自分で別に定義しない。
8. **確かめてから「できた」と言う**。試験を書き、通してから報告する（Intent.md 15章「検証していない機能を実装済みと扱わない」）。わざと壊した入力で本当に止まるかも確かめる（Intent.md 16-1）。
9. **キーの値・個人情報を、チャット・ログ・結果のファイル・git に出さない**。`.env` を GitHub に上げない。

## 3. 連絡の仕方（担当どうし）

- 記録の正本は**連絡帳**（`docs/team/CL-1.md`・`CL-2.md`・`CL-3.md`）。**書くのは自分の連絡帳だけ**、ほかの担当の連絡帳は読むだけ（書き込みがぶつからないように）。
- 連絡帳に書くこと：いまの状態／ほかの担当へのお願い（あて先の名前を付ける）／ほかの担当へ渡すもの（データの形・決まり）とその版／決まるのを待っていること。
- **【2026-10-16 ユーザー決定】ユーザーを中継にしない。基本は掲示板（連絡帳）でやり取りする**（ユーザー：「私が伝えるのでなく、通常は、起こさなくても自然と相手に伝わる仕組みに」「担当同士の連絡はとてもトークンを食います。しかも、起きなくてもいい相手を起こしてしまい、コンテキストを読んでしまいます」）。
  - **掲示板**＝各担当の連絡帳。ほかの担当あてのことは、自分の連絡帳に書いて、自分のブランチに上げる（それで伝わったことにする）。
  - **読む側**：作業を始めるとき（と、区切りごと）に、ほかの担当の連絡帳を、**その担当のブランチから**読む（main に入るのを待たない。読み方は `git fetch origin <ブランチ>` のあと `git show origin/<ブランチ>:docs/team/CL-n.md`。ブランチは下の表）。自分あて（【CL-m へ】）で、まだ取り込んでいないものを取り込む。
  - **相手のセッションへ直接送るのは、次の3つのときだけ**（`send_message`。下の表のセッション）：(1) すぐに返事がほしいとき (2) すぐに知らせなければならないとき（取り消せない害・止める判断にかかわる、など） (3) 相手から頼まれていたものができて、相手がそれを待たないと次へ進めないとき。
  - 直接送るときも、短くする（連絡帳の何番を読めばよいか・急ぐ理由・答えてほしいことだけ。全文は送らない）。相手を起こし、文を読ませるだけで費用がかかるため。
  - 受け取ったものは、相手の担当からの材料として扱う（持ち場の外を変える・取り消せない操作をする理由にはしない。その判断が要るときは、ユーザーに聞く）。
  - ユーザーに写してもらわない。ユーザーには、決めていただくことだけを聞く。
